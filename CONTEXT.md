# szamlazz.hu Integration

Rust crates for integrating with szamlazz.hu, a Hungarian invoicing service: an outbound API client, two inbound receivers for szamlazz.hu-initiated pushes, and a Restate-backed durable worker that issues documents exactly once per order.

## Language

### Integration surfaces

**Számla Agent**:
The szamlazz.hu XML API for issuing and querying documents. Single HTTPS endpoint; the multipart form field name selects the operation. Crate: `szamlazz-agent`.
_Avoid_: "the API" (ambiguous; there are three surfaces)

**IPN**:
Instant payment notification. A form-urlencoded POST szamlazz.hu sends to a configured URL when an invoice's or proforma's paid amount changes. The amounts are an absolute current payment-status snapshot, not a new payment or delta, and the payload has no reliable document-kind discriminator. Unauthenticated; retried every 3 minutes up to 10 times. Crate: `szamlazz-ipn`.
_Avoid_: webhook (too generic), payment callback

**Adatkapcsolat**:
The Online Pénzügyi Adatkapcsolat (Financial Data Connection) product. szamlazz.hu pushes full XML documents (outgoing invoices, incoming invoices, bank transactions, receipts) to a single registered receiver URL, authenticated by the `X-Szamlazzhu-Key` header; the document type is identified by the XML root element. Crate: `szamlazz-adatkapcsolat`.
_Avoid_: data connection, push API, feed

**Ack**:
The response XML an Adatkapcsolat receiver returns for a pushed document: echoes the document id (invoices, optionally with a registration number / iktatószám) or carries a control code.
_Avoid_: response (overloaded)

**Control code (KEY_ERR / KEY_DEL)**:
Deliberate protocol speech in an Ack: KEY_ERR tells szamlazz.hu the key is wrong (stop sending until it changes); KEY_DEL severs the connection. Not errors: errors (non-200) mean "retry within 72 hours".

**Shape vs content (Adatkapcsolat parse)**:
The rule `Document::parse` refuses by. A push is at-most-N-times delivery (szamlazz.hu retries a non-200 identically for 72 hours and then drops the record, for a bank transaction or receipt for good), so a deterministic refusal loses data, and the parse refuses only what the receiver cannot Ack: *shape*: not UTF-8 or XML, an unknown root or namespace, a missing document id (and an invoice's `szamlaszam`), a number or boolean not of its lexical type. Everything else is *content* and reads as the wire delivers it: an element the XSD requires but the push omits is `None`, an unknown `irany` is `TransactionDirection::Other`, a `<pdf>` that does not decode is `None` with the encoded text in `raw_xml()`, a date that is not a date (`<kelt>2015-12-01junk</kelt>`, `<kelt>é12345</kelt>`) is `None` with its text in `raw_xml()` (#122: the one lexical failure read as content; the crate already reads `xs:date` on its own terms, discarding the timezone suffix a civil date cannot hold, and the strip once split the text by a byte offset and panicked inside a multi-byte character, after the key check, leaving szamlazz.hu no answer; the `de` helpers never index or split wire text by a byte offset without a char-boundary check), an empty receipt batch has no receipts. The XSD's requirements are a **signal** (`Document::validate` (or the per-document `validate()`, `ValidationError`)) or an explicit **gate** (`Document::parse_strict`, `ParseError::Validation`), never the default; a date read as `None` for its text is reported by them, where the XSD requires the date, as the requirement it fails to meet (`missing required invoice alap/kelt`), the same as an omitted one (an optional date, `elszDatTol`, a buyer ledger `datum`, is `None` with no signal). The router's authenticated `400` is for shape only. Decision: #95 (review findings B-01, B-02, J-01), #122.
_Avoid_: strict parsing as the default, "invalid document" for a merely incomplete one in prose (`ParseError::Validation`'s display text `invalid document structure: …` is kept verbatim from 0.3; a `parse_strict` caller's messages did not change), required field (the XSD requires; the parse does not), "a value not of its lexical type" as shape without qualification (a date's is content since #122), a panic as a way to answer wire text (nothing on the parse path panics on content; a panic after the key check leaves szamlazz.hu no answer)

### Documents

**Invoice (számla)**:
A finalized request for payment, identified by an invoice number (számlaszám). Created via the Agent's invoice operation.

**Invoice direction (outgoing / incoming)**:
Which ledger side an invoice sits on for the account holder: outgoing (kimenő) = issued by the account holder, incoming (bejövő) = received from a supplier and registered with szamlazz.hu. Orthogonal to invoice kind (proforma, storno, prepayment, …). Distinct from bank-transaction direction: an incoming invoice is settled by an outgoing transaction.
_Avoid_: sales/purchase invoice, AR/AP, inbound/outbound

**Proforma (díjbekérő)**:
A payment request that is not yet an invoice. Created via the invoice operation with a flag; deletable (real invoices are not: they can only be reversed).

**Prepayment invoice (előlegszámla)** / **Final invoice (végszámla)**:
Advance invoice and the invoice that settles it. Both are invoice-operation flags. Like the plain invoice, either may name the proforma it converts (`dijbekeroSzamlaszam`; `InvoiceKind::Prepayment { proforma_number }`, `InvoiceKind::Final { prepayment_number, proforma_number }`: the XSD lists the element independently of the kind flags, #69), and the worker's `create_prepayment` takes `options.proforma` exactly as `create_invoice` does (`create_final` does not: the order's proforma was consumed by the prepayment invoice). szamlazz.hu links the prepayment invoice to the final (`elolegSzamlaszam` or shared order number) but does **not** net it into the final's totals: the final invoice lists the full performance and deducts the prepayment as a negative line at the same VAT rate, supplied by the caller (behaviour note C6-2).
_Avoid_: a final invoice "netted by the server", a prepayment invoice as unable to carry the proforma reference (the pre-#69 shape)

**Corrective invoice (helyesbítő számla)**:
An invoice that corrects a previously issued one, referencing its number.

**Storno invoice (sztornó)**:
The reversal of an issued invoice. A distinct Agent operation, not an invoice flag. Idempotent on the server: repeating the storno of an already reversed invoice echoes the existing storno number as success, with no error code and no second document. Sent on a proforma or delivery note it is a success-shaped no-op that echoes the requested number unchanged. Its fulfillment date (`teljesitesDatum`) must equal the original's `telj` (NAV allows a storno no other date), so the worker's storno handlers (`Szamlazz.Order.storno_invoice`, `Szamlazz.Agent.storno`) always send the verified original's `telj` explicitly, never a caller's date (`StornoRequest` has none; ADR 0007); szamlazz.hu defaults to that date when the element is omitted and accepts any other date silently, so the explicit send is what fails loudly. A verified original without a `telj` (szamlazz.hu's schema has it mandatory) is the `unavailable` fault with nothing sent, raised after the answers that need no send (not managed, account mismatch, already reversed, not stornoable). Never `keltDatum` (352).
_Avoid_: cancellation, void, a caller-settable storno date

**Receipt (nyugta)**:
A simpler proof-of-payment document with its own create/reverse/query/send operations. The only document type with an idempotency key (hívásazonosító).

**Delivery note (szállítólevél)**:
A non-financial document listing delivered goods; an invoice-operation flag.

### Agent concepts

**Agent key (számlaagentkulcs)**:
API-only credential passed inside the request XML. Preferred over username/password.

**Credit entry (jóváírás / kifizetés)**:
A payment registered against an invoice via the Agent. IPN reports the resulting current payment status, not the individual credit entry.
_Avoid_: payment (overloaded; reserve for the buyer's act)

**Response version (válaszverzió)**:
Agent request field selecting the response body format: 1 = plain text or raw PDF bytes, 2 = structured XML with base64 PDF.

**Invoice appearance (`eszamla`)**:
Whether a document is a paper invoice or an e-invoice. A boolean on the create and storno requests (`eszamla`, default `false` = paper); an integer code in a queried document, `szamlazz_agent::ops::query_xml::InvoiceAppearance`: `0` not an invoice (a proforma), `1` paper, `2`/`3` e-invoice, anything else `Unknown`; the vendor annotation, confirmed on the test account (#73): a create with `true` is queried back as `3`, one with `false` as `1`; `2` was never observed. szamlazz.hu does **not** require a storno's `eszamla` to match its original's: a mismatch is accepted silently and the `SS` takes the *request's* flag, numbered under the account's e-invoice prefix (`E-…`) when `true`, so the worker's storno handlers lift the flag from the verified original (`FoundDocument::e_invoice`, read off the journaled `appearance` code through `InvoiceAppearance`: `Paper` → `Some(false)`, `Electronic` → `Some(true)`, else `None`, which `StornoIntent::from_verified` fills with the account's `defaults.e_invoice`), never from the caller, exactly as they lift `telj` (ADR 0007); that derivation, not the server, is what keeps a reversal in its original's form. Every queried document of the 2026-09-03/06 probes reported `1`: paper (the P60 stornos, numbered `E-…` and never queried, were by that numbering e-invoice stornos of paper invoices); 352 (`keltDatum` must be today on a storno) was observed there on a paper storno, so it is not a rule of e-invoices only.
_Avoid_: e-invoicing "enabled" as a reading of `<eszamla>1</eszamla>` (the pre-#73 behaviour-note premise; `1` is paper), `eszamla` as a flag in a queried document (it is a code), a caller-settable storno `e_invoice`

**Outstanding amount (kintlévőség)**:
The unpaid remainder of an invoice's gross total.

**VAT rate (áfakulcs)**:
A numeric percentage or a NAV-defined special code (AAM, TAM, EUT, KBAET, …) on a line item. The code set is NAV-driven and changes over time: it is an open set, not a fixed enum. A percentage's wire token is normalised (`27.00` → `27`, `5.50` → `5.5`), hygiene, not a requirement: szamlazz.hu accepts `27.00` and `27.0` too (test account, P60), and a queried rate comes back as the double `27.0`.

**Line item (tétel)**:
One row of a document: name, quantity, unit, net unit price, VAT rate, and net/VAT/gross values whose arithmetic szamlazz.hu verifies server-side. When the crate derives the values (`LineItem::try_calculated`) the rounding is an explicit `Rounding`: the currency's *minor unit* (whole forints for HUF, cents for EUR; the choice the worker makes for every document), a fixed scale, or exact; half away from zero at each step, and a value that does not fit a decimal is `ArithmeticError`, never a panic (the infallible `calculated*` forms panic, documented). The worker answers that error as `invalid_input`. Minor-unit is what szamlazz.hu stores anyway: it rounds every sent value to two decimals on its own, each independently and without recomputing the gross, so an exact `100.004 / 27.00108 / 127.00508` becomes a stored `100 / 27 / 127.01` (P60); rounding per step on our side is what keeps the stored document consistent. Its `net = price × qty` check (259) tolerated a 0.5–2 HUF discrepancy and refused 5 (P60), so the half unit the rounding can introduce is inside.
_Avoid_: "currency-aware" for `calculated_for_currency` (it is exact, not minor-unit, for every currency but HUF, the pre-#60 default, kept only on that method), unrounded/exact as a default

### Restate worker concepts

**Order**:
The Restate Virtual Object through which every document of one order number is issued, registered with Restate as `Szamlazz.Order`. Its key is the order number (rendelésszám) trimmed of leading/trailing whitespace **by the caller**, case preserved, exactly what szamlazz.hu matches on; a key that is not already trimmed is refused as `invalid_input` before the *Prologue*, because Restate's per-key lock is on the raw key and ` ORD-1` would be a second instance of `ORD-1`'s order with its own lock and the same external ids (the order-key type itself stays lenient for the places that parse an order number rather than a key). The key's alphabet is strict where szamlazz.hu's behaviour is unverified (ADR 0002, #64): 1–40 bytes after trimming (a dashed UUID fits), no control character, **no internal whitespace of any kind** (a space, an NBSP), no `:` (the *External id* separator) and Unicode NFC; nothing is case-folded, collapsed or normalised; a key outside the alphabet is `invalid_input` naming the rule, because a `rendelesszam` the server stored differently from the key would strand the order behind `conflict{external_id_collision}`. It carries no account marker, because Restate namespaces the key per *Scope* (the same order number under two scopes is two instances with two locks). It keeps no state: the object exists for its per-key lock (same-key handlers run one at a time, which serializes issuing per order), and every handler answers from szamlazz.hu (the *Account* the invocation resolved to) through the order's external ids. Every handler first runs the *Prologue*: it pins the namespace, resolves the request's scope to its *Account* in a durable step named `account` (once per invocation, journaled, so the invocation finishes on the account it started on), fetches the credentials outside the journal for this execution, and opens the *Gateway* for this execution; nothing of that outlives the execution. Every document one of its handlers finds by number (the invoice a storno or corrective names, the proforma of `options.proforma: {number}`) must carry this order's number (else `conflict{not_managed}`) before it is acted on or linked. Type of the key: `restate_szamlazz::identity::OrderKey`. Crate: `restate-szamlazz`.
_Avoid_: order object, invoice workflow, ledger (there is none; szamlazz.hu is the source of truth), tenant object, a single internal space as allowed (the pre-#64 rule refused only runs)

**External id (szamlaKulsoAzon)**:
The Agent's optional per-document identifier, used by the worker as the identity handle. Deterministic from the key alone under the deployment's *Namespace* (`{namespace}:{order}:{kind}` for the four kinds, `{namespace}:{order}:corrective:{correction_id}`, `{namespace}:{order}:storno:{number}`, `{namespace}:by-number:{number}:storno` for an unmanaged storno), so any invocation can find what an earlier one issued; the two-segment `{namespace}:check-account` is the sentinel *check_account* probes and nothing the service issues carries. Bounded at **110 bytes** (`ExternalId::MAX_LEN`; the length verified accepted and queryable on szamlazz.hu, which documents no limit; a truncated id would make every leading query by the full id answer "not found" and a lost reply re-send) by bounding its parts: the namespace at 16, the *Order* key, the `correction_id` (`CorrectionId`) and the caller's *Invoice number* at 40 bytes each, so the longest shape, `{namespace}:{order}:corrective:{correction_id}`, is 109; proven at compile time in `identity.rs`. Its segments are separated by `:` (`ExternalId::SEPARATOR`), which every caller-supplied part excludes, and its eight fixed tokens (`ExternalId::TOKENS`: the five kinds, `storno`, `by-number`, `check-account`) are not correction ids in any letter case, so no composition reads as another. It carries no account marker: the namespace is one per deployment and shared by every account, and the *Scope* selects the account. Not unique server-side and never echoed in responses: a query returns the newest holder, and every document found by it is validated (order number, `tipus`) before it is trusted; nothing about the account (see *Account*). The only namespace marker any worker response carries.
_Avoid_: idempotency key (szamlazz.hu does not treat it as one), generation (no counter; the newest holder is the answer), external reference, account id or scope inside it (the scope selects the account; the id carries only the namespace), hashing (the parts are bounded so the id never needs it)

**Invoice number (as the caller sends it)**:
The `invoice_number` of the by-number requests (`Szamlazz.Agent.query`'s selector, `set_payments`, `storno`, `Szamlazz.Order.storno_invoice`, the base of `correct_invoice` and the `options.proforma: {number}` link) as the worker's contract type `restate_szamlazz::contract::InvoiceNumber`: 1–40 bytes, no whitespace, no control character, no `:`. Bounded because it flows into step names (`verify-{number}`, `storno-{number}`) and into the storno *External ids*; nothing is trimmed: a padded number is refused as a *Malformed body* (`invalid_input`, before the *Prologue*) rather than sent to szamlazz.hu to be answered 7. szamlazz.hu's own numbers (`E-TST-2026-123`) are far inside; NAV's `invoiceNumber` allows 50 characters. Distinct from `szamlazz_agent::InvoiceNumber`, the unvalidated wire type a number szamlazz.hu *reports* travels in; the worker's response types echo numbers as plain strings.
_Avoid_: `InvoiceNumberInput` (the `*Input` types mirror agent structs; this one mirrors nothing), an unbounded `String` in a request type

**Namespace**:
The external-id prefix of this deployment (`{namespace}:{order}:{kind}`); chosen by the operator, opaque to szamlazz.hu, permanent: changing it would hide every document issued so far. 1–16 bytes of `[a-z0-9-]`; `:` is excluded because it is the separator. One per deployment, shared by every *Account* it serves. Configured as the top-level `namespace` key of the deployment configuration, beside `[issue]`, `[read]` and `[resolve]` on `WorkerConfig`; it is not part of any account. Pinned per invocation in the *Prologue*. Type: `restate_szamlazz::identity::Namespace` (the deployment settings hold it).
_Avoid_: slug (the pre-#20 name), prefix (ambiguous with the invoice number prefix), tenant prefix

**Account**:
One szamlazz.hu account as the worker knows it: a resolver-owned id, endpoint (`account::Endpoint`: an `http` or `https` URL with a host and **no userinfo**; the endpoint is journaled with the account and shown in the Restate UI, so `user:password@` is refused at parse time; plain `http` stays allowed for a local mock or a proxy, and `Endpoint::is_cleartext` reports one on a host other than loopback as sending the agent key in cleartext, for a host's start-up log to `warn` on (#65)), document defaults, seller block and a *Credential ref*, never its agent key; resolved once per invocation and journaled, so an invocation finishes on the account it started on and the Restate UI can show it for the retention period without exposure. A *Journaled type*. **It carries no account pin**: nothing the worker compares a found document with. Ownership validation is about the document: under one of our external ids a document is ours when it carries the order number and the `tipus` of the kind (else `conflict{external_id_collision}`); found by number, `Szamlazz.Order`'s verifies require this order's number (else `conflict{not_managed}`). 0.3 pinned two fields of a queried document, `teszt` (`mode`, required) and `szallito/id` (`supplier_id`, optional); ADR 0006's account-pin amendment (2026-09-07) dropped both, with `AccountMode` and the `account_mismatch` fault: neither field is in a create response (a create's reply is a number and totals), so neither could fire before the first document of a fresh order had been issued into whatever account the key opens, and the reference value had to be read off the very account being checked (`szallito/id`, undocumented besides) or only told test from live (`teszt`). **The risk is accepted and stated**: a key under the wrong scope, a live key where a test one was meant or the reverse, issues there, answers `issued`, and nothing in the worker fails; the go-live check (the library README's *Go-live*, design §10: under each *Scope*, `Szamlazz.Agent.query` a document known to be the account's and read `test` and its *Seller block*) is what catches it. No namespace: that is a deployment setting. Type: `restate_szamlazz::account::Account`.
_Avoid_: tenant, customer, organizer (the caller's concept; an account is what an organizer or event maps to), account config (the static resolver's configuration is a different type), the agent key as part of it, mode / supplier id / account pin (all gone: ADR 0006, account-pin amendment), "fails loudly on its first found document" (the pre-amendment claim; the first document of a fresh order was never checked)

**Seller block (`<szallito>`)**:
The seller party of a queried document (the counterpart of `<vevo>`) as szamlazz.hu's own docs define the word: in standard invoicing the szállító issues the invoice to the buyer; in third-party invoicing (*Megbízott számlakibocsátás*, out of scope: a delegate issues with a dedicated login in the principal's account, and an agent key, which belongs to an account, never a user, cannot be used for it) the szállító is the *megbízó*, the company in whose name and account the documents are made. The block is the seller as printed on the document (`nev`, `cim`, `adoszam`, `bank`, and an `id` szamlazz.hu annotates nowhere), present in query bodies only, never in a create response; the same `szallitoTipus` names the third-party vendor on an incoming invoice, and the Adatkapcsolat re-pushes an invoice when the block's `bankszamla` changes, so it is per-document state. The Számla Agent crate parses it in full (`Supplier`; `.supplier.id` in the CLI's JSON). The worker **reads nothing from it**: 0.3 pinned its `id` as the account's `supplier_id` (an undocumented row id of unverified stability whose reference value could only be read off a document through the configuration it was meant to check, a tripwire that could not fire before the first wrong-account create and whose false positive would strand every order of the account), and ADR 0006's account-pin amendment (2026-09-07) dropped it, together with the `mode` pin on `teszt` (same blind spot; see *Account*). What replaces them is the go-live check (the library README's *Go-live*, design §10): under each *Scope*, `Szamlazz.Agent.query` a document known to be the account's and read `test` and this block's name and tax number. Considered, not taken: a pin on the seller tax number (documented, operator-known, what szamlazz.hu itself identifies an account by; the same tripwire with a trustworthy field), a configured canary document the probe and the create step would verify before a first send (the one shape that would gate).
_Avoid_: supplier id / supplier pin (the 0.3 pin; gone), supplier as an account identity, "the only server-side account identity a found document exposes" (the pre-amendment claim; there is none), third-party invoicing as in scope

**Credential ref**:
The opaque reference an *Account* carries to its credentials, handed to the *Credential store* on every handler execution (`CredentialStore::fetch(credential_ref)`). Owned by the resolver that produced the account; journaled with it, since it is not a secret. The static resolver sets it to the account's `id`. Type: `restate_szamlazz::account::CredentialRef`.
_Avoid_: reference without qualification (reserved for this), key id, secret name, scope (the scope selects the account; the ref selects its credentials)

**Account resolver**:
The pluggable trait (`AccountResolver::resolve(scope: Option<&str>)`) that maps a request's *Scope* to its *Account*; object-safe, boxed futures, no `Debug` requirement (#43: a resolver often holds a pool or a key table, and the crate never formats one; `Accounts`' own `Debug`, and so `Order`'s and `Agent`'s, names the two trait objects without descending into them, so a store that derives `Debug` over a key map cannot print its keys through the services). Answers as data: unscoped (no scope and no unscoped account), unknown (the scope names no account); `unavailable` is a retryable fault whose display text never echoes the source's own message. Its half of the safety contract, carried as a checklist on the trait's rustdoc: one szamlazz.hu account is reachable under exactly one scope value (unscoped counts as a value), no fan-in (the static resolver checks this at load time, a database-backed resolver must guarantee it itself, because the worker cannot detect fan-in at runtime and `check_account` only echoes configuration), the mapping is append-only, unique `(endpoint, credentials)` pairs, **the right key under the right scope** (the worker holds no account pin, so this is the resolver's guarantee, verified at go-live by reading `test` and the *Seller block* of a known document under each scope, never inferred by the worker; the `mode` matching `teszt`, the `supplier_id` recommendation, the unique-supplier-ids check and the *Prologue*'s `warn` on an unpinned scoped resolution of #88 are gone with the pins; ADR 0006, account-pin amendment), a stable *Credential ref* across rotations (rotate the value behind the reference, never the reference), and never caching the unscoped / unknown answers. The static resolver (`restate_szamlazz::account::StaticResolver`, built with `TryFrom` from serde-only configuration) implements both this and the *Credential store* with the agent key inline and `credential_ref = id`, in one of two mutually exclusive shapes: `[account]`, where `resolve(None)` is the account and any scope is unknown, or `[accounts.<scope>]`, where `resolve(None)` is unscoped and a scope is its account or unknown; the multi shape is checked at load time (unique `(endpoint, agent key)` pairs (the endpoint on its normalised form, `Endpoint::normalized`: scheme and host case, a default port written out, trailing slashes, so `…/szamla/` beside `…/szamla` with one key is one account, while the stored text and what the client posts to stay as written; #113) and ids; scope keys `[a-z0-9_]` of at most 36 bytes). There is no default account. Bundled with the store as `Accounts`, shared by both Restate services; the crate root re-exports `Credentials` and `AgentKey` (and the `restate_sdk` and `szamlazz_agent` crates) so an embedder implements both traits without a second dependency, and its `lib.rs` carries a compiling custom-wiring example (database-backed resolver, a credential store of the embedder's own, a service of the embedder's own on one endpoint) that names the two compiler errors that path hits: `account::Endpoint` vs `restate_sdk::prelude::Endpoint` (alias one) and, when one value is both resolver and store, `Arc::clone(&db)` inferring `Arc::<dyn AccountResolver>::clone` and failing where `db.clone()` coerces.
_Avoid_: tenant resolver, account lookup (lookup is the first durable step of issuing), directory, account cache (a resolver may cache internally; the worker does not), `Debug` supertrait (the pre-#43 shape)

**Scope**:
The Restate scope value a request arrives under (`/restate/scope/{scope}/call/…`); the caller's identifier for a szamlazz.hu account and the only channel for selecting one, never a header, a body field or the Virtual Object key. Opaque to the worker: it is handed to the *Account resolver* as is. Restate namespaces the Virtual Object key and the `Idempotency-Key` per scope (both are part of the invocation's identity, and the scope is the partition key), so the same order number under two scopes is two `Szamlazz.Order` instances and the same key under two scopes is two invocations; a path segment of each request, not a session: callers set it on every call. One account ⇔ one scope, and unscoped counts as a scope value (the single-account shape serves its account unscoped; the multi-account shape refuses unscoped requests). Format: Restate's `[a-zA-Z0-9_.-]`, non-empty, at most 36 characters (ASCII, so bytes; a dashed UUID is exactly 36); the static resolver's keys are the strict subset `[a-z0-9_]` so environment overrides can address them. Routing, not authorization: the ingress sits behind a gateway that sets the scope from the authenticated identity, never forwards a caller-supplied scope path and strips `x-restate-*` request headers. Reaches the worker only under protocol v7, which Restate's ingress does not gate a scoped path on: *check_account* per scope after every deploy is the check. Kafka ingress is untested in multi-account mode. Decision: ADR 0006.
_Avoid_: tenant id, tenant, account header, reference (see *Credential ref*), account id (the *Account*'s `id` is the resolver's own identifier, not the scope), event or organizer as the scope (they map to an account in the caller)

**Request identity (identity keys)**:
Restate's signature on every request the runtime makes to the endpoint, verified against the `publickeyv1_…` public keys a deployment registers on the SDK's endpoint builder (`Endpoint::builder().identity_key(…)`); with at least one key the endpoint refuses unsigned requests. What enforces the assumption the *Scope* model rests on (that only the Restate runtime speaks to the endpoint): the scope is protocol data inside the request, so an endpoint accepting unsigned requests lets any client reaching its port invoke either service under any scope, on every *Account* the deployment serves, and the gateway of ADR 0006 rule 6 sits in front of the ingress, not this port. Required wherever anything but the runtime can reach the port and **required** in the multi-account shape. The host's responsibility, not the library's: the SDK starts without keys, and nothing in `restate-szamlazz` can tell whether a deployment registered any (the removed `restate-szamlazz-endpoint` crate read the decision three ways and warned on an omission, #96; design §10 carries what a host does instead). Authenticates the runtime to the endpoint, never callers (that is the ingress gateway's job).
_Avoid_: caller authentication (ADR 0006 rule 6; the gateway's), "identity" without qualification (the *External id* is the document's; `identity.rs` is that module), signing key (the endpoint holds public keys only), `identity_keys` as a configuration key of this workspace (it was the endpoint crate's; a host names its own)

**Credential store**:
The pluggable trait (`CredentialStore::fetch(credential_ref)`) that returns an account's credentials by its *Credential ref*: the Számla Agent crate's `Credentials`, which has no serde implementation, so the compiler rejects any attempt to journal it (a narrow guard: `AgentKey::expose()` is one line from journalable; the e2e journal scan is the real guarantee). Its half of the safety contract: fetched on every handler execution, including replays, never journaled, held only for that execution; a rotation is picked up on the next execution of every in-flight invocation. Answers: the credentials, `gone` (the reference is not known; settled, so terminal at once: no attempt of the loop would answer differently), `unavailable` (retryable; display never echoes the source; retried in-process, three attempts 200 ms apart, then terminal); either way the fault is a terminal `unavailable`, never a Restate retry: a fault whose text tells the two apart but names neither the account nor the *Credential ref* (no response names the account, and a store's reference may be internal topology, a secret path; the operator's `warn` carries both, #65). Every `fetch` call is bounded by the worker at ten seconds (`prologue::CALL_DEADLINE`, a constant, not a setting) and dropped at the deadline: a store silent past it is retried like one that reported `unavailable`, then the terminal fault, whose text names the deadline (#114). The gateway is opened from a resolved *Account* and freshly fetched credentials (`Gateway::open`) over a fresh Számla Agent client every time, a boundary, not a performance choice: the default `reqwest::Client` keeps szamlazz.hu's `JSESSIONID`, and a shared client would carry one account's session into another's request.
_Avoid_: secret store (generic), key store, vault (a product), caching credentials across executions, session (the szamlazz.hu cookie is what the fresh client isolates)

**Idempotency-Key**:
Restate's ingress retry identity, sent by the caller as a header per logical request; Restate dedupes retries and attaches concurrent duplicates to the in-flight invocation. Deduplicated per *Scope*: the same key under two scopes is two invocations. Recommended, never relied on for safety. What to do with it after a failed call depends on whether the call got a **fault** or **no answer**. A fault (a 5xx with a body the worker wrote and `x-restate-error-source: invocation`) is a completed invocation whose stored completion Restate replays under the same key for the retention period (verified), so the key is rotated: the same key would repeat the failure instead of reconciling. No answer (a client timeout, an ingress 5xx whose source is not `invocation`) is an invocation still in flight, being re-dispatched by the server for as long as its invocation retry policy allows, so the key is **kept**: a retry with it attaches to the in-flight invocation and receives its outcome, while a new key would start a second invocation queued behind the first (#87). A killed invocation (its attempts exhausted) is a fault whose body is the last retryable error's text, not a `{code, message}`; the caller treats it as `outcome_unknown`. A Pretix-style caller uses the webhook notification id, which it cannot rotate: the reason kill is under review for the *Order* writes (ADR 0004, #87 amendment).
_Avoid_: request id (v1's body field; gone), correlation id, "rotate after any error" (only after a fault)

**Outcome**:
A domain result returned as data (HTTP 200): `issued`, `already_issued`, `reconciled`, `reversed`, `rejected`, `conflict{reason}`. Errors (`TerminalError`) are reserved for faults (the seven codes of `TerminalCode`, and nothing else): every fault either service raises carries one of them in `code`, with the status `TerminalCode::status` pins: `invalid_input` (400), `unknown_account` (400), `not_found` (404), `szamlazz_error` (422), `outcome_unknown` (500), `unavailable` (503), `credentials_rejected` (503). (`account_mismatch`, 409, was the eighth until ADR 0006's account-pin amendment; no handler compares a found document with the account any more.) A szamlazz.hu code never travels in `code` but in the fault's own `szamlazz_code` field, present on every fault a szamlazz.hu answer caused (`szamlazz_error`, `credentials_rejected`, `unavailable` on an inconclusive code). Three of the codes mean "outcome unknown, retry with a new `Idempotency-Key` or read `get`", never "no document exists": `outcome_unknown`, `unavailable`, `credentials_rejected`; the ingress marks them `x-restate-error-source: invocation`, which a caller pages on rather than auto-retries. The rest are settled (nothing landed): the three 4xx are raised before anything is sent, and `szamlazz_error` is szamlazz.hu answering with an error (to a read, or refusing the credit entries it was sent); retrying as is repeats the answer, so the caller fixes the request, the number, the scope or the account (or, for a `szamlazz_error` relaying a NAV outage, retries later with a new `Idempotency-Key`). `credentials_rejected` is szamlazz.hu answering 3/135/136/164 to any step: the worker's agent key is wrong, not the request; the request that drew the code was not acted on (szamlazz.hu answers these codes before acting), but the code may have come to a post-send re-query and an earlier execution may have landed, so it is a fault, never `rejected`, and 503 rather than a 4xx; its message says the outcome is not known, never that "this attempt issued nothing" (#63). `unknown_account` is the prologue's `account` step finding no account for the request: unscoped where accounts are scoped, or a scope no account is reachable by; raised before anything is issued, and the same request never succeeds, so the caller fixes the scope rather than retrying. `not_found` is a document the request names **by number** that szamlazz.hu does not know (code 7) (`Szamlazz.Agent.query`'s selector, the invoice of `Szamlazz.Agent.storno` or `Szamlazz.Order.storno_invoice`, the base of `correct_invoice`), one vocabulary across both services; never the answer to a missing proforma named by `options.proforma: {number}` (`conflict{proforma_missing}`, an outcome) or to `query_taxpayer` (NAV knowing no taxpayer is `valid: false`, a 200). `szamlazz_error` is a szamlazz.hu code the handler passes through rather than concludes from (`Szamlazz.Agent.query` on a code that is neither 7 nor a credential code, `query_taxpayer` on any `funcCode ≠ OK` (szamlazz.hu's or NAV's relayed one), `set_payments` on szamlazz.hu refusing the credit entries), with the code in `szamlazz_code` and szamlazz.hu's message; a NAV outage is therefore a terminal 422 the caller retries with a new `Idempotency-Key`. `unavailable` is the answer to an exhausted *Read policy* (szamlazz.hu did not answer a read through every execution the policy allows), naming the step and the last failure, about the document when the step knows one; it also covers a szamlazz.hu code a read cannot conclude from, and the same code, or `szlahu_down`, answered to the *Create step*'s or the storno step's leading query (settled data, nothing sent, never *Unconfirmed*; #63), a verified storno original without a `telj` (the date the *Storno invoice* must repeat, nothing sent; ADR 0007), and the prologue's own faults: the resolve policy exhausted, the credential store gone or unavailable. `invalid_input` is the caller's request: a *Malformed body*, refused by the handler's own decode before the *Prologue*, nothing journaled or sent; an *Invoice number* or a `correction_id` outside its bound is one, an *Order* key that is not already trimmed or outside its alphabet, or a *Taxpayer lookup* tax number in neither accepted form (refused likewise before the *Prologue*), or a request carrying a value the operation cannot take (an option the handler does not take, a `{number}` proforma link that is not a proforma, a sixth credit entry on `set_payments`, or a replacing `set_payments` with no entries; it would clear the invoice's payments (the wire contract takes five and the crate refuses the empty replace; the gateway's `request` pseudo-code, nothing sent)), a *Line item* whose arithmetic overflows a decimal (the handler's own validation, after the *Prologue*'s two entries because it needs the account's currency defaults and before any read; nothing sent, never a panic, which on the SDK's connection task would take every in-flight invocation down with it, #64); the same request never succeeds, so the caller fixes it rather than retrying. No response names the account; `external_id` is the only namespace marker, and `order_key` in a storno response is meaningful only under the same scope. On the wire a fault is the JSON **string** inside Restate's ingress envelope: `{"code": <HTTP status>, "message": "<the fault JSON>", "source": "invocation"}` under `x-restate-error-source: invocation` (server 1.7.8; the SDK carries a terminal error as code plus message and offers no other channel), so a caller parses `message` a second time, and the envelope's `code` is the status, never the token; a killed invocation wears the same envelope with the last retryable error's text in `message`. The body is the public `restate_szamlazz::contract::Fault` (`{code, message, szamlazz_code?, order?, kind?, external_id?}`; `Serialize + Deserialize`, open, `#[non_exhaustive]`, built with `Fault::new` and its setters; the service-side constructors are a crate-private inherent impl in `service::support`), which a Rust caller decodes `message` into: the e2e harness's `Reply::fault` does, rather than re-declaring the shape (#128). The library README's *Faults* section is the caller reference for it, the envelope asserted by the e2e harness's `Reply::fault`.
_Avoid_: error/failure for a rejection or conflict, status, "the fault body" for the envelope (the fault is inside `message`)

**Reissue**:
Issuing a new document of a kind after the one under its external id was reversed, by the service, the UI or anyone, at any distance in time: the service needs nothing from Restate to do it months later, only the key and the scope the caller recorded. Always explicit: `reissue: true` (with a new `Idempotency-Key`); without it the create returns `outcome: reversed`. Explicit because the service has no record of who reversed and cannot tell a stale retry of the original create from a deliberate new request; the flag on a live document is `conflict{live}`, so it can never cause a duplicate. The new document becomes the newest holder of the same external id. A reissue whose create reply was lost is reported as `issued` by the re-executed create step, not as a conflict.
_Avoid_: re-create, retry (a retry targets the same document)

**Reversal (as observed)**:
A document is reversed when szamlazz.hu reports `<sztornozott>true</sztornozott>` on it; the storno document carries `hivszamlaszam` = original and is the order-number hint only until something newer is issued under the order. The service does not track who reversed a document or when.
_Avoid_: reversal origin (v1 concept; gone), cancellation

**Foreign document**:
A live invoice-kind document (`SZ`, `ES`, `VS`) found under the order number by the order-number hint that is under none of this order's external ids: another channel or namespace on the same szamlazz.hu account. Detected live in the lookup step, on every kind but correctives, unconditionally (there is no setting); never adopted, nothing recorded; the create returns `conflict{foreign}`. The order's own live invoice, prepayment invoice or final invoice is never foreign: every create that could meet it looks its external id up first and is refused before the lookup step runs (`create_invoice` and `create_prepayment` in their exclusivity step against the other chain's id and `…:final` (`conflict{prepaid_chain}`; the final invoice outlives its reversed `ES`, so it needs its own row; #62), `create_proforma` against `…:invoice`, `…:prepayment` and `…:final` (`conflict{order_invoiced, existing_number}`: a proforma after the invoice makes no sense, but the invoice is ours)), so the hint never meets it. A duplicate-order-number answer (71/152) whose external-id re-query finds our document reversed or absent is the same situation seen from the create step: the order-number query names the existing document (`conflict{duplicate_order_number, existing_number?}`), never adopts it; a 71/152 with nothing under the order at all is settled the same way without `existing_number`, logged at `warn`; a refusal szamlazz.hu already gave is not re-sent for.
_Avoid_: external document, orphan, foreign for the order's own invoice met by `create_proforma` (that is `order_invoiced`)

**Lookup step**:
The first of the two durable steps of issuing (`lookup-{kind}`): one read-only `ctx.run` under the *Read policy* that queries our external id and, for every kind but correctives, takes the order-number hint. It settles every case that needs no create (a live document of ours (`already_issued`, or `conflict{live}` with `reissue`), a reversed one (`reversed{storno_number}`, or proceed with `reissue`), an invalid holder (`conflict{external_id_collision}`), a foreign document (`conflict{foreign}`)), and otherwise hands the create step what it saw. A query szamlazz.hu did not answer is *Unanswered* and re-executes the whole step; exhaustion is `unavailable{order, kind, external_id}`. Gateway fn: `Gateway::lookup` → `Result<LookupOutcome, Unanswered>`.
_Avoid_: pre-query (the create step has its own), attempt

**Ownership lookup (`OwnershipOutcome`)**:
The one "is this document ours?" read: `Gateway::lookup_ours(external_id, order, kind)` queries one of the order's *External ids* and validates the newest holder with `FoundDocument::is_ours` (the order number and the `tipus` of the kind), answering `Absent` (code 7), `Live` or `Reversed` (a document of ours), `Collision` (another order's or kind's document: never trusted and never read as "absent", since a document of ours may hide behind it), or the two answered codes (`CredentialsRejected`, `Api`). What every step that decides on an external id of the order without issuing journals: the exclusivity checks (`exclusivity-{kind}`), `prepayment-for-final`, `proforma-link`, `get-{kind}` and `proforma-for-delete`; the *Lookup step* and the *Create step* ask the same question of the same query inside their own outcomes, through the same internal (`Gateway::seen`), so the validation and its collision `warn` are written once, on the gateway side of the seam. The handlers decide on it as data: a live document refuses or links, a reversed one and nothing proceed (`get` reports both, `delete_proforma` treats a reversed proforma as absent), a collision refuses (`get` leaves the slot empty), an answered code is `unavailable` or `credentials_rejected`. A *Journaled type* since #181, replacing `QueryOutcome` on these reads, which recorded less than the handler decided. Type: `restate_szamlazz::gateway::OwnershipOutcome`.
_Avoid_: `support::Lookup` / `Lookup::classify` (the pre-#181 service-side classification; gone), `OwnedLookup` (reads as Rust's owned-vs-borrowed), external-id query (the selector, not the question)

**Create step**:
The second durable step of issuing (`create-{kind}`): one `ctx.run` under the issue policy whose every execution is query-first *inside the closure*: the external-id query first, the send only when the external id holds **nothing**, or **exactly the document the lookup step saw reversed**, still reversed. A live document that is not the reversed one the lookup saw was issued by an earlier execution and is answered as `issued` without sending; a reversed document that is not the one the lookup saw was issued by an earlier execution and reversed since, and is answered as `reversed` without sending (a reversal the caller has not acknowledged: *Reissue* is always explicit); the lookup's reversed document reported live is a server inconsistency answered as `conflict{live}` without sending. An *answer* to the leading query that is neither 7 nor a credential code (another szamlazz.hu code (`CreateOutcome::Api`) or `szlahu_down` (`CreateOutcome::Unavailable`)) is settled data with nothing sent, answered as the `unavailable` fault at once, exactly as the *Lookup step* answers the same code: never *Unconfirmed*, which would spend the issue policy (sized for the post-send window) on a read and end `outcome_unknown` after ~39 minutes holding the order key although nothing was sent (#63); only a transport failure of the leading query is `Unconfirmed::Transport`. A lost reply is re-queried once, immediately; nothing found makes the step **unconfirmed**, and Restate re-executes it after the policy's delay. The query lives inside the closure because a separate journaled pre-query would replay its stale "nothing" on the retry. Gateway fn: `Gateway::create` → `Result<CreateOutcome, Unconfirmed>`. The storno step (`Gateway::storno`, `StornoOutcome::Api` / `Unavailable`) follows the same rule.
_Avoid_: attempt, issue step (the whole two-step sequence is "issuing"), send (one part of the step), unconfirmed for an answered leading query (an answer is data; nothing was sent)

**Unconfirmed**:
The one error of the create and storno steps: szamlazz.hu's answer to the *send* is not known: a transport failure (`Transport`), `szlahu_down` (`Unavailable`), an open code (`Open`: 1, 55, 56 without a number, a code the agent crate does not know; `code: None` is the one open answer without a code, a success without a document number, and displays as such, never as `szlahu_down`), after the immediate re-query found nothing; or the re-query itself failed (`ReQueryFailed{sent, re_query}`), whose display names both how the send ended and how the re-query failed, so the re-query's failure never hides that a send happened. Retryable to the SDK, so the issue policy re-executes the step; its exhaustion is the `outcome_unknown` fault, whose message repeats the last display. Every *known* answer, including rejections, duplicates, the duplicate-order-number contradiction (71/152 with nothing under the order, a refusal, settled after one send) and an answer to the *leading* query (another code, `szlahu_down`, nothing was sent; #63), is `Ok` data. The only `Unconfirmed` before a send is `Transport` on the leading query, an exchange without an answer. Which codes are open is the agent crate's *Outcome class*, not the worker's own table.
_Avoid_: unknown outcome (the fault is `outcome_unknown`; this is what precedes it), transport error (one cause of it), `Contradiction` as a variant (the pre-#41 retryable one; a 71/152 with nothing under the order is settled data now), rejected for a code the crate does not know (it may be a new "issued, but…" code; #13), an answered leading query as `Unconfirmed::Transport` (the pre-#63 fold; it is `CreateOutcome::Api` / `Unavailable` now), `szlahu_down` as an "open code" (it is `Unavailable`)

**Outcome class**:
The Számla Agent crate's answer to "may a document exist despite this error?": `szamlazz_agent::OutcomeClass`, from `ErrorCode::outcome_class()`, `ResponseError::outcome_class()` and `ClientError::outcome_class()`: `Rejected` (szamlazz.hu refused before acting; the credential codes 3/135/136/164 included), `Unknown` (1, 55, 56 without a number, every code the crate does not know, `szlahu_down`, a transport or parse failure; query by external id before re-sending), `DuplicateOrderNumber` (71/152), `NotFound` (7). Distinct from `is_retryable()`, which says whether the same *query* can succeed later (1, 55) and is never permission to re-send a create. The worker's create and storno steps take their API-code arms from it and add `CredentialsRejected` on top, read off `ErrorCode::is_credential_error()` (3/135/136/164, a subset of `Rejected`; the agent crate's method since #128, so every consumer gets the same answer); `#[non_exhaustive]`, and a class the worker does not know is treated as `Unknown`. Decision: #13.
_Avoid_: retryable (a different question), error class (it classifies the outcome, not the error), severity

**Issue policy**:
The run retry policy of the create and storno steps: `[issue]` in the deployment configuration (`max_attempts` executions, `initial_delay` growing by `factor` to `max_delay`, bounded by `max_duration`) mapped field for field onto `RunRetryPolicy::new()`. Deployment-level (on `WorkerConfig`), shapes no journal entry. Set explicitly because the SDK's default run policy sends no retry delay and the server would spend the handler's `invocation_retry_policy` instead. `max_duration` is the hard bound; the attempt count is not durable across every replay (ADR 0004). `initial_delay` has a floor, `IssueConfig::MIN_INITIAL_DELAY`, the Számla Agent client's exported `REQUEST_TIMEOUT` (60 s) plus `RE_CHECK_MARGIN` (30 s), 90 s, that `WorkerConfig::validate` refuses to go under (`WorkerConfigError::IssueDelayBelowFloor`, naming the rule): a write step re-executed sooner would query for the cut execution's send while it may still be in flight, since szamlazz.hu has been seen to stall for a minute and still issue. The same rule sizes every write handler's `initial_interval` (2 m, pinned by the discovery test). The floor is on this policy only, and bites where a deployment validates its configuration; the e2e suite's 1 s policies never pass through `validate` (ADR 0004, #61 amendment). One of the three policies of the deployment, beside the *Read policy* and the *Resolve policy*. Type: `restate_szamlazz::config::IssueConfig`.
_Avoid_: attempt budget, backoff (the loop is gone), retry policy without qualification (the handlers have their own), a second copy of "60 s" (derive from `szamlazz_agent::client::REQUEST_TIMEOUT`)

**Read policy**:
The run retry policy of every read-only durable step of both services (the *Lookup step*, the exclusivity, proforma-link and `get` lookups, the verifies, the order-number hint, the storno lookup, `Szamlazz.Agent.query`, the *Taxpayer lookup*'s one step and the *check_account* probe): `[read]` in the deployment configuration, the same five fields as the *Issue policy* (`max_attempts`, `initial_delay`, `factor`, `max_delay`, `max_duration`; defaults `5`, `5s → 60s`, `5m`) mapped field for field onto `RunRetryPolicy::new()`. A read szamlazz.hu did not answer is the step's *Unanswered* error, re-executed under it; every szamlazz.hu *answer* (a document, code 7, a credential code, another API code) is data and never retried. Its exhaustion (or a cancel mid-read) is the `unavailable` fault, naming the step and the last failure, about the document when the step knows one. Safe because a read writes nothing and a re-executed closure's answer is exactly as fresh as a first one; sized for szamlazz.hu: five executions 5 → 10 → 20 → 40 s apart ride out a blip of about a minute, and a stalling szamlazz.hu (observed for a minute at a time) is waited out up to the 5 m bound, because this policy, not the handlers' invocation retry policy, is what decides how long a szamlazz.hu outage is tolerated: a run retry is re-dispatched by the server without spending an invocation attempt (#87), and a read that gives up is a terminal `unavailable` stored under the caller's *Idempotency-Key*. Deployment-level (on `WorkerConfig`), shapes no journal entry; set explicitly for the same reason as the issue policy. The one read that does not fault on exhaustion is the **best-effort** read after a verify found the document already reversed (the storno-number hint of `Szamlazz.Order.storno_invoice`, the by-number storno lookup of `Szamlazz.Agent.storno`) whose handler already knows its answer (`reversed`) and only lacks the storno number: exhaustion is `None` after a `warn` naming the step; a **cancellation** (the SDK's 409) is never swallowed and propagates, so a cancelled invocation does not complete as `reversed` (J13, #65; `support::best_effort`). Decision: ADR 0004 (#37 amendment; defaults widened in the #87 amendment). Type: `restate_szamlazz::config::ReadConfig`.
_Avoid_: query policy, lookup policy (one read among several), retry policy without qualification, transport retry (the failure is anything unanswered, `szlahu_down` included)

**Unanswered**:
The one error of every read fn of the *Gateway* (`lookup`, `lookup_ours`, `verify`, `query`, `hint`, `lookup_storno`, `query_taxpayer`, `probe`): szamlazz.hu produced no answer: a transport or parse failure (`Transport`) or `szlahu_down` (`Unavailable`). The read-side twin of *Unconfirmed*: retryable to the SDK, so the *Read policy* re-executes the step; its exhaustion is the `unavailable` fault. Never a journaled outcome: the `Transport` variants of `LookupOutcome`, `QueryOutcome`, `StornoLookupOutcome` and `ProbeOutcome` are gone, and `TaxpayerOutcome` and `OwnershipOutcome` never had one; another szamlazz.hu code on a read is the data variant `Api{code, message}`, which the handlers that cannot conclude from it answer as `unavailable` without a retry (`Szamlazz.Agent.query` passes it through as `szamlazz_error`, 422; the probe accepts it). Type: `restate_szamlazz::gateway::Unanswered`.
_Avoid_: transport error (one cause of it), unavailable (the fault it becomes on exhaustion), Unconfirmed (the write steps' error; a write's outcome may be unknown, a read's is simply not yet had)

**szamlazz.hu answer (`SzamlazzAnswer`) / Rejection code**:
What szamlazz.hu answers with when it answers a code rather than a document, as one type wherever a *Gateway* outcome carries it: `restate_szamlazz::gateway::SzamlazzAnswer { code, message }` in every `CredentialsRejected` and `Api` variant and flattened into `CreateOutcome::DuplicateOrderNumber` (`code`, `message` beside `existing_number`); `From<ApiError>`; `Display` as `{code}: {message}`. The `Fault` constructors that name szamlazz.hu's answer (`szamlazz_error`, `inconclusive_answer`, `credentials_rejected`) take one. A write's `Rejected` variant (`CreateOutcome`, `StornoOutcome`, `DeleteOutcome`, `SetPaymentsOutcome`) carries a `Rejection { code: RejectionCode, message }`, whose `RejectionCode::{Szamlazz(String), Request}` tells szamlazz.hu's refusal from the wire contract's before anything was sent (a sixth credit entry, a replacing `set_payments` with no entries, a document without line items); `Request` serialises as the pseudo-code string `request` (`RejectionCode::REQUEST`) and a szamlazz.hu code as itself, so the journaled shape is the one string field it always was, and `set_payments` matches on the enum rather than comparing a string (J-05-04, #128). Both are *Journaled types*' parts, `#[non_exhaustive]`.
_Avoid_: `REQUEST_CODE` (the pre-#128 constant; `RejectionCode::Request` / `RejectionCode::REQUEST`), `code`/`message` as two loose fields on a new variant, "error" for an answer (an answer is data the read journals)

**Consumed proforma**:
A proforma that szamlazz.hu removed from its query surface because an invoice or prepayment converted it, explicitly by reference or implicitly by shared order number. Derived live in `get`: the proforma is absent under its external id while the invoice or prepayment carries `hivdijbekszam`, reported as `{state: consumed, by}`. Distinct from a deleted proforma, which is simply absent and may be recreated.
_Avoid_: converted (the invoice is converted from it; the proforma is consumed), deleted

**Gateway (`gateway` module) / `Szamlazz.Agent` service**:
The module that speaks to szamlazz.hu on behalf of one account: `restate_szamlazz::gateway::Gateway` owns the `szamlazz_agent::Client` and the account it is opened for, and exposes one plain async fn per durable step (`lookup`, `lookup_ours`, `create`, `verify`, `query`, `hint`, `lookup_storno`, `storno`, `delete_proforma`, `set_payments`, `query_taxpayer`, `probe`) with outcome-as-data; every expected szamlazz.hu outcome is a value, never an `Err`; the two `Err`s say what a run retry policy may re-execute: `Err(Unanswered)` of the read fns for a read szamlazz.hu did not answer, `Err(Unconfirmed)` of the create and storno steps for an answer that is not known. Not a second client: the Számla Agent `Client` is the transport it wraps. Every read of account configuration by the Restate services (document defaults, seller block) goes through `Gateway::account()`; the services themselves hold no gateway, only the *Accounts* bundle and the deployment-level `WorkerConfig` (namespace, issue, read and resolve policies), and the *Prologue* opens one (`Gateway::open`) per handler execution, over a fresh client, from the resolved *Account* and freshly fetched credentials. `Gateway::open_with_http` opens one over a caller-built `reqwest::Client` (re-exported as `szamlazz_agent::reqwest`, since the agent crate's `ClientBuilder::http_client` is the same hook one level down): the embedder's hook for a proxy or a custom TLS setup, and what the unit tests and the wiremock harness open their gateways with, over the default client's settings minus the root certificates, so that no test under `cargo test --workspace` parses the system CA store (about 28 ms of CPU per client through reqwest's platform verifier, and a failure on a host without a store) for a plain-`http://` mock (#136); the e2e deployment's gateways, under `--ignored`, are the prologue's `Gateway::open`, so the fresh-jar boundary of the production path is exercised there and nowhere in the un-ignored suite (the session-isolation test of `tests/gateway.rs` proves the harness's client fresh per open, not `Gateway::open`'s). The fresh-client-per-open boundary is then the caller's to keep, because two gateways over one client share its cookie jar. `Szamlazz.Order` calls the gateway inside `ctx.run`. The `Szamlazz.Agent` Restate service is a thin stateless facade over the same module for by-number operations (query, credit entries, storno of unmanaged documents), the *Taxpayer lookup* by tax number (the one handler that is about no document, there because it is a per-account read and the worker is the one place that holds the account's key), and the *check_account* probe. Unkeyed, so its invocations run concurrently and two by-number writes on one invoice (`set_payments`, `storno`) are not serialised by the worker as an *Order*'s handlers are by its per-key lock: two replacing `set_payments` race and the last send to land wins (under reordered webhook deliveries, the older snapshot), while two stornos both send and the repeat is answered with the existing storno number by szamlazz.hu's idempotent storno (verified for a sequential repeat; two sends in the same instant are unverified); a keyed `Szamlazz.Document` object was judged over-engineering (J4, #115), and the caller serialises per invoice on its side or sends `additive: true` and lets szamlazz.hu sum. Neither Restate service calls the other. First named `steps` (ADR 0001).
_Avoid_: steps (for the module, the pre-rename name), client (for the module; it is not a second client), session (for the module; the szamlazz.hu cookie is what its fresh client isolates), "the agent" without qualification, Invoice service, Document service / `Szamlazz.Document` (considered and not built)

**Malformed body**:
A request body the contract refuses: a field no request type knows (every request type and every object it nests is closed; `#[serde(deny_unknown_fields)]`, `additionalProperties: false` in the discovery schema, so `{"options": {"resissue": true}}` is refused, never read as `reissue: false`), a wrong type, a missing required field, or invalid JSON. Answered as the `invalid_input` fault (400) with serde's message, naming the field when there is one (`malformed request body: unknown field \`resissue\`, expected \`reissue\` or \`proforma\` …`), the same `{code, message}` shape as every fault, never the SDK's plain-text `Cannot decode input payload`, because every handler takes its input as `service::Body<T>`, whose SDK `Deserialize` never fails (it keeps the verdict) and whose discovery metadata is exactly `Json<T>`'s; the handler's first act, before the *Prologue*, is to turn the kept error into the fault, so nothing is journaled and nothing is sent. A bounded contract type refused by its own `Deserialize` (an *Invoice number* over 40 bytes, a `correction_id` equal to an external-id token) is a malformed body too: serde's message carries the type's rule (`invoice number is 41 bytes long, at most 40 are allowed`). Not to be confused with a well-formed body carrying a value the handler refuses before the *Prologue* (the *Taxpayer lookup*'s tax number in neither accepted form, an untrimmed *Order* key or one outside its alphabet), which is the same fault at the same point (nothing journaled, nothing sent) by the handler's own check, not serde's. Response types stay open: a client must tolerate fields added later.
_Avoid_: invalid payload (the SDK's word), decode error (one cause), unknown field (one cause), bad request (the HTTP class)

**Prologue**:
The four steps every handler of both Restate services runs after decoding its body (a *Malformed body* is refused here, before anything is journaled) and parsing its key, and before its operation: **pin** the namespace in a pure durable step (`namespace`); **resolve** the request's scope to its *Account* in a durable step named `account` under the *Resolve policy* (unscoped and unknown journaled as data and answered as `unknown_account`, an unavailable resolver retried, its exhaustion `unavailable`); **fetch** the account's credentials outside the journal on every execution with a short in-process retry, then terminal `unavailable`; **open** the *Gateway* over a fresh client. Every call it makes into the *Account resolver* or the *Credential store* (each `resolve`, each `fetch` attempt) runs under a ten-second deadline (`prologue::CALL_DEADLINE`, a worker constant; a resolver that has not answered by then is not going to) and is dropped at it, the timeout being the existing retryable answer (the `account` step's error, so the *Resolve policy* re-executes it; one fetch attempt's failure, so the in-process retry runs) and never the handler's inactivity timeout: the *Resolve policy* bounds re-executions, not one hung call (#114). Its decisions are functions of their inputs whose only effect is a log line, and the two bounded calls are the one place it awaits an embedder (`service::prologue`; the pre-#88 `warn` on a scoped request resolving to an unpinned account went with the pins: ADR 0006, account-pin amendment); its durable behaviour is observable only under Restate. One module, `service::prologue`, holds both the decisions and the durable steps (`prologue::execute` runs a handler execution: `run_prologue`, then the body), generic over `support::RunCtx` (the one trait the run helpers need of a Restate context: scope, key, invocation id, a journaled run; implemented for the SDK's three context types).
_Avoid_: preamble, setup, middleware (there is no interception layer; it is the first lines of every handler), init

**check_account (`Szamlazz.Agent.check_account`)**:
The read-only probe for onboarding and deploy pipelines, and the deploy-time canary for the experimental Restate flags: the *Prologue* like every handler, then one durable step (`probe`) under the *Read policy* (a query of the sentinel external id `{namespace}:check-account`, which nothing the service issues carries, expecting "not found"), answering the *Scope* the SDK saw, the *configured* account (`id`), the *Namespace* and whether szamlazz.hu accepted the credentials: `{state: ok}`, or `{state: rejected, code, message}` on 3/135/136/164 **as data, not a fault**. `scope: null` under a scoped call means the server did not forward the scope (`protocol_v7` off; the ingress does not refuse a scoped path for it); the probe is the only defence against that case, since the worker has no per-request signal of "was this call scoped?" it is willing to depend on (an ingress-path guard on the undocumented, caller-overridable `x-restate-ingress-path` header was considered and dropped). Credential acceptance is its only szamlazz.hu-verified fact; *which* account the key opens, and whether it is a test account, no operation answers and the worker checks nowhere, so the go-live check follows the probe with a `query` of a document known to be the account's and a reading of its `test` and *Seller block*. Issues nothing; no input; explicit `journal_retention` so the leak assertion can scan it. Called under each configured scope after a deploy, it proves the scope reaches the worker, resolves to the configured account and its key works; it cannot detect fan-in: it only echoes configuration. An exchange that produced no answer is *Unanswered*, retried; exhaustion is `unavailable`. Gateway fn: `Gateway::probe` → `Result<ProbeOutcome, Unanswered>`; response type `contract::CheckAccountResponse`.
_Avoid_: health check (it checks one account under one scope, not the process), login test, ping

**Taxpayer lookup (`Szamlazz.Agent.query_taxpayer`)**:
The NAV taxpayer query (`xmltaxpayer`) on the *Account* the request's *Scope* resolves to: the *Prologue* like every handler, then one durable step (`taxpayer-{prefix}`) under the *Read policy*, answering NAV's record of the taxpayer (`valid`, `name`, `tax_number`, `vat_code`, `addresses[]`) **as data**: `valid: false` (NAV knows no taxpayer under the prefix) is a normal 200, never `not_found`. In the worker because it is a per-account read that needs the account's agent key, and the worker is the one place a multi-account deployment holds one (ADR 0006); the one `Szamlazz.Agent` handler that is about no document. The request is `{tax_number}` in exactly two forms: the bare eight-digit stem (`12345678`) or the full `NNNNNNNN-N-NN` (`12345678-2-42`); the handler derives the **prefix** (törzsszám, `TaxpayerPrefix`) and anything else is `invalid_input` before the *Prologue*, like a *Malformed body*. The step is named by the prefix, not the number as sent, so the stem and the full number are one entry. Every `funcCode ≠ OK` (szamlazz.hu's own code or NAV's relayed `errorCode`) is an *answer*, passed through as `szamlazz_error` (422, the code in `szamlazz_code`) and never retried (a NAV outage is a terminal 422 the caller retries with a new `Idempotency-Key`); a credential code is `credentials_rejected`; an exchange with no answer is *Unanswered*, `unavailable` on exhaustion. Finds no document. Journals the crate-owned projection `TaxpayerOutcome::Found(QueryTaxpayerResponse)`, never the agent crate's `TaxpayerInfo`. Not cached by the worker (ADR 0005); the caller caches, with a TTL on the order of a day. Gateway fn: `Gateway::query_taxpayer` → `Result<TaxpayerOutcome, Unanswered>`; contract: `QueryTaxpayerRequest` / `QueryTaxpayerResponse` (`TaxpayerAddress`). Decision: #49.
_Avoid_: tax number validation (it is NAV's answer, not a format check; the format check is the `invalid_input` refusal), VIES / EU VAT lookup (a different register), taxpayer status (`adóalany`, the buyer field on a document), taxpayer query as a non-goal (the pre-#49 README line)

**Execution**:
What one handler execution runs on: the *Gateway* the *Prologue* opened and the `WorkerConfig` with the pinned namespace. Built by the prologue, dropped with the execution: no gateway, client or credentials outlive it; "handler execution" is the unit, since a run-policy retry re-executes the whole handler with replay. Type: `service::prologue::Execution` (the handler bodies are its methods). Every execution runs inside one tracing span, **`execution{scope, order, restate.invocation.id, account.id}`**, opened before the prologue's first step and left after the handler's answer (`prologue::execute`; the span is `prologue::execution_span`): `scope` is what the SDK saw (`<unscoped>` when none, as the start-up log prints it), `order` the Virtual Object key (absent on `Szamlazz.Agent`), `restate.invocation.id` the value the ingress returns as `x-restate-id`, and `account.id` the resolved *Account*'s id, recorded once the `account` step has answered (`prologue::record_account`). So every log line the execution emits (the prologue's own warnings, the *Gateway* steps' `gateway.*` spans and events, the paging `credentials_rejected` warning, whose own fields stay `namespace` and `code`) is attributable to a scope, an account and an invocation from the worker's log alone (#65). Never the key: the account id is journaled and shown in the Restate UI already.
_Avoid_: attempt (for the handler; the SDK's word for a run retry is also "attempt", and neither is journaled), session (the szamlazz.hu cookie), context (the SDK's `ctx`), handler span or prologue span (the span is the execution's; it outlives the prologue), the account id in a response (the span and the log carry it; no response does)

**Resolve policy**:
The run retry policy of the *Prologue*'s `account` step: `initial_delay` growing by `factor` to `max_delay`, bounded by `max_duration`, no attempt cap by default (`max_attempts` may be written, like on every table). Deployment-level (on `WorkerConfig`), shapes no journal entry, set explicitly for the same reason as the *Issue policy*. Defaults `1s → 10s`, `1m`; configured as `[resolve]` in the deployment configuration, beside `[issue]` and `[read]`. Type: `restate_szamlazz::config::ResolveConfig`, an instantiation of the one *Retry policy config*.
_Avoid_: retry policy without qualification, account policy

**Retry policy config**:
The one struct behind the three run retry policies of the deployment, `restate_szamlazz::config::RetryPolicyConfig<T: Table>`: `max_attempts` (optional; the duration is the sole bound when unset), `initial_delay`, `factor`, `max_delay`, `max_duration`, closed to unknown keys, mapped field for field onto `RunRetryPolicy::new()` (an unset cap sets none). The type parameter is the table (`config::table::{Issue, Read, Resolve}`, sealed), which names the policy in a `WorkerConfigError` and carries its defaults, so `IssueConfig`, `ReadConfig` and `ResolveConfig` are three aliases of one struct with three sets of defaults (J-05-03, #128); the fields the three tables take are identical, `max_attempts` included (`[resolve]` leaves it unset by default rather than lacking it). Every table is held to the same invariants by `WorkerConfig::validate` (a cap of zero, delay order, factor), the issue floor on `[issue]` alone.
_Avoid_: three policy structs (the pre-#128 shape), a `[resolve]` without `max_attempts` (it has the key; the default is unset), policy without qualification

**Validated worker config**:
`restate_szamlazz::config::ValidatedWorkerConfig`, the newtype `WorkerConfig::validate` yields (the one constructor a deployment has) and what `Order::from_parts` / `Agent::from_parts` take, so a service cannot be built over an issue policy below its floor; dereferences to the `WorkerConfig`. `ValidatedWorkerConfig::unchecked` wraps without checking, behind the `test-util` cargo feature the e2e harness enables for its one-second policies (sized for a scripted mock) and a deployment never does (#128). A deployment validates where it loads its configuration; the e2e's `worker_config()` is the only `unchecked` caller.
_Avoid_: `worker.validate()?;` as a statement whose result is dropped (the pre-#128 wiring; `validate` consumes and returns), a bypass constructor without the feature

**Journaled type**:
A type the services write as the result of a `ctx.run`: the *Namespace* the prologue journals, the `account` step's resolution (carrying the *Account*), and the *Gateway*'s outcomes (`LookupOutcome`, `CreateOutcome`, `QueryOutcome`, `OwnershipOutcome`, `StornoLookupOutcome`, `StornoOutcome`, `DeleteOutcome`, `SetPaymentsOutcome`, `ProbeOutcome`, `TaxpayerOutcome`). Every journaled type is **crate-owned**; a `szamlazz_agent` response type is never journaled directly: the document outcomes carry the *Found document* and *Issued document* projections, `TaxpayerOutcome` the crate-owned `QueryTaxpayerResponse`, so what the worker never reads of a document (the buyer block, the seller block, the line items, the PDF) is not in an entry the Restate UI shows for the retention period, and the agent key never is. **No compatibility contract**: a release is a new Restate deployment and an in-flight invocation replays only on the deployment that wrote its journal (ADR 0009), so a journaled type may be reshaped between releases; there is no additive-only rule, no fixture, no archive. `service::journal` checks what an entry holds on a sample of every variant: it round-trips through serde, carries no sentinel agent key, and carries no `supplier`, `buyer`, `items`, `financial_items`, `labels` or `pdf` key at any depth; **complete by mechanism**, because it is a privacy invariant and not a convention: the sealed `Journaled` marker (implemented through the one `journaled!` list in `support`) is the run helpers' bound, so only a listed type can be a `ctx.run` result, the scan's registry is held to that list, and each enum's samples are held to its exhaustive `variants!` list, so a type or variant journaled without a sample fails by name. Decision: ADR 0009 (superseding ADR 0005's #47, #125 and #127 amendments).
_Avoid_: run result (the SDK's word; the type is what matters), additive-only / fixture / pin / archive rule (the pre-ADR-0009 contract; gone), `Journaled` as a compatibility marker (it marks what the scan covers, nothing about replay), schema version (there is none), snapshot, state (the *Order* keeps none; the journal is Restate's, not the service's), an agent response type "as it is" in an outcome, `InvoiceDocumentExt` (gone; the checks are `FoundDocument`'s methods)

**Found document / Issued document**:
The worker's projections of a szamlazz.hu document, the types the document outcomes journal (`restate_szamlazz::gateway::document`, #127). A **found document** (`FoundDocument`, `From<InvoiceDocument>`) is what the handlers read off a queried `<szamla>` and nothing else: `document_id` (`alap/id`), `number`, `document_type` (`tipus`), `order_number` (`rendelesszam` trimmed, an empty or whitespace-only element read as `None`: the one reading of the element, made once, in the projection; what `carries_order` compares with the *Order* key and what `Szamlazz.Agent.storno` answers as `managed_by_order`'s `order_key`), `reversed` (`sztornozott`), `referenced_invoice_number` (`hivszamlaszam`), `referenced_proforma_number` (`hivdijbekszam`), `appearance` (the `eszamla` integer code; `e_invoice()` reads it through the agent crate's `InvoiceAppearance`, so a code the crate learns later is read on replay), `issue_date` (`kelt`), `fulfillment_date` (`telj`), `due_date` (`fizh`), `currency`, `test` (`teszt`, carried, compared with nothing), the grand total (`net_total`, `vat_total`, `gross_total`) and `payments` (`RecordedCreditEntry`: date, title, amount, comment, bank account); `document_id` is read by no handler and carried for correlation with szamlazz.hu's records. Not the *External id*: szamlazz.hu never echoes `szamlaKulsoAzon`, and the handler holds it from the key. The checks the services make before trusting or acting on a document are its methods: `is_live`, `is_ours(order, kind)`, `carries_order`, `is_storno_of`, `e_invoice`, `payment_amounts`. `Szamlazz.Agent.query`'s `QueryResponse` is projected from it. An **issued document** (`IssuedDocument`) is what they read off a create reply (`TryFrom<InvoiceCreationResult>`: a reply without a number is `Unnumbered`, not an issued document, and the *Create step* re-queries) or a storno reply (`From<CreatedInvoice>`): `number`, `document_id`, `net_total`, `gross_total`, `outstanding`, `customer_account_url`, `notification_delivery_failed`; never the PDF. Both are made at the *Gateway*'s wire boundary (`query_raw`, the create and storno sends); nothing past it holds an agent response type. `#[non_exhaustive]`, constructed in tests through the wire (`test_support::Doc` (defined in `tests/common/mod.rs`, included by path) renders the `<szamla>` XML, parses it through the agent crate and projects it), never as literals.
_Avoid_: `InvoiceDocument` for what a handler holds (the agent's type; the gateway projects it at the boundary), `InvoiceDocumentExt` (the pre-#127 trait), a document "as it is" / "whole" in the journal, the raw `rendelesszam` (the projection carries the reading), `eszamla` as a flag on the projection (it is the code; `e_invoice()` is the flag)

**Step-name table**:
`RUN_NAMES` in the e2e harness (`tests/e2e/harness/run_names.rs`) lists, per handler of both Restate services, the ordered `ctx.run` names of every **path** the handler journals: `namespace`, `account`, then its steps; a handler with two shapes (`create_invoice` and `create_prepayment` with `proforma-link` or `verify-proforma-{number}`, `storno_invoice` ending in the storno or in `hint-storno-{number}`) has two rows. A `{number}` / `{prefix}` segment is a parameter, read by its prefix (the most specific pattern first: `verify-storno-…` is never `verify-{number}`). The check holds when, over every invocation the server still holds at the end of the run, the run sequence is a **prefix** of one of its handler's paths (a handler that answers early (`unknown_account`, a conflict, a refusal before the prologue) journals the first steps only), every handler seen is in the table, and every path was **walked in full** by at least one invocation (so a step dropped from a path's end is caught too, and the table cannot go stale). The walk requirement is what sizes the e2e (#134): the suite is one scenario per path (the sequence test) plus the durable-execution scenarios, and a scenario that is the only walker of a path stays however plain its decision (the decision is a unit test; the scenario proves the steps run in that order under Restate). Verified from `sys_journal`, so it needs a server: it is the last scenario of the e2e (`tests/e2e/invariants.rs`), not a unit test. The matching is the *Restate e2e harness* crate's (`restate_e2e_harness::run_names`: `RunPath`, `RunPatterns::pattern` reading a journaled name as its pattern by the longest prefix, `is_prefix_of_path`), unit-tested there over a table of its own; the szamlazz harness's `run_names.rs` holds `RUN_NAMES` and a `run_pattern(name)` over the patterns derived from it, so the table and its matcher cannot disagree. Why it is kept under immutable deployments (ADR 0009): Restate's *pause and resume on a new deployment* moves a stuck invocation onto fixed code and requires of the new code the same `ctx.run` sequence, result types that still decode and unchanged step inputs; the table is the **sequence half**, the only one with a mechanism (the other two are a review of the release's diff, and a release that reshaped a *Journaled type* refuses the resume). Decision: #66, ADR 0009.
_Avoid_: run-name pin (the pre-ADR-0009 name; "pin" is retired from the journal vocabulary), the matcher as szamlazz code (it is the crate's; the table is the consumer's), step names as a fixture file (it is a table in the harness, verified against a live journal), journal snapshot, a per-step assertion in a scenario as "the check" (scenarios assert their own steps; the table covers every invocation of every handler), a journal compatibility contract (there is none; the table serves the resume path), the table's diff as "replay compatibility" (it is the sequence third of it)

**Restate e2e harness (`restate-e2e-harness`)**:
The workspace crate (`crates/restate-e2e-harness`, published on crates.io, versioned on its own from 0.1.0, unix only and gated so a non-unix build fails with a message) that is the Restate half of an end-to-end suite for any `restate_sdk` endpoint: the *Server gate* and the launcher (`Launcher::launch(&ServerSpec)`, the spawned `Restate` handle), an endpoint served in-process and registered (`Restate::deploy(Endpoint) -> Deployment`, repeatable, so a redeploy is two calls), `set_public` and `drain`, the ingress (`Restate::invoke` → `Reply`, whose `fault::<F>()` asserts Restate's error envelope and decodes the JSON string in `message` into the caller's type), the admin API (`Admin`: SQL, `journal` / `runs` / `invocation` / `all_journals` / `all_invocations`, kill / cancel / purge, `await_status`, the in-flight invocations on a key, the `Watch` sampler with its pure `Sampler`), the introspection rows (`JournalEntry` with `raw` hex-decoded, `Invocation`, `run_result`), the *Step-name table*'s matcher and `plain_http()` (the no-root-store `reqwest` builder for loopback traffic, #136). **The one hard rule**: it depends on `restate-sdk`, `reqwest`, `serde` / `serde_json`, `tokio` and `nix` (no `tracing`: it prints a few `eprintln!` lines about the server it spawned and otherwise panics), and never on `restate-szamlazz`; `restate-szamlazz` takes it as a path dev-dependency (stripped on publish). A dependency back would be a dev-dependency cycle Cargo resolves by compiling `restate-szamlazz` twice, so every `Order`, `Agent` or `Fault` crossing the boundary would be two types; the seam is therefore forced: the crate exports building blocks and knows no szamlazz type, and what is szamlazz's stays in `restate-szamlazz/tests/e2e/harness/`: the `Harness` composing `Restate`, the wiremock and the accounts (phase 1's static resolver; phase 2's mutable resolver and store, a resolution failed per scope, a fetch held per credential reference), the two `ServerSpec`s, the document-centric stub helpers over the szamlazz fixtures every test layer shares (`tests/common/mod.rs`: the `<szamla>` renderer, the response templates, the selector matchers; #134), `RUN_NAMES`, and a `Reply` newtype decoding the contract's `Fault`. Its own contract is one ignored `e2e_smoke` with a trivial service of its own (a named run, a JSON-bodied `TerminalError`, a hanging handler killed and purged), run by the Dagger `endToEnd` check beside the szamlazz e2e (`--ignored e2e_`); the szamlazz e2e is its integration test. A second Restate worker embedding `Order` and `Agent` is the crate's second consumer. Decision: #167.
_Avoid_: harness for the crate when the szamlazz `Harness` type is in scope (say the harness crate; the `Harness` is the consumer's type), a `Harness` type in the crate (the consumer composes), a testcontainers / docker feature (revisit only if `restate-sdk-testcontainers` gains server env vars and an admin URL), a dependency on `restate-szamlazz` from the crate, szamlazz stubs or `RUN_NAMES` in the crate

**Server gate**:
How an e2e suite gets its Restate server, decided once from the environment before anything starts (`server_gate` in the *Restate e2e harness* crate's `gate` module, a pure function under its own tests), in this order: `RESTATE_ADMIN_URL` / `RESTATE_INGRESS_URL` reuse a running server (the szamlazz main suite only, which expects the three experimental flags; the protocol-v7 canary needs a server of its own shape and never reuses; `compose.yaml` starts one); `RESTATE_SERVER_BIN` names a `restate-server` binary the harness **spawns** on the loopback, one process per suite, leading a process group of its own, configured through Restate's `RESTATE_*` environment, its log and data under a temp directory (`restate-e2e-{pid}-{name}-{admin port}`, unique per launch, so two launches of one spec in one test binary share nothing) kept when the test fails (what CI uses, since the Dagger container has no docker daemon and a Dagger service cannot reach back into the container that binds it; the Dagger check prints the kept log when the suite fails, since the container is discarded; a developer gets the same binary with `dagger call ci restate-server export --path ./restate-server`). `RESTATE_ENDPOINT_HOST` overrides the endpoint host in either mode. **No port is fixed** (#123): a spawned server's ports are chosen free at launch, a listener on port 0 per port (bound, read, released, passed through `RESTATE_*`), so two runs on one host collide with nothing; a port taken between the choice and the bind shows as the server failing to start, reported at once naming the ports rather than waited on. A `ServerSpec` names the shape (a name, one path component of `[a-z0-9-]` since the base dir is removed recursively on drop, checked before any spawn; `NAME=value` flags), and `/version` is checked at launch to report each of the three experimental features on iff its flag is in the spec. A server the harness started is stopped when the handle drops (the group killed) and by the harness's own SIGINT/SIGTERM handler, since a signal runs no `Drop`. With neither source the suite **skips** with a message on a developer machine and **fails** when `CI` is set: a run that passed by skipping proves nothing. The docker launcher (a container of the Restate image, named per run and labelled with the pid, stale ones removed by the next run) is gone (#167): CI never used it, and with it went the container naming, the label/pid scheme, the `docker port` read-back and the `docker info` probe. Decision: #66, #123, #167.
_Avoid_: docker-gated (the pre-#66 shape), a docker launcher as a third source (gone with #167), skip in CI, testcontainers (the harness drives `restate-server` itself), Drop-only cleanup and fixed host ports (18080/19070, the pre-#123 shape), a stale container found by name or label (there are no containers)
