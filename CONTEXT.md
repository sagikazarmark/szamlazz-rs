# szamlazz.hu Integration

Rust crates for integrating with szamlazz.hu, a Hungarian invoicing service: an outbound API client, two inbound receivers for szamlazz.hu-initiated pushes, and a Restate-backed durable worker that issues documents exactly once per order.

## Language

### Integration surfaces

**Számla Agent**:
The szamlazz.hu XML API for issuing and querying documents. Single HTTPS endpoint; the multipart form field name selects the operation. Crate: `szamlazz-agent`.
_Avoid_: "the API" (ambiguous; there are three surfaces)

**IPN**:
Instant payment notification. A form-urlencoded POST szamlazz.hu sends to a configured URL when an invoice's or proforma's paid amount changes. The amounts are an absolute current payment-status snapshot, not a new payment or delta, and the payload has no reliable document-kind discriminator. Unauthenticated; retried every 3 minutes up to 10 times. Crate: `szamlazz-ipn`.
_Avoid_: webhook (too generic), payment callback

**Reported IPN content**:
The optional amounts, payment date and payment method in an IPN, whose decoded, untrimmed raw fields preserve omitted, empty and unreadable values distinctly; malformed form encoding or missing/blank document identity is shape, while unreadable amounts and dates are content. Full-payment status is tri-state (`is_fully_paid() -> Option<bool>`), unknown when either amount is unknown, and even a reported true is only an unauthenticated query hint: verify on the receiver's configured account before financial action; [the IPN README](crates/szamlazz-ipn/README.md) defines parsing, raw fields and delivery ordering.
_Avoid_: unknown as zero, unknown as unpaid, full-payment comparison as payment evidence, IPN date as an ordering timestamp

**Adatkapcsolat**:
The Online Pénzügyi Adatkapcsolat (Financial Data Connection) product. szamlazz.hu pushes full XML documents (outgoing invoices, incoming invoices, bank transactions, receipts) to a single registered receiver URL, authenticated by the `X-Szamlazzhu-Key` header; the document type is identified by the XML root element. Crate: `szamlazz-adatkapcsolat`.
_Avoid_: data connection, push API, feed

**Ack**:
The response XML an Adatkapcsolat receiver returns for a pushed document: echoes the document id (invoices, optionally with a registration number / iktatószám) or carries a control code.
_Avoid_: response (overloaded)

**Control code (KEY_ERR / KEY_DEL)**:
Deliberate protocol speech in an Ack: KEY_ERR tells szamlazz.hu the key is wrong (stop sending until it changes); KEY_DEL severs the connection. Not errors: errors (non-200) mean "retry within 72 hours". In the crate `ControlCode::KeyUnknown` / `ControlCode::Disconnect` (`InvoiceAck::key_unknown()`, `Ack::key_unknown()`), and `ControlCode::to_xml(kind)` renders either as the Ack of a *Root kind*, the one Ack shape every kind shares, so a receiver that has identified a push can answer KEY_ERR without parsing (or authenticating) the body (#176). Decision on the name: #130 (a): the 0.3 `KeyError` / `key_error()` named a control code "error".
_Avoid_: `KeyError` / `key_error` (0.3), key error in prose (the key is *unknown*; an *error* is a non-200)

**Root kind**:
Which of the four streams a push carries, named by its XML root element: `szamlazz_adatkapcsolat::RootKind` (`OutgoingInvoice` `<szamla>`, `IncomingInvoice` `<szamlabe>`, `BankTransaction` `<banktranz>`, `Receipts` `<xmlnyugtaarchiv>`), the **one** enumeration of the kinds, read by `Document::identify(body)` from the root's start tag alone (UTF-8 checked over the whole body, nothing else read) and by `Document::kind()` off a parsed document, and what `ControlCode::to_xml`, the archiver's directory and the axum router's KEY_ERR Ack take; `InvoiceDirection` is its invoice half (`RootKind::direction() -> Option<InvoiceDirection>`, `From<InvoiceDirection> for RootKind`), kept because the invoice-only surfaces (`InvoiceAck::to_xml`, `InvoiceDocument::validate`) take exactly two values. `Document`, `RootKind` and `InvoiceDirection` are **exhaustive**: a fifth stream is a new `Handler` method, a breaking change by the trait's design (every method required, so a new stream cannot be acknowledged and discarded), and a `#[non_exhaustive]` on top bought nothing and cost every consumer a wildcard arm (the 0.3 README quick start did not compile downstream for it). The protocol's order without the router: identify, authenticate (`keys_match`), then parse. Decision: #176 (1, 2), superseding the 0.3 shape (`RootKind` crate-private, `archive::DocumentKind` a private copy, the per-kind KEY_ERR Ack written in the axum adapter, `InvoiceAck::for_document` behind the `axum` feature).
_Avoid_: document kind (the agent crate's `DocumentType` is the `tipus` code, a different thing), `DocumentKind` (the deleted archive copy), `Stream` as a type or variant name (prose may say stream, the wire's word; the type is the kind), a wildcard arm over `Document`

**Shape vs content (Adatkapcsolat parse)**:
The rule `Document::parse` refuses by. A push is at-most-N-times delivery (szamlazz.hu retries a non-200 identically for 72 hours and then drops the record, for a bank transaction or receipt for good), so a deterministic refusal loses data, and the parse refuses only a body that is not the pushed record: *shape*: not UTF-8 or XML, an unknown root or namespace, a record without its **identity** (an invoice's `alap/id` and `szamlaszam`, a bank transaction's `id`, a receipt's `alap/id`; missing or not an integer), a number or boolean not of its lexical type. The identity is shape because it is what a receiver keys the record by, **not** because every Ack echoes it (#176 (3), decided 2026-09-09): an invoice Ack echoes `alap/id` and nothing echoes `szamlaszam`, a bank transaction's or a receipt batch's Ack carries no id at all, yet redelivery is the protocol's normal case (a lost Ack, a failed fan-out member) and a receiver tolerates it by the id (the archiver names its objects by it); szamlazz.hu assigns the id itself and its schemas type it an integer, so a push without one is not a record it holds, the same class as a truncated body. The cost is stated: a receipt batch with one id-less `<nyugta>` is refused whole and dropped after 72 hours; the alternative (an `Option` id on the two kinds, an archiver fallback name that collides under `Overwrite`) was considered and not taken. Everything else is *content* and reads as the wire delivers it: an element the XSD requires but the push omits is `None`, an unknown `irany` is `TransactionDirection::Other`, a `<pdf>` that does not decode is `None` with the encoded text in `raw_xml()`, a date that is not a date (`<kelt>2015-12-01junk</kelt>`, `<kelt>é12345</kelt>`) is `None` with its text in `raw_xml()` (#122: the one lexical failure read as content; the crate already reads `xs:date` on its own terms, discarding the timezone suffix a civil date cannot hold, and the strip once split the text by a byte offset and panicked inside a multi-byte character, after the key check, leaving szamlazz.hu no answer; the `de` helpers never index or split wire text by a byte offset without a char-boundary check), an empty receipt batch has no receipts. The XSD's requirements are a **signal** (`Document::validate` (or the per-document `validate()`), answering a typed `ValidationError`: `MissingRequired { path }`, `UnknownToken { path, token }`, `Negative { path }`, `Empty { path, child }`, each displaying the 0.3 text verbatim, so a receiver acts on which element without parsing a message; #130 (c)) or an explicit **gate** (`Document::parse_strict`, `ParseError::Validation`), never the default; a date read as `None` for its text is reported by them, where the XSD requires the date, as the requirement it fails to meet (`missing required invoice alap/kelt`), the same as an omitted one (an optional date, `elszDatTol`, a buyer ledger `datum`, is `None` with no signal). The router's authenticated `400` is for shape only. Decision: #95 (review findings B-01, B-02, J-01), #122, #176 (3).
_Avoid_: strict parsing as the default, "invalid document" for a merely incomplete one in prose (`ParseError::Validation`'s display text `invalid document structure: …` is kept verbatim from 0.3; a `parse_strict` caller's messages did not change), required field (the XSD requires; the parse does not), "a value not of its lexical type" as shape without qualification (a date's is content since #122), a panic as a way to answer wire text (nothing on the parse path panics on content; a panic after the key check leaves szamlazz.hu no answer), "what the receiver cannot Ack" as the shape rule (the pre-#176 wording; the rule is identity), a string `ValidationError` (0.3)

**Connection (Adatkapcsolat)**:
One registered Adatkapcsolat connection: one szamlazz.hu account pushing to a receiver URL under one `X-Szamlazzhu-Key`, the party a presented key resolves to when several share a receiver. The protocol's own word (KEY_DEL "severs the connection"; the key is "the connection's identifier"). `axum::KeyResolver::resolve(key)` answers the connection's `Handler`, **owned** (`Option<Arc<Self::Handler>>`, #130 (1)), so a resolver may hand out a handler it holds (the fixed-key router's one `Arc::clone` per request) or build a connection context per request from what a database or secrets lookup found; `Ok(None)` is a key **definitely** unknown (the router answers KEY_ERR, and a bank transaction or receipt so answered is never resent), `Err(_)` a lookup that could not complete (`503`, the record stays retryable), never confused. A key that is a secret is compared with `szamlazz_adatkapcsolat::keys_match` (constant time via `subtle`, exported, what the fixed-key router uses; #130 (3)). `Handler::Error` and `KeyResolver::Error` are `std::error::Error` (`Fanout` keeps each member's error whole in `HandlerFailure::error: BoxError`, `source()` chain included; #130 (b)); the router never echoes either, and logs them at `warn` only under the `tracing` feature, so a deployment without it logs its own (#130 (2)).
_Avoid_: tenant, customer, multi-customer / multi-tenant router (the 0.3 words; "multi-connection"), account (the worker's *Account* is a different thing: the resolver's side of an agent key), `Option<&Self::Handler>` (0.3, a borrow of the resolver), a `Display`-only error bound (0.3)

**Registration number (iktatószám)**:
The identifier a receiver's own system assigns to a pushed incoming or outgoing invoice and may echo in the invoice *Ack* (`InvoiceAck::with_registration_number`); szamlazz.hu records it on the document (the queried `<iktatoszam>`), and it is the receiver's, never szamlazz.hu's own id. Optional; nothing in the protocol requires one.
_Avoid_: filing number, reference number, document id (that is szamlazz.hu's `alap/id`)

**Body limit (Adatkapcsolat)**:
The request-body cap the axum receiver router applies before authenticating a push (`szamlazz_adatkapcsolat::axum::BodyLimit`: `Max(bytes)`, default 64 MiB, or `Unlimited`), because the receiver sits on the public internet and buffers a body before it can check the key; over the cap is `413`, which szamlazz.hu retries like any non-200. Receipt batches are unbounded in principle, so raising it is a deployment-level choice, made deliberately.
_Avoid_: payload size limit (the HTTP framework's word), a cap chosen for the deployment by the crate

### Documents

**Invoice (számla)**:
A finalized request for payment, identified by an invoice number (számlaszám). Created via the Agent's invoice operation.

**Invoice direction (outgoing / incoming)**:
Which ledger side an invoice sits on for the account holder: outgoing (kimenő) = issued by the account holder, incoming (bejövő) = received from a supplier and registered with szamlazz.hu. Orthogonal to invoice kind (proforma, storno, prepayment, …). Distinct from bank-transaction direction: an incoming invoice is settled by an outgoing transaction.
_Avoid_: sales/purchase invoice, AR/AP, inbound/outbound

**Proforma (díjbekérő)**:
A payment request that is not yet an invoice. Created via the invoice operation with a flag; deletable (real invoices are not: they can only be reversed).

**Prepayment invoice (előlegszámla)** / **Final invoice (végszámla)**:
Advance invoice and the invoice that settles it. Both are invoice-operation flags. Like the plain invoice, either may name the proforma it converts (`dijbekeroSzamlaszam`; `InvoiceKind::Prepayment { proforma_number }`, `InvoiceKind::Final { prepayment_number, proforma_number }`: the XSD lists the element independently of the kind flags, #69), and the worker's `create_prepayment` takes `options.proforma` exactly as `create_invoice` does (`create_final` does not: the order's proforma was consumed by the prepayment invoice). szamlazz.hu links the prepayment invoice to the final (`elolegSzamlaszam` or shared order number) but does **not** net it into the final's totals: the final invoice lists the full performance and deducts the prepayment as a negative line at the same VAT rate, supplied by the caller (behaviour note C6-2).
_Avoid_: a final invoice "netted by the server", a prepayment invoice as unable to carry the proforma reference (the pre-#69 shape)

**Corrective invoice (helyesbítő számla)**:
An invoice that corrects a previously issued one, referencing its number.
The Order's supported corrective base is an ordinary, prepayment or final invoice;
further corrections name that original base, not a previous corrective. This is the
worker's supported contract, not a claim that the vendor forbids every other relationship.

**Storno invoice (sztornó)**:
The reversal of an issued invoice, a distinct Számla Agent operation whose fulfillment date must repeat the verified original's `telj`; a missing or unusable original date is `unavailable` with no send, while an invalid caller comment is `invalid_input`. Repeat storno has been observed to return the existing reversal, and proforma/delivery-note storno to echo the target as a no-op: unkeyed Gateway storno retains that echo policy, while a protected Order send against a verified stornoable invoice treats a same-number echo as uncertainty, retaining the marker for read-only reconciliation ([ADR 0007, including the 2026-09-11 amendment](docs/adr/0007-storno-repeats-the-originals-fulfillment-date.md)).
_Avoid_: cancellation, void, a caller-settable storno date

**Receipt (nyugta)**:
A simpler proof-of-payment document with its own create/reverse/query/send operations. The only document type with an idempotency key (hívásazonosító). Its `tipus` is `szamlazz_agent::ReceiptType` (`NY` a receipt, `SN` a storno receipt, else `Other`); a reversed one is `reversed`, and the storno receipt names the original as `reversed_receipt_number`. The receipt's `kifizetesek` are how the buyer paid, by tender (`ReceiptPayment`): the buyer's act, so the word *payment* is right there.
_Avoid_: cancelled (for `stornozott`), `kind` for the receipt's `tipus` (0.3; `document_type` since 0.4)

**Document type (`tipus`)**:
The code a queried document carries: `SZ` invoice, `D` proforma, `ES` prepayment invoice, `VS` final invoice, `HS` corrective, `SS` storno, `SL` delivery note. The Számla Agent crate's open enum `szamlazz_agent::DocumentType` (`Other(String)` for a code it does not know; serialised as the token, so a journaled `FoundDocument::document_type` reads the same as the wire), the one name `document_type` on every surface that carries it, the adatkapcsolat crate's included (`InvoiceInfo::document_type`, `ReceiptInfo::document_type`, the wire token as an `Option<String>`: the receiver shares the name and the open-set rule, not the enum; ADR 0010, #129). The worker's two sets are `FoundDocument` methods, `is_invoice_family` (`SZ`/`ES`/`VS`: what the order-number hint treats as a *Foreign document*) and `is_stornoable` (`SZ`/`ES`/`VS`/`HS`), and its kinds map through `IssuedKind::document_type` / `IssuedKind::for_document_type`. Open-set rule across the crate: a wire *token* the crate does not know is an `Other(String)` (`VatRate`, `PaymentMethod`, `DocumentType`, `ReceiptType`, `InvoiceTemplate`, `ReceiptTemplate`), a numeric *code* an `Unknown(n)` (`InvoiceAppearance`). Decision: #139, #129 (the tipus slice).
_Avoid_: a `tipus` literal (`"SZ"`) in the worker, `kind` for the wire element (the request word: `CreateInvoice.kind` is an `InvoiceKind`), type code as a bare string

**Delivery note (szállítólevél)**:
A non-financial document listing delivered goods; an invoice-operation flag.

### Agent concepts

**Invoice acknowledgement (Számla Agent)**:
A successful invoice-operation envelope, distinct from a reported document number or proof of a reversal. An unnumbered storno acknowledgement retains uncertainty about the exact reversal; a credit acknowledgement or fetched PDF can omit reported identity without substituting the request's target as a vendor echo.
_Avoid_: Ack (reserved for Adatkapcsolat), verified reversal for a bare success, preview for every unnumbered acknowledgement

**Reported taxpayer validity**:
The true or false fact NAV supplies about a taxpayer, when supplied; an omitted verdict is unreported, never an invalid taxpayer. Exchange correlation, software metadata and informational diagnostics are distinct from the taxpayer's business data.
_Avoid_: false for unreported validity, successful lookup as proof of taxpayer validity

**Agent key (számlaagentkulcs)**:
API-only credential passed inside the request XML. Preferred over username/password.

**Credit entry (jóváírás / kifizetés)**:
A payment registered against an invoice via the Agent. IPN reports the resulting current payment status, not the individual credit entry. In the Számla Agent crate it is `CreditEntry` on the way out (`RegisterCreditEntry`) and `RecordedCreditEntry` on the way back (`InvoiceDocument::credit_entries`); its `jogcim` is the **title** on both sides, a `PaymentMethod` (the method the entry was settled by; an unknown token is `PaymentMethod::Other`). The register operation answers the `InvoiceBalance` (net, gross, outstanding, payment method). The one deliberate exception to the word: the CLI verb `szamlazz payment register`, user-facing and kept, since the operator's word for the act is "payment" (#185). The worker's by-number write is `Szamlazz.Agent.set_credit_entries` (`SetCreditEntriesRequest` of `CreditEntryInput { date, title, amount, comment }`, `SetCreditEntriesResponse`, the step `set-credit-entries-{number}`), the queried invoice's are `QueryResponse.credit_entries` (`CreditEntryRecord`) and `OrderStatus`'s document's `credit_entries`, the projection's `FoundDocument::credit_entries` / `credit_entry_amounts()`: the 0.3 `set_payments` / `PaymentEntry { method, description }` / `payments` were renamed in the Restate-conventions review (2026-09-09), a breaking change of the worker's contract (a handler name is part of the Restate registration).
The Adatkapcsolat invoice model uses the same names, `RecordedCreditEntry`, `InvoiceDocument::credit_entries` and `title` for `jogcim` (the receiver keeps `Option<String>`, the agent a `PaymentMethod`; ADR 0010). Receipt `payments` remain the buyer's tenders.
_Avoid_: payment (overloaded; reserve for the buyer's act, and the receipt's `ReceiptPayment`, which is one), `RecordedPayment` / `payments` on the queried invoice (0.3 names), `method` for `jogcim` (the request's 0.3 name; `title` on both sides since 0.4, the worker's `CreditEntryInput` included), `set_payments` / `PaymentEntry` / `PaymentRecord` / `payments` (the worker's 0.3 wire names)

**Response version (válaszverzió)**:
Agent request field selecting the response body format: 1 = plain text or raw PDF bytes, 2 = structured XML with base64 PDF. The crate requests `2` everywhere it has the choice, as the one constant `szamlazz_agent::ops::RESPONSE_VERSION`, so the pin is greppable (#184 (4)).
_Avoid_: a `"2"` literal at a writer

**Queried-document blocks (agent)**:
The parts of a queried `<szamla>` (`InvoiceDocument`) the worker never reads, named once here with their Hungarian elements so the English is not guessed twice: `FinancialItem` (`qutet`, a ledger-side row beside the printed line items: VAT deductibility `afalevon`, settlement period, labels; szamlazz.hu documents no English meaning, the name is most likely a *QUiCK tétel* after the accounting system its `forras` codes list), `Waybill` (`fuvarlevel`, the carrier block and its per-carrier sub-blocks `Mpl`, `Sprinter`, `TransOFlex`, `PickPackPoint`), `ExchangeRate` (`arfolyam`, bank and rate for a non-HUF document), `BuyerLedgerInfo` (`vevo/fokonyv`, the buyer's general-ledger accounts and settlement dates), `customer_account_url` (`vevoifiokurl` in the create reply's body and the `szlahu_vevoifiokurl` header: the buyer-facing page of the document), `economic_event_id` (`gazdEsemAzon`: the id of the economic event the document belongs to, equal to the original's `alap/id` on an `SS`/`HS` and inherited by a converted `SZ` from its `D`, as observed). Each carries its element as a `#[doc(alias)]`.
_Avoid_: financial line for `qutet` (it is not a printed line), shipping block (a waybill is a carrier document), an English rendering of `qutet` as settled fact


**Invoice appearance (`eszamla`)**:
Whether a document is a paper invoice or an e-invoice. A boolean on the create and storno requests (`e_invoice`; the wire `eszamla`, default `false` = paper); an integer code in a queried document, `InvoiceInfo::appearance` of type `szamlazz_agent::ops::query_xml::InvoiceAppearance`: `0` not an invoice (a proforma), `1` paper, `2`/`3` e-invoice (`Electronic(code)`, and `is_e_invoice` is the variant, whatever code a hand-built value carries), anything else `Unknown`; the vendor annotation, confirmed on the test account (#73): a create with `true` is queried back as `3`, one with `false` as `1`; `2` was never observed. szamlazz.hu does **not** require a storno's `eszamla` to match its original's: a mismatch is accepted silently and the `SS` takes the *request's* flag, numbered under the account's e-invoice prefix (`E-…`) when `true`, so the worker's storno handlers lift the flag from the verified original (`FoundDocument::e_invoice`, read off the journaled `appearance` code through `InvoiceAppearance`: `Paper` → `Some(false)`, `Electronic` → `Some(true)`, else `None`, which `StornoIntent::from_verified` fills with the account's `defaults.e_invoice`), never from the caller, exactly as they lift `telj` (ADR 0007); that derivation, not the server, is what keeps a reversal in its original's form. Every queried document of the 2026-09-03/06 probes reported `1`: paper (the P60 stornos, numbered `E-…` and never queried, were by that numbering e-invoice stornos of paper invoices); 352 (`keltDatum` must be today on a storno) was observed there on a paper storno, so it is not a rule of e-invoices only. The code is an `i64` in both XML crates and serialises as the integer it is (the agent's 0.3 string `"2"` is gone); the adatkapcsolat twin (`szamlazz_adatkapcsolat::InvoiceAppearance`, on `InvoiceInfo::appearance`) is a separate type by decision, ADR 0010: the crates share the vocabulary, not the type.
_Avoid_: e-invoicing "enabled" as a reading of `<eszamla>1</eszamla>` (the pre-#73 behaviour-note premise; `1` is paper), `eszamla` as a flag in a queried document (it is a code), `e_invoice` as the queried field's name (0.3; `appearance` since 0.4), a caller-settable storno `e_invoice`

**Outstanding amount (kintlévőség)**:
The unpaid remainder of an invoice's gross total.

**VAT rate (áfakulcs)**:
A numeric percentage or a NAV-defined special code (AAM, TAM, EUT, KBAET, …) on a line item. The code set is NAV-driven and changes over time: it is an open set, not a fixed enum. A percentage's wire token is normalised (`27.00` → `27`, `5.50` → `5.5`), hygiene, not a requirement: szamlazz.hu accepts `27.00` and `27.0` too (test account, P60), and a queried rate comes back as the double `27.0`.

**Line item (tétel)**:
One row of a document: name, quantity, unit, net unit price, VAT rate, and net/VAT/gross values whose arithmetic szamlazz.hu verifies server-side. When the crate derives the values (`LineItem::try_calculated`, the one derived constructor since 0.4) the rounding is an explicit `Rounding`: the currency's *minor unit* (whole forints for HUF, cents for EUR; the choice the worker makes for every document), a fixed scale, or exact; half away from zero at each step, and a value that does not fit a decimal is `ArithmeticError`, never a panic. The worker answers that error as `invalid_input`. `LineItem` is plain data (ADR 0008): the optional fields are set with functional update, not builder methods. A receipt row has no element for `margin_vat_base` or the ledger's economic-event and settlement fields, so a `CreateReceipt` carrying one is refused before the wire (`RequestError::UnsupportedOnReceipt`) rather than sent without it (#182). Minor-unit is what szamlazz.hu stores anyway: it rounds every sent value to two decimals on its own, each independently and without recomputing the gross, so an exact `100.004 / 27.00108 / 127.00508` becomes a stored `100 / 27 / 127.01` (P60); rounding per step on our side is what keeps the stored document consistent. Its `net = price × qty` check (259) tolerated a 0.5–2 HUF discrepancy and refused 5 (P60), so the half unit the rounding can introduce is inside.
_Avoid_: `calculated` / `calculated_for_currency` / `with_comment` (the 0.3 forms, removed in 0.4: two panicked on caller money and the last was exact rather than minor-unit for every currency but HUF), unrounded/exact as a default, a receipt writer that drops a field silently

**Authoritative line amounts**:
Caller-approved net, VAT and gross values that must be submitted together without
repair. Distinct from a net-calculated line: gross-first pricing derives VAT from
the line gross, then net by subtraction, so rounding a net unit price first may
produce a different split. Monetary preflight establishes the submitted amounts;
approved document totals assert their sum before issuance. Neither establishes
provider acceptance or settles write uncertainty. Decision: ADR 0016.
_Avoid_: gross unit price as the meaning of `unit_price`, monetary parity checked only after issuance, arbitrary splits as provider-validated

### Restate worker concepts

**Order**:
The `Szamlazz.Order` Restate Virtual Object serializing document mutations per *Scope* and order number, with szamlazz.hu as the document source of truth and only *Unresolved write* uncertainty as durable state. Its key is caller-trimmed, case-preserved, XML 1.0 text of 1–40 UTF-8 bytes with no whitespace, control character or `:`, in Unicode NFC; document ownership, marker admission, recovery and execution rules are in [the protected Order protocol](docs/design/order-write-protocol.md) and [the worker identity contract](crates/restate-szamlazz/README.md#identity).
_Avoid_: order object, invoice workflow, ledger (there is none; szamlazz.hu is the source of truth), tenant object, a single internal space as allowed (the pre-#64 rule refused only runs)

**Document kind / Issued kind**:
The two closed enumerations of what an *Order* issues: `DocumentKind` (`Proforma`, `Invoice`, `Prepayment`, `Final`), a kind of which an order carries **at most one live document**, each with its own handler and *External id* (`{namespace}:{order}:{kind}`), and `IssuedKind`, those four plus `Corrective` (an order may carry any number, under `…:corrective:{correction_id}`): the kind of anything the service issued, what the *Lookup step*, the *Create step* and every response's `kind` carry. They map onto the wire's *Document type* through `IssuedKind::document_type` / `for_document_type`, never by a `tipus` literal; the storno and the delivery note are document types no kind names (a storno is a reversal of a kind's document, never a kind itself). Neither is `#[non_exhaustive]`: a fifth kind is a new handler and a new external-id shape, a breaking change by design. Types: `restate_szamlazz::identity::{DocumentKind, IssuedKind}`.
_Avoid_: kind for the wire `tipus` (the request word), `DocumentKind` for the deleted adatkapcsolat archive copy (#176), a storno kind

**External id (szamlaKulsoAzon)**:
The Agent's optional per-document identifier, used by the worker as the identity handle. Deterministic from the key alone under the deployment's *Namespace* (`{namespace}:{order}:{kind}` for the four kinds, `{namespace}:{order}:corrective:{correction_id}`, `{namespace}:{order}:storno:{number}`, `{namespace}:by-number:{number}:storno` for an unmanaged storno), so any invocation can find what an earlier one issued; the two-segment `{namespace}:check-account` is the sentinel *check_account* probes and nothing the service issues carries. Bounded at **110 bytes** (`ExternalId::MAX_LEN`; the length verified accepted and queryable on szamlazz.hu, which documents no limit; a truncated id could hide the document from queries by its full id and prevent reconciliation) by bounding its parts: the namespace at 16, the *Order* key, the `correction_id` (`CorrectionId`) and the caller's *Invoice number* at 40 bytes each, so the longest shape, `{namespace}:{order}:corrective:{correction_id}`, is 109; proven at compile time in `identity.rs`. Its segments are separated by `:` (`ExternalId::SEPARATOR`), which every caller-supplied part excludes, and its eight fixed tokens (`ExternalId::TOKENS`: the five kinds, `storno`, `by-number`, `check-account`) are not correction ids in any letter case, so no composition reads as another. It carries no account marker: the namespace is one per deployment and shared by every account, and the *Scope* selects the account. Not unique server-side and never echoed in responses: a query returns the newest holder, and every document found by it is validated (order number, `tipus`) before it is trusted; nothing about the account (see *Account*). It is a discovery handle, never durable write protection. The only namespace marker any worker response carries.
_Avoid_: idempotency key (szamlazz.hu does not treat it as one), generation (no counter; the newest holder is the answer), external reference, account id or scope inside it (the scope selects the account; the id carries only the namespace), hashing (the parts are bounded so the id never needs it)

**Invoice number (as the caller sends it)**:
The worker's bounded mutation target (`contract::InvoiceNumber`): exact XML 1.0 text of 1–40 UTF-8 bytes, with no whitespace, C0/C1 control character or `:`, preserved without trimming because it enters step names and storno *External ids*. Distinct from a vendor-reported number and recovery evidence; discovery's character limit does not establish the byte bound, which is an additional runtime rule ([worker identity contract](crates/restate-szamlazz/README.md#identity)).
_Avoid_: `InvoiceNumberInput` (the `*Input` types mirror agent structs; this one mirrors nothing), an unbounded `String` in a request type

**Namespace**:
The external-id prefix of this deployment (`{namespace}:{order}:{kind}`); chosen by the operator, opaque to szamlazz.hu, permanent: changing it would hide every document issued so far. 1–16 bytes of `[a-z0-9-]`; `:` is excluded because it is the separator. One per deployment, shared by every *Account* it serves. Configured as the top-level `namespace` key of the deployment configuration, beside `[issue]`, `[read]` and `[resolve]` on `WorkerConfig`; it is not part of any account. Pinned per invocation in the *Prologue*. Type: `restate_szamlazz::identity::Namespace` (the deployment settings hold it).
_Avoid_: slug (the pre-#20 name), prefix (ambiguous with the invoice number prefix), tenant prefix

**Account**:
One szamlazz.hu account as the worker knows it: a resolver-owned id, endpoint (`account::Endpoint`: an `http` or `https` URL with a host and **no userinfo**; the endpoint is journaled with the account and shown in the Restate UI, so `user:password@` is refused at parse time; plain `http` stays allowed for a local mock or a proxy, and `Endpoint::is_cleartext` reports one on a host other than loopback as sending the agent key in cleartext, for a host's start-up log to `warn` on (#65)), document defaults, seller block and a *Credential ref*, never its agent key; resolved once per invocation and journaled, so an invocation finishes on the account it started on and the Restate UI can show it for the retention period without exposure. A *Journaled type*. **It carries no account pin**: nothing the worker compares a found document with. Ownership validation is about the document: under one of our external ids a document is ours when it carries the order number and the `tipus` of the kind (else `conflict{external_id_collision}`); found by number, `Szamlazz.Order`'s verifies require this order's number (else `conflict{not_managed}`). 0.3 pinned two fields of a queried document, `teszt` (`mode`, required) and `szallito/id` (`supplier_id`, optional); ADR 0006's account-pin amendment (2026-09-07) dropped both, with `AccountMode` and the `account_mismatch` fault: neither field is in a create response (a create's reply is a number and totals), so neither could fire before the first document of a fresh order had been issued into whatever account the key opens, and the reference value had to be read off the very account being checked (`szallito/id`, undocumented besides) or only told test from live (`teszt`). **The risk is accepted and stated**: a key under the wrong scope, a live key where a test one was meant or the reverse, issues there, answers `issued`, and nothing in the worker fails. The go-live check (the library README's *Go-live*, design §10) uses executable `crates/restate-szamlazz/examples/verify_seller.rs` with the **actual deployed `Accounts` resolver and credential store**, a fresh Számla Agent client at the resolved endpoint per scope, and independent expectations for a known document's `test`, seller name and tax number, outside Restate's journal. A separately copied key does not check the deployed mapping; `Szamlazz.Agent.query` deliberately omits the seller block. Repeat after rotation; the check is point-in-time, not a pin. No namespace: that is a deployment setting. Type: `restate_szamlazz::account::Account`.
_Avoid_: tenant, customer, organizer (the caller's concept; an account is what an organizer or event maps to), account config (the static resolver's configuration is a different type), the agent key as part of it, mode / supplier id / account pin (all gone: ADR 0006, account-pin amendment), "fails loudly on its first found document" (the pre-amendment claim; the first document of a fresh order was never checked)

**Seller block (`<szallito>`)**:
The seller party of a queried document (the counterpart of `<vevo>`) as szamlazz.hu's own docs define the word: in standard invoicing the szállító issues the invoice to the buyer; in third-party invoicing (*Megbízott számlakibocsátás*, out of scope: a delegate issues with a dedicated login in the principal's account, and an agent key, which belongs to an account, never a user, cannot be used for it) the szállító is the *megbízó*, the company in whose name and account the documents are made. The block is the seller as printed on the document (`nev`, `cim`, `adoszam`, `bank`, and an `id` szamlazz.hu annotates nowhere), present in query bodies only, never in a create response; the same `szallitoTipus` names the third-party vendor on an incoming invoice, and the Adatkapcsolat re-pushes an invoice when the block's `bankszamla` changes, so it is per-document state. The Számla Agent crate parses it in full (`Supplier`; `.supplier.id` in the CLI's JSON). The Restate services **read nothing from it** and `Szamlazz.Agent.query` deliberately omits it: 0.3 pinned its `id` as the account's `supplier_id` (an undocumented row id of unverified stability whose reference value could only be read off a document through the configuration it was meant to check, a tripwire that could not fire before the first wrong-account create and whose false positive would strand every order of the account), and ADR 0006's account-pin amendment (2026-09-07) dropped it, together with the `mode` pin on `teszt` (same blind spot; see *Account*). The go-live check uses `examples/verify_seller.rs` with the actual deployed `Accounts` bundle, outside the journal: under each *Scope*, a fresh Számla Agent client queries a known document and compares `test` and this block's name and tax number with independent expectations. Considered, not taken: a pin on the seller tax number (documented, operator-known, what szamlazz.hu itself identifies an account by; the same tripwire with a trustworthy field), a configured canary document the probe and the create step would verify before a first send (the one shape that would gate).
_Avoid_: supplier id / supplier pin (the 0.3 pin; gone), supplier as an account identity, "the only server-side account identity a found document exposes" (the pre-amendment claim; there is none), third-party invoicing as in scope

**Credential ref**:
The opaque reference an *Account* carries to its credentials, handed to the *Credential store* on every handler execution (`CredentialStore::fetch(credential_ref)`). Owned by the resolver that produced the account; journaled with it, since it is not a secret. The static resolver sets it to the account's `id`. Type: `restate_szamlazz::account::CredentialRef`.
_Avoid_: reference without qualification (reserved for this), key id, secret name, scope (the scope selects the account; the ref selects its credentials)

**Account resolver**:
The pluggable trait (`AccountResolver::resolve(scope: Option<&str>)`) that maps a request's *Scope* to its *Account*; object-safe, boxed futures, no `Debug` requirement (#43: a resolver often holds a pool or a key table, and the crate never formats one; `Accounts`' own `Debug`, and so `Order`'s and `Agent`'s, names the two trait objects without descending into them, so a store that derives `Debug` over a key map cannot print its keys through the services). Answers as data: unscoped (no scope and no unscoped account), unknown (the scope names no account); `unavailable` is a retryable fault whose display text never echoes the source's own message. Its half of the safety contract, carried as a checklist on the trait's rustdoc: one szamlazz.hu account is reachable under exactly one scope value (unscoped counts as a value), no fan-in (the static resolver checks this at load time, a database-backed resolver must guarantee it itself, because the worker cannot detect fan-in at runtime and `check_account` only echoes configuration), the mapping is append-only, unique `(endpoint, credentials)` pairs, **the right key under the right scope** (the worker holds no account pin, so this is the resolver's guarantee, verified at go-live and after rotation by `examples/verify_seller.rs` using the actual deployed `Accounts` resolver/store and a fresh Számla Agent client per scope to compare a known document's `test` and *Seller block* with independent expectations; `Szamlazz.Agent.query` omits that block; the `mode` matching `teszt`, the `supplier_id` recommendation, the unique-supplier-ids check and the *Prologue*'s `warn` on an unpinned scoped resolution of #88 are gone with the pins; ADR 0006, account-pin amendment), a stable *Credential ref* across rotations (rotate the value behind the reference, never the reference), and never caching the unscoped / unknown answers. The static resolver (`restate_szamlazz::account::StaticResolver`, built with `TryFrom` from serde-only configuration) implements both this and the *Credential store* with the agent key inline and `credential_ref = id`, in one of two mutually exclusive shapes: `[account]`, where `resolve(None)` is the account and any scope is unknown, or `[accounts.<scope>]`, where `resolve(None)` is unscoped and a scope is its account or unknown; the multi shape is checked at load time (unique `(endpoint, agent key)` pairs (the endpoint on its normalised form, `Endpoint::normalized`: scheme and host case, a default port written out, trailing slashes, so `…/szamla/` beside `…/szamla` with one key is one account, while the stored text and what the client posts to stay as written; #113) and ids; scope keys `[a-z0-9_]` of at most 36 bytes). There is no default account. Bundled with the store as `Accounts`, shared by both Restate services; the crate root re-exports `Credentials` and `AgentKey` (and the `restate_sdk` and `szamlazz_agent` crates) so an embedder implements both traits without a second dependency, and its `lib.rs` carries a compiling custom-wiring example (database-backed resolver, a credential store of the embedder's own, a service of the embedder's own on one endpoint) that names the two compiler errors that path hits: `account::Endpoint` vs `restate_sdk::prelude::Endpoint` (alias one) and, when one value is both resolver and store, `Arc::clone(&db)` inferring `Arc::<dyn AccountResolver>::clone` and failing where `db.clone()` coerces.
_Avoid_: tenant resolver, account lookup (lookup is the first durable step of issuing), directory, account cache (a resolver may cache internally; the worker does not), `Debug` supertrait (the pre-#43 shape)

**Endpoint comparison (Account)**:
Equivalent URL spellings of an Account's Számla Agent target, with trailing slashes deliberately treated as equivalent; original text remains the Account's configured value. This check cannot establish account uniqueness through DNS aliases, redirects, proxies or different credentials: those remain the resolver's and operator's no-fan-in responsibility (#214, superseding the narrower comparison description above).
_Avoid_: URL comparison as proof that two accounts are distinct

**Scope**:
The Restate scope value a request arrives under (`/restate/scope/{scope}/call/…`); the caller's identifier for a szamlazz.hu account and the only channel for selecting one, never a header, a body field or the Virtual Object key. Opaque to the worker: it is handed to the *Account resolver* as is. Restate namespaces the Virtual Object key and the `Idempotency-Key` per scope (both are part of the invocation's identity, and the scope is the partition key), so the same order number under two scopes is two `Szamlazz.Order` instances and the same key under two scopes is two invocations; a path segment of each request, not a session: callers set it on every call. One account ⇔ one scope, and unscoped counts as a scope value (the single-account shape serves its account unscoped; the multi-account shape refuses unscoped requests). Format: Restate's `[a-zA-Z0-9_.-]`, non-empty, at most 36 characters (ASCII, so bytes; a dashed UUID is exactly 36); the static resolver's keys are the strict subset `[a-z0-9_]` so environment overrides can address them. Routing, not authorization: the ingress sits behind a gateway that sets the scope from the authenticated identity, never forwards a caller-supplied scope path and strips `x-restate-*` request headers. Reaches the worker only under protocol v7, which Restate's ingress does not gate a scoped path on: *check_account* per scope after every deploy is the check. Kafka ingress is untested in multi-account mode. Decision: ADR 0006.
_Avoid_: tenant id, tenant, account header, reference (see *Credential ref*), account id (the *Account*'s `id` is the resolver's own identifier, not the scope), event or organizer as the scope (they map to an account in the caller)

**Request identity (identity keys)**:
Restate's signature on every request the runtime makes to the endpoint, verified against the `publickeyv1_…` public keys a deployment registers on the SDK's endpoint builder (`Endpoint::builder().identity_key(…)`); with at least one key the endpoint refuses unsigned requests. What enforces the assumption the *Scope* model rests on (that only the Restate runtime speaks to the endpoint): the scope is protocol data inside the request, so an endpoint accepting unsigned requests lets any client reaching its port invoke either service under any scope, on every *Account* the deployment serves, and the gateway of ADR 0006 rule 6 sits in front of the ingress, not this port. Required wherever anything but the runtime can reach the port and **required** in the multi-account shape. The host's responsibility, not the library's: the SDK starts without keys, and nothing in `restate-szamlazz` can tell whether a deployment registered any (the removed `restate-szamlazz-endpoint` crate read the decision three ways and warned on an omission, #96; design §10 carries what a host does instead). Authenticates the runtime to the endpoint, never callers (that is the ingress gateway's job).
_Avoid_: caller authentication (ADR 0006 rule 6; the gateway's), "identity" without qualification (the *External id* is the document's; `identity.rs` is that module), signing key (the endpoint holds public keys only), `identity_keys` as a configuration key of this workspace (it was the endpoint crate's; a host names its own)

**Credential store**:
The source of an account's credentials, addressed by its stable *Credential ref*. Credentials are acquired only when an *Execution* needs an external operation and are held only for that execution; completed operations replay without consulting the store. A dynamic store makes rotation visible to the next execution that needs an operation. A static store retains startup credentials: registering a new immutable deployment does not rotate keys held by an older deployment. Store unavailability, an unknown reference or failed Gateway initialization produces `unavailable` at the executing operation boundary, preserving uncertainty about any earlier send. Credentials and sensitive source messages never enter journals or caller faults. The bounded fetch and failure policy is specified in design §4 (#200, #65, #114).
_Avoid_: secret store (generic), key store, vault (a product), caching credentials across executions, session (the szamlazz.hu cookie is what the fresh client isolates)

**Idempotency-Key**:
Restate's per-*Scope* ingress retry identity for one logical request: keep it while the invocation is unfinished, paused included, to attach or retrieve its retained outcome; a completed fault is replayed under the same key for its retention period. Deliberate renewal after write uncertainty requires settlement of the exact earlier request before a new key, and a new business decision with the original *Expected-document intent*; empty queries, elapsed time, cancellation and kill do not settle uncertainty ([caller contract](crates/restate-szamlazz/README.md#caller-contract), ADR 0004).
_Avoid_: request id (v1's body field; gone), correlation id, "rotate after any error", rotation as permission to resend

**Outcome**:
A domain result returned as data (HTTP 200), such as `issued`, `already_issued`, `reconciled`, `reversed`, `rejected` or `conflict{reason}`, distinct from a fault. `CreateOutcome` and `StornoOutcome` name the caller's tokens and the Gateway's journaled outcomes in their respective modules; path-qualify the Gateway type where both are in scope, and consult [the worker contract](crates/restate-szamlazz/README.md#contract) for the open token sets and response shapes.
_Avoid_: error/failure for a rejection or conflict, status, "the fault body" for the envelope (the fault is inside `message`), `contract::Outcome` (0.3; `CreateOutcome`), `GatewayStornoOutcome` / an `as Gateway…` import alias (path-qualify), `ALL` for an open token set, treating `#[non_exhaustive]` as wire openness

**Fault**:
A structured worker failure (`contract::Fault`), carried as JSON text inside Restate's ingress envelope `message`; the envelope's `code` is the HTTP status, the inner `code` the worker token, and `szamlazz_code` a vendor answer when present. `outcome_unknown`, `unavailable` and `credentials_rejected` preserve possible write effects and require settlement before deliberate renewal; unknown codes or causes remain unclassified, native kill errors remain native, and [the fault contract](crates/restate-szamlazz/README.md#faults) defines operation-specific meanings and cancellation handling.
_Avoid_: fault as proof of non-execution, vendor code as the fault token, unknown token as retry advice

**Invocation cancellation**:
An intentional stop of a Restate invocation, distinct from infrastructure unavailability and from reversing a document. Read cancellation is the structured `cancelled` fault (409); write cancellation is `outcome_unknown` (500) with `cause: cancelled`, because an external effect may have landed. Neither authorizes automatic retry or reissue: reconcile a cancelled write before deliberately renewing the operation. A killed invocation may retain a native error rather than a worker fault. Decision: ADR 0011, #203.
_Avoid_: cancellation as rollback, cancellation as dependency unavailability, cancellation as permission to reissue

**Reissue**:
Explicit replacement of the particular reversed document named by `options.reissue: {expected_number}`, after settling any earlier write uncertainty; the replacement becomes the newest holder of the same *External id*. An absent or changed target before arming, or an absent target at the permitted final pre-send check, is `conflict{target_changed}` with nothing sent. A matching live target is `conflict{live}`, and a reply naming the old target does not establish replacement: retain uncertainty and reconcile read-only ([ADR 0012](docs/adr/0012-expected-document-mutation-intent.md), [protected protocol](docs/design/order-write-protocol.md)).
_Avoid_: re-create, retry (a retry targets the same document)

**Expected-document intent**:
The particular known document a caller means to replace or delete. A reissue or
deletion retains that expected number across retries; a replacement does not
inherit the caller's permission. Distinct from external-id discovery (finding
the newest holder) and finite request deduplication (replaying a retained
completion). A changed target requires a new business decision, not an automatic
substitution of its number. ADR 0012 records the request contract and migration
from the historical boolean reissue option.
_Avoid_: generation, indefinite idempotency, expected number as vendor atomic compare-and-set

**Named-target deletion**:
Explicit deletion of the caller's exact recorded proforma in the resolved account,
requiring that it carry the current Order key. Distinct from namespace-owned deletion,
which selects the expected holder of the worker's proforma external id. A coexisting
namespace-owned proforma is untouched; an absent namespace slot says nothing about the
named target. Reported absence cannot distinguish deletion from consumption or settle
an earlier uncertain send.
_Avoid_: adoption, force as an ownership bypass, local association as vendor-reported order association

**Reversal (as observed)**:
A document is reversed when szamlazz.hu reports `<sztornozott>true</sztornozott>` on it; the storno document carries `hivszamlaszam` = original and is the order-number hint only until something newer is issued under the order. The service does not track who reversed a document or when.
_Avoid_: reversal origin (v1 concept; gone), cancellation

**Foreign document**:
A live invoice-kind document (`SZ`, `ES`, `VS`) found under the order number by the order-number hint that is under none of this order's external ids: another channel or namespace on the same szamlazz.hu account. Detected live in the lookup step, on every kind but correctives, unconditionally (there is no setting); never adopted, nothing recorded; the create returns `conflict{foreign}`. The order's own live invoice, prepayment invoice or final invoice is never foreign: every create that could meet it looks its external id up first and is refused before the lookup step runs (`create_invoice` and `create_prepayment` in their exclusivity step against the other chain's id and `…:final` (`conflict{prepaid_chain}`; the final invoice outlives its reversed `ES`, so it needs its own row; #62), `create_proforma` against `…:invoice`, `…:prepayment` and `…:final` (`conflict{order_invoiced, existing_number}`: a proforma after the invoice makes no sense, but the invoice is ours)), so the hint never meets it. A duplicate-order-number answer (71/152) whose external-id re-query finds our document reversed or absent is the same situation seen from the create step: the order-number query names the existing document (`conflict{duplicate_order_number, existing_number?}`), never adopts it; a 71/152 with nothing under the order at all is settled the same way without `existing_number`, logged at `warn`; a refusal szamlazz.hu already gave is not re-sent for.
_Avoid_: external document, orphan, foreign for the order's own invoice met by `create_proforma` (that is `order_invoiced`)

**Lookup step**:
The full read before the *Create step* (`lookup-{kind}`), after the target *Ownership lookup* and prerequisites: one read-only `ctx.run` under the *Read policy* that queries our external id and, for every kind but correctives, takes the order-number hint. It settles every case that needs no create (a live document of ours (`already_issued`, or `conflict{live}` with `reissue`), a reversed one (`reversed{storno_number}`, or proceed with `reissue`), an invalid holder (`conflict{external_id_collision}`), a foreign document (`conflict{foreign}`)), and otherwise hands the create step what it saw. It re-observes changes outside the order's lock after references are resolved; it does not replace the earlier ownership-only read, which settles an existing target before prerequisites can hide it. A query szamlazz.hu did not answer is *Unanswered* and re-executes the whole step; exhaustion is `unavailable{order, kind, external_id}`. Gateway fn: `Gateway::lookup` → `Result<LookupOutcome, Unanswered>`.
_Avoid_: pre-query (the create step has its own), attempt

**Ownership lookup (`OwnershipOutcome`)**:
The one "is this document ours?" read: `Gateway::lookup_ours(external_id, order, kind)` queries one of the order's *External ids* and validates the newest holder with `FoundDocument::is_ours` (the order number and the `tipus` of the kind), answering `Absent` (code 7), `Live` or `Reversed` (a document of ours), `Collision` (another order's or kind's document: never trusted and never read as "absent", since a document of ours may hide behind it), or the two answered codes (`CredentialsRejected`, `Api`). Every one is named `lookup-{kind}` for the kind whose id it reads. The **target ownership lookup** is the first read of every create/correct handler after validation and the *Prologue*, before prerequisites: live is `already_issued` (or `conflict{live}` with `reissue`), collision is `conflict{external_id_collision}`, reversed without reissue is `reversed`. A reversed non-corrective takes a best-effort `hint-storno-{number}` (exhaustion leaves the number absent, cancellation propagates); a corrective takes no hint. Only an absent target or explicit reissue proceeds through prerequisites, then the full *Lookup step* and *Create step*. A consumed proforma, reversed prepayment or changed corrective base cannot hide an existing target. The prerequisite reads (exclusivity, `create_final`'s prepayment, proforma link), `delete_proforma`'s proforma and `get`'s four also journal this outcome; their decisions remain their own. The full lookup and create ask the ownership question inside their own outcomes through `Gateway::seen`, so validation and its collision `warn` have one home. Answered codes become `unavailable` or `credentials_rejected`. A *Journaled type* since #181. Type: `restate_szamlazz::gateway::OwnershipOutcome`.
_Avoid_: `support::Lookup` / `Lookup::classify` (the pre-#181 service-side classification; gone), `OwnedLookup` (reads as Rust's owned-vs-borrowed), external-id query (the selector, not the question)

**Create step**:
The protected Order write after ownership, prerequisites and the full lookup: one acknowledged, consumed send permission plus a fresh holder check, followed by journaled settlement or retained uncertainty. An interrupted or inconclusive write continues through read-only reconciliation and pause, never another create send; the exact arming, expected-target, corrective-base and evidence rules live in [the protected protocol](docs/design/order-write-protocol.md).
_Avoid_: attempt, issue step (the whole protocol is "issuing"), send (one part of the step), unconfirmed for an answered leading query (an answer is data; nothing was sent)

**Unconfirmed**:
A create or storno exchange whose outcome is not established, including lost answers, open codes and contradictory or insufficient acknowledgement identity; it grants no permission to repeat a write. Protected Order writes retain a marker and reconcile read-only, direct Gateway create callers own durable uncertainty and settlement, and unmanaged storno retains its distinct *Issue policy* ([Gateway contract](crates/restate-szamlazz/README.md#gateway-and-services), [storno evidence policy](docs/adr/0007-storno-repeats-the-originals-fulfillment-date.md)); a failed leading query can also be unconfirmed, so the term alone does not assert a send occurred.
_Avoid_: unknown outcome (the fault is `outcome_unknown`; this is what precedes it), transport error (one cause of it), `Contradiction` as a variant (the pre-#41 retryable one; a 71/152 with nothing under the order is settled data now), rejected for a code the crate does not know (it may be a new "issued, but…" code; #13), an answered leading query as `Unconfirmed::Transport` (the pre-#63 fold; it is `CreateOutcome::Api` / `Unavailable` now), `szlahu_down` as an "open code" (it is `Unavailable`)

**Outcome class**:
The Számla Agent crate's answer to "may a document exist despite this error?": `szamlazz_agent::OutcomeClass`, from `ErrorCode::outcome_class()`, `ResponseError::outcome_class()` and `ClientError::outcome_class()`: `Rejected` (szamlazz.hu refused before acting; the credential codes 3/135/136/164 included), `Unknown` (1, 55, 56 without a number, every code the crate does not know, `szlahu_down`, a transport or parse failure; retain uncertainty and reconcile read-only), `DuplicateOrderNumber` (71/152), `NotFound` (7). Distinct from `is_retryable()`, which says whether the same *query* can succeed later (1, 55) and is never permission to re-send a create. The worker's create and storno steps take their API-code arms from it and add `CredentialsRejected` on top, read off `ErrorCode::is_credential_error()` (3/135/136/164, a subset of `Rejected`; the agent crate's method since #128, so every consumer gets the same answer); `#[non_exhaustive]`, and a class the worker does not know is treated as `Unknown`. Decision: #13.
_Avoid_: retryable (a different question), error class (it classifies the outcome, not the error), severity

**Unresolved write**:
A write whose external effect may still occur or may have occurred without a conclusive answer. An empty query,
elapsed time, cancellation or invocation kill does not settle it. An **unresolved-write marker** records that
uncertainty across invocations; it is not a ledger of documents. The original invocation is retained for
read-only reconciliation and pause; the marker guards later mutations after its lock is released. Recovery
requires matching positive evidence or an audited operator assertion that the exact request did not execute
and cannot execute later. A marker can conservatively describe a request that never sent. Operator attestation
is never represented as vendor proof (ADR 0004, #205, #216).
_Avoid_: pending invoice (existence is not known), timeout as negative settlement, kill as permission to issue

**Audited positive settlement**:
An authorized operator's evidence that the exact unresolved write completed and cannot execute later, naming
its issued document, reversal document or deleted proforma and a durable audit reference. Distinct from both
worker-verified document evidence and non-execution attestation: a completed deletion cannot truthfully be
called non-execution. Absence, elapsed time, cancellation and kill alone establish none of these conclusions.
Decision: ADR 0013.
_Avoid_: vendor proof for operator evidence, force-clear, positive settlement as permission to reissue

**Issue policy**:
The deployment's run retry policy for unmanaged `Szamlazz.Agent.storno`, relying on observed storno idempotence; protected Order writes instead consume one permission and retain read-only reconciliation under their invocation policy. Execution-count and duration limits are exhaustion thresholds, not deadlines or external-send bounds, and delay is not settlement of an earlier request ([worker retry controls](crates/restate-szamlazz/README.md#retry-policy), ADR 0004).
_Avoid_: attempt budget, backoff (the loop is gone), retry policy without qualification (the handlers have their own), a second copy of "60 s" (derive from `szamlazz_agent::client::REQUEST_TIMEOUT`)

**Read policy**:
The deployment's run retry policy for ordinary reads and operator document verification: unanswered reads may be re-executed, while replay of a completed read uses its recorded observation. Exhaustion becomes `unavailable` (or absent optional storno information on a best-effort read), cancellation propagates distinctly, and protected Order reconciliation uses its mutation invocation policy instead ([worker retry controls](crates/restate-szamlazz/README.md#retry-policy), ADRs 0004 and 0011).
_Avoid_: query policy, lookup policy (one read among several), retry policy without qualification, transport retry (the failure is anything unanswered, `szlahu_down` included)

**Unanswered**:
The one error of every read fn of the *Gateway* (`lookup`, `lookup_ours`, `verify`, `query`, `hint`, `lookup_storno`, `query_taxpayer`, `probe`): szamlazz.hu produced no answer: a transport or parse failure (`Transport`) or `szlahu_down` (`Unavailable`). The read-side twin of *Unconfirmed*: retryable to the SDK, so the *Read policy* re-executes the step; its exhaustion is the `unavailable` fault. Never a journaled outcome: the `Transport` variants of `LookupOutcome`, `QueryOutcome`, `StornoLookupOutcome` and `ProbeOutcome` are gone, and `TaxpayerOutcome` and `OwnershipOutcome` never had one; another szamlazz.hu code on a read is the data variant `Api{code, message}`, which the handlers that cannot conclude from it answer as `unavailable` without a retry (`Szamlazz.Agent.query` passes it through as `szamlazz_error`, 422; the probe accepts it). Type: `restate_szamlazz::gateway::Unanswered`.
_Avoid_: transport error (one cause of it), unavailable (the fault it becomes on exhaustion), Unconfirmed (the write steps' error; a write's outcome may be unknown, a read's is simply not yet had)

**Lost answer**:
A one-shot write's missing answer, distinct from an inconclusive vendor code (an answer arrived but did not settle the effect); both preserve uncertainty. Protected Order deletion retains its marker for read-only reconciliation or authorized recovery, while unkeyed credit-entry registration reports `outcome_unknown` even on a vendor refusal that cannot settle an earlier interrupted execution: its caller must settle that exact request and exclude delayed execution before renewing, then query and submit only still-required entries or the current intended replacement ([protection by operation](crates/restate-szamlazz/README.md#protection-by-operation)).
_Avoid_: `Transport` as the variant of a one-shot write (one cause, and it hid `szlahu_down`), unknown outcome (the fault is `outcome_unknown`; this is what the step journals before it), Unconfirmed for a one-shot write (nothing re-queries or re-executes), a re-query or a retry of `set_credit_entries` inside the step

**szamlazz.hu answer (`SzamlazzAnswer`) / Rejection code**:
What szamlazz.hu answers with when it answers a code rather than a document, as one type wherever a *Gateway* outcome carries it: `restate_szamlazz::gateway::SzamlazzAnswer { code, message }` in every `CredentialsRejected` and `Api` variant and flattened into `CreateOutcome::DuplicateOrderNumber` (`code`, `message` beside `existing_number`); `From<ApiError>`; `Display` as `{code}: {message}`. The one mapping from a code onto a fault takes one: `service::support::AnsweredCode::{CredentialsRejected, Inconclusive, PassedThrough}(answer).into_fault(namespace)` (the handler's reading of the code, lifted out of the outcome at the site that decides on it; `credentials_rejected` 503, `unavailable` 503, `szamlazz_error` 422), the home of the paging `credentials_rejected` warning: the mapping pages (once, at the site that decides on the code, whether or not the fault is then raised) and the `Fault` constructors are pure (#153); `Fault::szamlazz_error` and `szamlazz_error_on` take one for a `Rejected` that is passed through. A write's `Rejected` variant (`CreateOutcome`, `StornoOutcome`, `DeleteOutcome`, `SetCreditEntriesOutcome`) carries a `Rejection { code: RejectionCode, message }`, whose `RejectionCode::{Szamlazz(String), Request}` tells szamlazz.hu's refusal from the wire contract's before anything was sent (a sixth credit entry, a replacing `set_credit_entries` with no entries, a document without line items); `Request` serialises as the pseudo-code string `request` (`RejectionCode::REQUEST`) and a szamlazz.hu code as itself, so the journaled shape is the one string field it always was, and `set_credit_entries` matches on the enum rather than comparing a string (J-05-04, #128). Both are *Journaled types*' parts, `#[non_exhaustive]`.
_Avoid_: `REQUEST_CODE` (the pre-#128 constant; `RejectionCode::Request` / `RejectionCode::REQUEST`), `code`/`message` as two loose fields on a new variant, "error" for an answer (an answer is data the read journals)

**Storno verdict**:
What a storno handler does next with the document its verify found, decided as data before any send (`service::storno::StornoVerdict`, crate-private): `Proceed` (a live, stornoable document of this order (`Szamlazz.Order.storno_invoice`) or of no order (`Szamlazz.Agent.storno`)), `AlreadyReversed` (`sztornozott` is true, by anyone: the one verdict that needs a further read, the best-effort storno-number hint under the *Read policy*, then `reversed{storno_number?}`), `Answered(response)` (settled without a send: `conflict{not_managed}` for another order's number; on `Szamlazz.Agent.storno`, `managed_by_order` with a supported `order_key`, or `UnsupportedOrderNumber` (`unsupported_order_number`) with the reported string and the failed rule in `message`, asking the operator to reverse in szamlazz.hu and reconcile in the caller's system, never normalise the number or bypass the order guard; `rejected{not_stornoable}` for a `tipus` outside `SZ`/`ES`/`VS`/`HS` on the order's handler). The *Storno invoice* protocol's decision point, written once for both shells (`storno_verdict`, `unmanaged_storno_verdict`) and table-tested.
_Avoid_: storno decision, precheck, a verdict that sends

**Consumed proforma**:
A proforma that szamlazz.hu removed from its query surface because an invoice or prepayment converted it, explicitly by reference or implicitly by shared order number. Derived live in `get`: the proforma is absent under its external id while the invoice or prepayment carries `hivdijbekszam`, reported as `{state: consumed, by}`. Distinct from a deleted proforma, which is simply absent and may be recreated.
_Avoid_: converted (the invoice is converted from it; the proforma is consumed), deleted

**Gateway (`gateway` module) / `Szamlazz.Agent` service**:
The module speaking to szamlazz.hu for one *Account*, opened only for an *Execution*'s actual external operations; `Szamlazz.Agent` is its unkeyed, concurrent Restate facade for by-number operations, taxpayer lookup and account checking. Direct create consumers explicitly grant one consumed permission and own durable exclusion, uncertainty retention and settlement; the public API and transport responsibilities are in [the Gateway contract](crates/restate-szamlazz/README.md#gateway-and-services), while Order owns the protected protocol.
Expert custom orchestrators are an explicitly supported consumer by ADR 0014 (2026-09-12), accepting caller-owned durability; public visibility and the historical embedder hook did not by themselves establish that decision. Ordinary applications use protected Order.
_Avoid_: steps (for the module, the pre-rename name), client (for the module; it is not a second client), session (for the module; the szamlazz.hu cookie is what its fresh client isolates), "the agent" without qualification, Invoice service, Document service / `Szamlazz.Document` (considered and not built)

**Reconciliation evidence**:
Read-only evidence for retained issuance or reversal intent, shared by expert Gateway orchestrators and protected Order recovery. Matching issuance must differ from the expected old reissue target and name the intended corrective base when applicable; it may since have been reversed. Reversal requires both the matching storno and a freshly queried, matching reversed original. An exact candidate is not silently replaced. Absence, collision, blocked verification and unanswered reads preserve uncertainty; document queries cannot establish deletion. Positive evidence settles neither the caller's durable record nor permission for a new write by itself. Decision: ADR 0014.
_Avoid_: ownership alone as completion evidence, absence as non-execution, reconciliation as write retry, operator attestation as queried evidence

**Malformed body**:
A request body rejected by the closed worker contract: unknown fields, wrong or missing values, invalid JSON or a bounded value outside its rules. It yields structured `invalid_input` before the prologue or any send; response objects remain open to added fields ([worker contract](crates/restate-szamlazz/README.md#contract)).
_Avoid_: invalid payload (the SDK's word), decode error (one cause), unknown field (one cause), bad request (the HTTP class)

**Prologue**:
The common beginning of a handler after body and key validation: pin the deployment's *Namespace* and resolve the request's *Scope* to its journaled *Account*. The Account is available for deterministic decisions. Credential acquisition and Gateway initialization belong to an executing external operation, not to the Prologue: replaying completed operations needs neither. Decision: #200; design §4.
_Avoid_: preamble, setup, middleware (there is no interception layer; it is the first lines of every handler), init

**check_account (`Szamlazz.Agent.check_account`)**:
The read-only probe for onboarding and deploy pipelines, and the deploy-time canary for the experimental Restate flags: the *Prologue* like every handler, then one durable step (`probe`) under the *Read policy* (a query of the sentinel external id `{namespace}:check-account`, which nothing the service issues carries, expecting "not found"), answering the *Scope* the SDK saw, the *configured* account (`id`), the *Namespace* and whether szamlazz.hu accepted the credentials: `{state: ok}`, or `{state: rejected, code, message}` on 3/135/136/164 **as data, not a fault**. `CredentialsCheck::Other { state, fields }` preserves a newer state and its payload without inferring acceptance; `KNOWN` lists the known state tokens. `scope: null` under a scoped call means the server did not forward the scope (`protocol_v7` off; the ingress does not refuse a scoped path for it); the probe is the only defence against that case, since the worker has no per-request signal of "was this call scoped?" it is willing to depend on (an ingress-path guard on the undocumented, caller-overridable `x-restate-ingress-path` header was considered and dropped). Credential acceptance is its only szamlazz.hu-verified fact. The separate go-live seller check is executable `examples/verify_seller.rs`, using the actual deployed `Accounts` resolver/store and a fresh Számla Agent client per scope to compare a known document's `test` and *Seller block* with independent expectations outside the journal; `Szamlazz.Agent.query` deliberately omits that block. Issues nothing; no input; explicit `journal_retention` so the leak assertion can scan it. Called under each configured scope after a deploy, it proves the scope reaches the worker, resolves to the configured account and its key works; it cannot detect fan-in: it only echoes configuration. An exchange that produced no answer is *Unanswered*, retried; exhaustion is `unavailable`. Gateway fn: `Gateway::probe` → `Result<ProbeOutcome, Unanswered>`; response type `contract::CheckAccountResponse`.
_Avoid_: health check (it checks one account under one scope, not the process), login test, ping

**Taxpayer lookup (`Szamlazz.Agent.query_taxpayer`)**:
The NAV taxpayer query (`xmltaxpayer`) on the *Account* the request's *Scope* resolves to: the *Prologue* like every handler, then one durable step (`lookup-taxpayer-{prefix}`) under the *Read policy*, answering NAV's record of the taxpayer (`valid`, `name`, `tax_number`, `vat_code`, `addresses[]`) **as data**: `valid: false` (NAV knows no taxpayer under the prefix) is a normal 200, never `not_found`. In the worker because it is a per-account read that needs the account's agent key, and the worker is the one place a multi-account deployment holds one (ADR 0006); the one `Szamlazz.Agent` handler that is about no document. The request is `{tax_number}` in exactly two forms: the bare eight-digit stem (`12345678`) or the full `NNNNNNNN-N-NN` (`12345678-2-42`); the handler derives the **prefix** (törzsszám, `TaxpayerPrefix`) and anything else is `invalid_input` before the *Prologue*, like a *Malformed body*. The step is named by the prefix, not the number as sent, so the stem and the full number are one entry. Every `funcCode ≠ OK` (szamlazz.hu's own code or NAV's relayed `errorCode`) is an *answer*, passed through as `szamlazz_error` (422, the code in `szamlazz_code`) and never retried (a NAV outage is a terminal 422 the caller retries with a new `Idempotency-Key`); a credential code is `credentials_rejected`; an exchange with no answer is *Unanswered*, `unavailable` on exhaustion. Finds no document. Journals the crate-owned projection `TaxpayerOutcome::Found(QueryTaxpayerResponse)`, never the agent crate's `TaxpayerInfo`. Not cached by the worker (ADR 0005); the caller caches, with a TTL on the order of a day. Gateway fn: `Gateway::query_taxpayer` → `Result<TaxpayerOutcome, Unanswered>`; contract: `QueryTaxpayerRequest` / `QueryTaxpayerResponse` (`TaxpayerAddress`). Decision: #49.
_Avoid_: tax number validation (it is NAV's answer, not a format check; the format check is the `invalid_input` refusal), VIES / EU VAT lookup (a different register), taxpayer status (`adóalany`, the buyer field on a document), taxpayer query as a non-goal (the pre-#49 README line)

**Execution**:
One handler execution, including replay of earlier completed operations and any newly executed operations. It uses the journaled *Account* and pinned *Namespace*. Its first external operation that actually executes acquires credentials and opens a fresh *Gateway*, reused only within this execution. An execution that only replays completed operations needs no credentials or client. No Gateway, client or credentials outlive the execution. Its logs are attributed to the scope, order, Restate invocation and resolved account (#65, #200).
_Avoid_: attempt (for the handler; the SDK's word for a run retry is also "attempt", and neither is journaled), session (the szamlazz.hu cookie), context (the SDK's `ctx`), handler span or prologue span (the span is the execution's; it outlives the prologue), the account id in a response (the span and the log carry it; no response does)

**Resolve policy**:
The deployment's run retry policy for resolving the request's *Account* in the *Prologue*. Duration is the sole exhaustion threshold by default; an execution-count threshold may also be set. Both can overshoot and neither interrupts a hung resolver call; that call has a separate deadline. Configuration and defaults are in design §9. Decision: ADR 0004 (#204 amendment).
_Avoid_: retry policy without qualification, account policy

**Retry policy config**:
The common configuration vocabulary of the deployment's *Issue policy*, *Read policy* and *Resolve policy*: execution-count and duration exhaustion thresholds, initial delay, delay multiplier and maximum delay. Duration is the sole exhaustion threshold when the count is unset. Thresholds govern retry exhaustion, not hard elapsed time or external-send counts; a one-shot policy suppresses deliberate retries but cannot prevent crash-driven re-execution before completion is recorded. The three policies share one configuration shape with different defaults (design §9; #128, #184, #204).
_Avoid_: three policy structs (the pre-#128 shape), a `[resolve]` without `max_attempts` (it has the key; the default is unset), policy without qualification, `config::Policy` (the pre-#184 enum; the table types are the enumeration)

**Validated worker config**:
`restate_szamlazz::config::ValidatedWorkerConfig`, the newtype `WorkerConfig::validate` yields (the one constructor a deployment has) and what `Order::from_parts` / `Agent::from_parts` take, so a service cannot be built over an issue policy below its floor; dereferences to the `WorkerConfig`. `ValidatedWorkerConfig::unchecked` wraps without checking, behind the `test-util` cargo feature the e2e harness enables for its one-second policies (sized for a scripted mock) and a deployment never does (#128). A deployment validates where it loads its configuration; the e2e's `worker_config()` is the only `unchecked` caller.
_Avoid_: `worker.validate()?;` as a statement whose result is dropped (the pre-#128 wiring; `validate` consumes and returns), a bypass constructor without the feature

**Journaled type**:
A crate-owned result recorded for replay within an invocation: the namespace, account resolution or an external-operation outcome. Document results carry only the *Found document* and *Issued document* projections, never credentials or unneeded document content. There is no general cross-release compatibility contract: normal immutable-deployment routing keeps replay on its original code. *Exceptional replay* requires reviewing the particular journal against the candidate code. A privacy invariant is distinct from a compatibility guarantee. Decision: ADR 0009 (including #204; superseding ADR 0005's journal-compatibility amendments).
_Avoid_: run result (the SDK's word; the type is what matters), additive-only / fixture / pin / archive rule (the pre-ADR-0009 contract; gone), `Journaled` as a compatibility marker, journal as Order state (the unresolved-write marker is separate), an agent response type "as it is" in an outcome, `InvoiceDocumentExt` (gone; the checks are `FoundDocument`'s methods)

**Found document / Issued document**:
The worker's projections of a szamlazz.hu document, the types the document outcomes journal (`restate_szamlazz::gateway::document`, #127). A **found document** (`FoundDocument`, `From<InvoiceDocument>`) is what the handlers read off a queried `<szamla>` and nothing else: `document_id` (`alap/id`), `number`, `document_type` (`tipus`, the agent crate's open *Document type*, journaled as its token), `order_number` (`rendelesszam` trimmed, an empty or whitespace-only element read as `None`: the one reading of the element, made once, in the projection; what `carries_order` compares with the *Order* key and what `Szamlazz.Agent.storno` answers as `managed_by_order`'s or `unsupported_order_number`'s `order_key`), `reversed` (`sztornozott`), `referenced_invoice_number` (`hivszamlaszam`), `referenced_proforma_number` (`hivdijbekszam`), `appearance` (the `eszamla` integer code; `e_invoice()` reads it through the agent crate's `InvoiceAppearance`, so a code the crate learns later is read on replay), `issue_date` (`kelt`), `fulfillment_date` (`telj`), `due_date` (`fizh`), `currency`, `test` (`teszt`, carried, compared with nothing), the grand total (`net_total`, `vat_total`, `gross_total`) and `credit_entries` (the worker's `RecordedCreditEntry`, projected from the agent crate's: date, title as the payment method's wire token, amount, comment, bank account); `document_id` is read by no handler and carried for correlation with szamlazz.hu's records. Not the *External id*: szamlazz.hu never echoes `szamlaKulsoAzon`, and the handler holds it from the key. The checks the services make before trusting or acting on a document are its methods: `is_live`, `is_ours(order, kind)`, `carries_order`, `is_storno_of`, `is_invoice_family`, `is_stornoable`, `e_invoice`, `credit_entry_amounts`. `Szamlazz.Agent.query`'s `QueryResponse` is projected from it and carries no seller block. An **issued document** (`IssuedDocument`) is what they read off a create reply or a storno reply, `From<CreatedInvoice>`, the agent crate's numbered document: a create answers a `CreationOutcome`, and only its `Issued(CreatedInvoice)` arm is a document (the `Preview` arm, which the worker never asks for, is a reply without a number, and the *Create step* re-queries): `number`, `document_id`, `net_total`, `gross_total`, `outstanding`, `customer_account_url`, `notification_delivery_failed`; never the PDF. Both are made at the *Gateway*'s wire boundary (`query_raw`, the create and storno sends); nothing past it holds an agent response type. `#[non_exhaustive]`, constructed in tests through the wire (`test_support::Doc` (defined in `tests/common/mod.rs`, included by path) renders the `<szamla>` XML, parses it through the agent crate and projects it), never as literals.
_Avoid_: `InvoiceDocument` for what a handler holds (the agent's type; the gateway projects it at the boundary), `InvoiceDocumentExt` (the pre-#127 trait), `Unnumbered` / `TryFrom<InvoiceCreationResult>` (the pre-0.4 shape; the agent crate's `CreationOutcome` carries the case), a document "as it is" / "whole" in the journal, the raw `rendelesszam` (the projection carries the reading), `eszamla` as a flag on the projection (it is the code; `e_invoice()` is the flag)

**Step-name table**:
The ordered step-name patterns of every handler path, checked against observed journals and the deployed handler set, with every path walked in full. A regression signal for changed sequences, not proof of *Exceptional replay* compatibility: allowed patterns do not establish that a particular old invocation takes the same branch or emits the same exact commands. Review its actual prefix, branch logic, serialization and inputs as well. The table and its check are described in design §11. Decision: #66, ADR 0009 (#204 amendment).
_Avoid_: run-name pin, journal snapshot, a journal compatibility contract, the table's diff as proof of replay compatibility, allowed path patterns as proof of an old invocation's branch

**Shared observation (`get`)**:
What szamlazz.hu reports for the order's four external ids, observed alongside exclusive writes. A non-atomic observation: its separately journaled reads can mix observation times and replay ages. Each new poll needs a fresh invocation/key; reusing a retained *Idempotency-Key* may replay a completed answer, and unspecified discovery retention does not disable deduplication. Absence does not establish that an in-flight create will never land. Native attach/output answers whether a particular invocation completed; `get` answers what the external service reports. Decision: ADR 0005 (#204 amendment).
_Avoid_: snapshot, completion barrier, "right now", "never stale", "nothing to replay"

**Exceptional replay**:
Operator-selected replay outside normal immutable-deployment routing: a deployment-changing resume or a restart from a retained journal prefix. Requires reviewing the actual invocation prefix, branch logic, exact commands, serialization and inputs against the candidate code, plus reconciling external effects that a restart may repeat. Deployment defaults are version-specific; ADR 0009's #204 amendment records the source-verified server 1.7.8 behavior. Keeping code available is distinct from result or journal retention.
_Avoid_: resume as the only exceptional replay path, protocol compatibility as application compatibility, kill/restart as rollback

**Quiesced producers**:
Callers stopped from admitting further work during a mapping flag day, including internal SDK callers and pending delayed sends. A private service blocks ingress calls but still accepts internal calls. Stopping a delayed send's originator does not remove the detached send. The private → drain → switch shorthand assumes ingress-only producers with no pending delayed sends; otherwise quiescing them precedes and spans that procedure. Decision: ADR 0006 (#204 amendment).
_Avoid_: service privacy as a global producer stop

**Execution timeouts**:
Inactivity timeout waits for progress before requesting SDK suspension; abort timeout starts after that request and bounds the subsequent wait before forced abort. Distinct from per-call deadlines, run exhaustion thresholds and terminal invocation kill; none implies external rollback. Decision: ADR 0004 (#204 amendment).
_Avoid_: inactivity and abort as concurrent timers starting with the external call

**Step name**:
The name of one `ctx.run` as the Restate UI, `sys_journal` and the *Step-name table* show it: kebab-case, `{verb}-{object}[-{parameter}]`, the verb being the *Gateway*'s question, not the handler's purpose: `lookup-{kind}` is every *Ownership lookup* of one of the order's external ids (the *Lookup step*, the exclusivity checks, the proforma link, `create_final`'s prepayment, `delete_proforma`'s proforma, `get`'s four reads: the table says which handler journals it where), `lookup-storno-{number}` and `lookup-taxpayer-{prefix}` the other lookups, `verify-original-{number}` a storno shell's read of its original by number (one name on both `Szamlazz.Order.storno_invoice` and `Szamlazz.Agent.storno`), `verify-base-{number}` / `verify-proforma-{number}` the other verifies, `hint-storno-{number}` the best-effort read, `create-{kind}` / `storno-{number}` / `delete-proforma-{number}` / `set-credit-entries-{number}` the writes, and a bare noun where the step is the handler's one read of that thing (`namespace`, `account`, `probe`, `query`). A `{number}` / `{prefix}` parameter is bounded (the *Invoice number*, the `TaxpayerPrefix`) so the name is, and is read by its prefix, so no fixed name may begin with a parametrized prefix (the harness's `RunPatterns::of` refuses one). Renaming a step reshapes the journal a *pause and resume on a new deployment* replays, so a rename is a breaking release; the 0.3 names `exclusivity-{kind}`, `proforma-link`, `prepayment-for-final`, `proforma-for-delete`, `get-{kind}`, `verify-storno-{number}`, `verify-{number}`, `taxpayer-{prefix}` and `set-payments-{number}` went in the Restate-conventions review (2026-09-09).
_Avoid_: a step named for the handler's purpose (`exclusivity-…`, `proforma-link`: the 0.3 names; the verb is the read), `{object}-for-{purpose}`, two names for one read, a fixed name under a parametrized prefix

**Restate e2e harness (`restate-e2e-harness`)**:
First-release completion boundary: end successful tests with `Restate::finish().await`, which requests shutdown of all local endpoints together, joins serving/connection/SDK handler tasks, and fails on recorded task panics even if Restate retried successfully. `finish_with_failures` returns plain `EndpointFailure { uri, message }` rows for tests deliberately asserting expected panics. Forced cancellation at the drain deadline is expected; external effects and independently spawned application tasks remain outside this boundary. Drop is best-effort cleanup, not a task-failure assertion. Incomplete startup (including timeout/task abortion), cancelled finish, and endpoint failures retain an owned server's diagnostic directory. Admin observation helpers expose per-call `_with_timeout` variants: 30-second defaults for status/in-flight/pause/purge, 60 seconds for drain/register; pause and purge start observation after their initiating PATCH, whose HTTP timeout is separate.

First-release hardening (2026-09-10): the allowed dependencies below also include `rustix` for safe non-reaping exit inspection on Linux and macOS, and `hyper` / `hyper-util` for managed HTTP/2 serving over the SDK's `HyperEndpoint`. A local endpoint's lifetime belongs to its `Restate` handle, including when the server is reused; dropping the handle requests shutdown of all its endpoints. `Deployment` remains a plain URI/port descriptor, so discarding one leaves the endpoint available for replay and redeployment tests. The runtime executes shutdown: connections drain for ten seconds, then remaining connection and SDK handler tasks are cancelled and joined. SDK 0.12's `HttpServer` detaches both kinds of tasks and its timeout only stops waiting, so the harness owns them through its private server module. Drop is not a synchronous completion barrier; independently spawned application tasks and external effects are not cancelled. Readiness shares one 90-second deadline across health, SQL and version, inspecting the owned child during probes and after successful answers. `Table::pattern(service, handler, name)` and `Table::check` match patterns within each handler; missing journal map entries fail as `Violations::missing_journals`, earning no coverage. An explicitly supplied empty journal remains an empty sequence.

The external crate ([crates.io](https://crates.io/crates/restate-e2e-harness), [upstream repository](https://github.com/sagikazarmark/restate-e2e-harness), versioned on its own from 0.1.0, unix only) that is the Restate half of an end-to-end suite for any `restate_sdk` endpoint. `restate-szamlazz` takes it as a crates.io dev-dependency; the local `crates/restate-e2e-harness` copy was removed after publication. It provides the *Server gate* and launcher (`Launcher::launch(&ServerSpec)`), the spawned `Restate` handle, repeatable in-process deployment (`Restate::deploy(Endpoint) -> Deployment`), `set_public` and `drain`, ingress (`Call`, `Restate::invoke`, `Reply::fault::<F>()`), the admin API (`Admin`: SQL, journals, invocations, handlers, kill / cancel / purge and observation helpers), the `Watch` sampler, introspection rows and the *Step-name table*'s `Table::check`. No ingress path string is built outside the crate (#179). Its row and result types are **plain data** (public fields, nothing `#[non_exhaustive]`; added fields are breaking changes, #189). Its loopback HTTP client is crate-private; the szamlazz suite builds its gateway client over `szamlazz_agent::reqwest` (#136, #179). The crate knows no szamlazz type and never depends on `restate-szamlazz`: a dependency back would create a dev-dependency cycle and duplicate types. **Server gate**:
How an e2e suite gets its Restate server, decided once from the environment before anything starts (`server_gate` in the *Restate e2e harness* crate's `gate` module, a pure function under its own tests), in this order: `RESTATE_ADMIN_URL` / `RESTATE_INGRESS_URL` reuse a running server (the szamlazz main suite only, which expects the three experimental features on; the protocol-v7 canary needs a server of its own shape and never reuses; `compose.yaml` starts one); `RESTATE_SERVER_BIN` names a `restate-server` binary the harness **spawns** on the loopback, one process per suite, leading a process group of its own, configured through Restate's `RESTATE_*` environment, its log and data under an exclusively owned temp directory. Each launch starts with fresh storage independently of port reuse; an existing directory is never adopted, its evidence never overwritten or deleted by another launch. Failed launches and panic teardown retain their own log and data for inspection; normal teardown removes only that launch's directory (#210). This is what CI uses, since the Dagger container has no docker daemon and a Dagger service cannot reach back into the container that binds it; the Dagger check prints the kept log when the suite fails, since the container is discarded; a developer gets the same binary with `dagger call ci restate-server export --path ./restate-server`. `RESTATE_ENDPOINT_HOST` overrides the endpoint host in either mode. **No port is fixed** (#123): a spawned server's ports are chosen free at launch, a listener on port 0 per port (bound, read, released, passed through `RESTATE_*`), so two runs on one host collide with nothing; a port taken between the choice and the bind shows as the server failing to start, reported at once naming the ports rather than waited on. A `ServerSpec` names the shape (a name, one path component of `[a-z0-9-]` since the base dir is removed recursively on drop, checked before any spawn; the experimental `Feature`s it needs, each on or off (`features: &[(Feature, bool)]`; `VQUEUES`, `PROTOCOL_V7`, `SCOPED_VIRTUAL_OBJECTS`), set on the spawned server and checked against `/version` at launch for a spawned and a reused server alike, a feature not listed neither set nor checked, so a Restate release turning one on by default breaks nothing; and any other `NAME=value` environment, #189), and `RESTATE_ENDPOINT_HOST` is read by `launcher_or_skip` with the other variables, so `server_gate` and `Launcher::launch` are functions of what it read. The in-process endpoint is bound to the loopback when the server reaches it there (a spawned server, no override) and to every interface otherwise (a reused server may be a container reaching back to the host). A server the harness started is stopped when the handle drops (the group killed) and by the harness's own SIGINT/SIGTERM handler, since a signal runs no `Drop`. With neither source the suite **skips** with a message on a developer machine and **fails** when `CI` is set: a run that passed by skipping proves nothing. The docker launcher (a container of the Restate image, named per run and labelled with the pid, stale ones removed by the next run) is gone (#167): CI never used it, and with it went the container naming, the label/pid scheme, the `docker port` read-back and the `docker info` probe. Decision: #66, #123, #167, #210.
_Avoid_: docker-gated (the pre-#66 shape), a docker launcher as a third source (gone with #167), skip in CI, testcontainers (the harness drives `restate-server` itself), Drop-only cleanup and fixed host ports (18080/19070, the pre-#123 shape), a stale container found by name or label (there are no containers)
