## Executive conclusion

**The crate implements all eleven documented Számla Agent operations, with strong field coverage. No missing documented operation or required business-data capability was established.** The previously reviewed major field, parsing and error-catalogue gaps are repaired in this revision.

There is **one confirmed P2 arithmetic-contract defect**, affecting unusual Decimal precision boundaries. Four P3 runtime hardening/evidence-preservation findings and six P3 documentation/evidence clarifications remain. None of these establishes a live-account incident. No P0/P1 finding was established.

The request writers and conforming-response readers otherwise match the reviewed official definitions, subject to the explicitly identified vendor-source conflicts and supported live deviations below. This is evidence-backed review coverage, **not certification that every combination works on the deployed vendor service**.

This consolidated report is the final adjudication. Where a specialist report's priority or remedy differs, use this report—particularly F3, F5 and D6.

### F1 — Decimal checks do not guarantee exact arithmetic

**Code:** [`item.rs:189–212`](../../crates/szamlazz-agent/src/item.rs#L189); advertised contract at lines 11–30 and 163–180. **Confidence: high**, reproduced independently by two reviewers.

The official [rounding rules](https://docs.szamlazz.hu/agent/generating_invoice/settings_and_rules/rounding) say to multiply price by quantity and then round. The crate additionally promises an explicit local rounding policy and errors when a value cannot fit. However, `checked_mul`, `checked_div` and `checked_add` can reduce precision while returning `Some`; the subsequent rounding acts on the altered intermediate.

```rust
use rust_decimal::dec;
use szamlazz_agent::{LineItem, Rounding, VatRate};

let item = LineItem::try_calculated(
    "boundary", dec!(0.9999999999999999999999999999), "db",
    dec!(0.005), VatRate::Aam, Rounding::Scale(2),
).unwrap();
// Current net_value: 0.01.
// Exact product: 0.0049999999999999999999999999995.
// Half-away-from-zero at scale 2: 0.00.
```

Also reproduced: `1e-28 × 0.1` returns zero under `Exact`, and gross addition can lose a fractional component without error. These are unusual precision-boundary inputs, not evidence that ordinary invoice amounts are routinely wrong. Server-side rounding and live-observed tolerance cannot explain a pre-wire contract violation.

**Fix boundary:** loss-aware net, VAT and gross arithmetic. Conservative rejection is sufficient; arbitrary precision is not mandatory. Update error wording if “overflow” variants also represent precision loss/underflow. Keep explicit caller-supplied `LineItem::new` values available. [Full evidence and controls](2026-09-10-agent-api-invoices.md#inv-01--medium-checked-decimal-arithmetic-can-silently-round-before-the-selected-rounding-policy).

### F2 — Preserve a known refusal when optional payload parsing fails

**Code:** [`envelope.rs:188–200`](../../crates/szamlazz-agent/src/ops/envelope.rs#L188), lines 203–242 and 272–278. **Confidence: high in reproduction; live occurrence unobserved.**

Given headers `szlahu_error_code: 56` and `szlahu_szamlaszam: I-2`, a complete XML envelope containing `sikeres=false`, `hibakod=3`, and `<szamlabrutto><bad/></szamlabrutto>` returns successful `CreatedInvoice`. Omitting that amount, or using ordinary malformed numeric text, correctly preserves the body refusal. Duplicate amount elements also reproduce the erroneous success.

The [create](https://docs.szamlazz.hu/agent/generating_invoice/response) and [storno](https://docs.szamlazz.hu/agent/reversing_invoice/response) pages define the false/code/message verdict. They do not define contradictory-channel precedence. This finding concerns the crate's inconsistent handling of its own readable-refusal policy, **not a proven failure on a conforming vendor reply**.

**Fix boundary:** retain the verdict independently from optional payload deserialization. Preserve the specific first-party-PHP-backed numbered-56 behavior, whole-document checks and supported non-XML notification-failure fallback. [Reproduction and exact source evidence](2026-09-10-agent-api-mutations.md#m1--optional-payload-deserialization-can-erase-a-readable-body-refusal-under-header-code-56).

### F3 — Retain received headers on incomplete transfers

**Code:** [`client.rs:315–330`](../../crates/szamlazz-agent/src/client.rs#L315), especially line 326. **Confidence: high behavior / medium API remedy.**

A loopback server returning a complete header section but closing before its declared body length causes `response.bytes().await?` to discard the collected headers. Both code 3 and numbered 56 become only `Transport` / `Unknown`; callers cannot inspect the received number or refusal.

The [documented headers](https://docs.szamlazz.hu/agent/generating_invoice/response) are useful reconciliation evidence. Nevertheless, **the existing uncertainty classification is correct**. This is a P3 evidence-preservation limitation, downgraded from the specialist's P2 proposal.

**Fix boundary:** expose received status/headers with the transfer cause and an explicit incomplete-body condition. Do not substitute an empty body and invoke the normal parser; an unseen body could contain a contradictory refusal. Do not promote a numbered header to unconditional success. [Loopback reproduction](2026-09-10-agent-api-transport.md#r1--preserve-received-evidence-when-response-body-transfer-fails).

### F4 — Redact credentials embedded in custom endpoint URLs

**Code:** [`client.rs:104–110`](../../crates/szamlazz-agent/src/client.rs#L104), lines 180–213 and 272–276. **Confidence: high; conditional on caller-supplied userinfo.**

`https://alice:URL_PASSWORD@example.test/szamla/` is accepted and the password appears in derived Debug output. Normal XML agent-key redaction works. This affects custom endpoint diagnostics, not normal default-endpoint users or remotely supplied invoice data.

The [authentication contract](https://docs.szamlazz.hu/agent/basics/authentication) uses XML credentials and requires secret treatment. Accepting URL userinfo is not itself an API violation. Prefer diagnostic redaction; rejecting userinfo is a separate capability decision and still requires protecting builder and rejected-input output. [Evidence](2026-09-10-agent-api-transport.md#r2--endpoint-credentials-bypass-debug-redaction).

### F5 — Close the diagnostic-bound gap and narrow the logging promise

**Code:** [`xml.rs:132–134`](../../crates/szamlazz-agent/src/xml.rs#L132), [`error.rs:595–692`](../../crates/szamlazz-agent/src/error.rs#L595), [`README.md:349`](../../crates/szamlazz-agent/README.md#L349). **Confidence: high**, independently reproduced during adjudication.

- A 23,000-character unexpected root name produces a **23,394-character `UnexpectedBody` display**: the root is interpolated before the bounded body excerpt.
- A 23,000-character vendor error message produces a 23,021-character API display; an invalid boolean containing that text produces a 23,036-character parser display.

Thus both the wrong-root path's bounded-diagnostic promise and the README's general “can be logged as is” guidance need correction. The [vendor error guidance](https://docs.szamlazz.hu/agent/basics/error-handling) permits lengthy diagnostic content; it supplies no universal message bound.

**Fix boundary:** bound or omit the upstream root-name fragment. Preserve verbatim `ApiError.message` data, but explicitly qualify display/logging guarantees for parser messages, API messages and ordinary response headers. Merely saying “UnexpectedBody is bounded” remains false until the root fragment is fixed. This folds the adjudicator's additional reproduction into [transport D1](2026-09-10-agent-api-transport.md#d1--limit-the-bounded-error-display-promise-to-the-paths-that-enforce-it), rather than counting it twice.

## 4. Preserve supported deviations

These remain justified; forcing a single older schema/example on them would regress useful behavior:

- **External ids:** non-unique; newest holder returned; id attaches on actual creation, not a replay; no server idempotency guarantee.
- **Invoice storno:** repeated reversal can echo the existing SS; proforma/delivery-note storno can be a success-shaped no-op. Missing/positive gross is not proof that no reversal happened.
- **Dates and appearance:** observed issue-date substitution, storno fulfillment handling and request-selected appearance remain qualified account evidence. Queried `eszamla=1` is paper.
- **Sparse and body-only responses:** optional totals/metadata, header-free successes and HTTP-200 body-only errors remain supported. No universal strict-XSD response gate is recommended.
- **Monetary behavior:** preserve observed comma headers, explicit caller amounts, server tolerance and independent invoice storage rounding. Receipt rules remain separate from invoice observations.
- **Newer inline fields over stale downloads:** retain buyer group id, erasure-code fields and receipt order selectors supported by current pages/first-party code.
- **Numbered 56:** preserve the specific first-party implementation rule. Its provenance is PHP/documentation, not a successful live probe.
- **Receipt email:** absent details on `SendReceipt` must still emit a present-empty `emailKuldes`; omission of the block means a different operation effect.
