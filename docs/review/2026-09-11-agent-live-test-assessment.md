# Számla Agent live-test assessment — 2026-09-11

## Recommendation

**Keep the three current core scenarios. Improve the existing invoice journey rather than build a larger live matrix. Keep most probes outside release acceptance; make the receipt lifecycle a separately selectable acceptance journey when receipts are used.** The suite is already small and mostly asserts persisted business facts, rather than merely logging successful calls.

The highest-value addition is **one standalone `QueryInvoicePdf` call on the existing invoice**, with number and PDF-signature assertions. It is part of the README's main-use example but is absent from every current agent live/probe scenario. Next, fold populated credit-entry clearing into that invoice's existing credit-entry sequence if clearing is a supported use being released. Neither requires another invoice. Preserve repeated storno, explicit previous-month fulfillment, replacement/additive semantics, and proforma absence checks: mocks cannot confirm these vendor behaviors.

This is a source assessment of working-tree HEAD `28dcec1456cc08d50089ed8f9c9d15f877c7c3d2`, not a new execution record. No tests were run, no credentials or `.env` contents were read, and no code was changed. Existing dirty files were treated as user work. Scope is the agent crate, its checked-in vendor corpus and behavior/probe records, and relevant test wiring; Restate scenarios are not independently reviewed here. `CONTEXT.md` supplied the vocabulary; no additional `AGENTS.md` or `CLAUDE.md` was found. ### Gating, failure behavior and CI

- **Opt-in has two layers:** the transport feature and `#[ignore]`. Default crate features are empty ([Cargo.toml:14–17](../../crates/szamlazz-agent/Cargo.toml#L14-L17)); every scenario above is ignored. Credentials alone enable nothing. Selecting the ignored target without transport executes its panicking sentinel. A missing/blank key panics instead of skipping ([support:31–36](../../crates/szamlazz-agent/tests/live_support/mod.rs#L31-L36)). No helper loads a credential file.
- `cargo live` means **workspace** live acceptance, not agent-only: the alias supplies all features and ignored-only, and the profile selects both agent and worker live binaries. The documented five total core cases include only **three agent cases** ([.cargo/config.toml:1–5](../../.cargo/config.toml#L1-L5), [.config/nextest.toml:21–43](../../.config/nextest.toml#L21-L43), [testing.md:21–29](../testing.md#L21-L29)). An agent-only run can use the documented package filter pattern; no new runner is necessary ([testing.md:173–178](../testing.md#L173-L178)).
- Live/probe nextest profiles are serial, fail-fast, **zero whole-test retries**, with immediate output and successful-output JUnit retention. Their 60-second slow timers have no terminate-after setting. This is per-runner serialization, not an account-wide lock ([nextest.toml:21–43](../../.config/nextest.toml#L21-L43), [testing.md:189–196](../testing.md#L189-L196)). Plain Cargo does not acquire those profile policies; the documented fallback supplies `--test-threads=1` explicitly.
- The default native client uses a fresh cookie jar, a one-minute per-request timeout, and no redirects; `Client::send` performs checked wire generation and a POST, then parses the response, without an application-level recovery loop ([client.rs:280–308](../../crates/szamlazz-agent/src/client.rs#L280-L308), [374–405](../../crates/szamlazz-agent/src/client.rs#L374-L405)). Core tests exercise production default client construction that the local HTTP mocks deliberately bypass ([tests/client.rs:18–37](../../crates/szamlazz-agent/tests/client.rs#L18-L37)).
- Ordinary nextest excludes live/probes. GitHub PR/main CI invokes `dagger check`; Dagger's automatic test/schema functions are `@check`, while `live` is manual and has no such annotation ([nextest.toml:5–11](../../.config/nextest.toml#L5-L11), [.github/workflows/dagger.yaml:3–20](../../.github/workflows/dagger.yaml#L3-L20), [.dagger/modules/ci/main.dang:39–58](../../.dagger/modules/ci/main.dang#L39-L58), [134–159](../../.dagger/modules/ci/main.dang#L134-L159)).
- Dagger live injects a Secret and a required nonempty run label after compilation. A fresh label is needed to invalidate external-execution caching; UUIDs distinguish newly executed scenarios but cannot prove an execution happened when Dagger returned a cached result. Failure scripting preserves the exit status and prints available JUnit/kept server logs ([main.dang:94–122](../../.dagger/modules/ci/main.dang#L94-L122), [141–158](../../.dagger/modules/ci/main.dang#L141-L158), [testing.md:276–299](../testing.md#L276-L299)).
- **Selection mismatch worth simplifying later:** Dagger `probes: true` runs all seven and demands receipt prefix/email, while the guide advises choosing an experiment. Use existing local filters for rare investigations; adding more default probes would worsen this mismatch ([main.dang:141–157](../../.dagger/modules/ci/main.dang#L141-L157), [testing.md:218–234,297–299](../testing.md#L218-L299)). Receipt settings are nonblank checks, not complete prefix/inbox validation ([receipts.rs:23–43](../../crates/szamlazz-agent/tests/probes/receipts.rs#L23-L43), [268–271](../../crates/szamlazz-agent/tests/probes/receipts.rs#L268-L271)).

### Cleanup is substantive, but not rollback

`Run` logs a fresh UUID order and write intent before sends and records returned invoice numbers. A direct known rejection clears uncertainty; other write errors panic with the intent retained. Successful storno stays unresolved until the returned number is queried and verified as a distinct SS referring to the original ([support:73–173](../../crates/szamlazz-agent/tests/live_support/mod.rs#L73-L173), [268–295](../../crates/szamlazz-agent/tests/live_support/mod.rs#L268-L295)).

Lifecycles catch assertion panics, then clean known documents last-created-first. Any unresolved intent defers mutation cleanup. Query/delete/storno failures stop dependent cleanup; cleanup failure fails an otherwise successful scenario, and an original panic is rethrown after diagnostics ([support:188–265](../../crates/szamlazz-agent/tests/live_support/mod.rs#L188-L265)). This behavior should be retained.

The invoice cleanup helper verifies the SS but does **not** reread the original's reversal marker afterward; the core scenario explicitly does. Receipt cleanup verifies both SS-equivalent SN relationships and the original marker ([live.rs:105–120](../../crates/szamlazz-agent/tests/live.rs#L105-L120), [receipts.rs:115–173](../../crates/szamlazz-agent/tests/probes/receipts.rs#L115-L173)). Invoice cleanup deletion trusts the acknowledgement; core proforma deletion additionally checks absence. A process abort cannot run this async cleanup. `test=true` is checked **after issuance**, not a pre-send test-account gate ([support:120–131,310–314](../../crates/szamlazz-agent/tests/live_support/mod.rs#L120-L314), [testing.md:159–163,307–318](../testing.md#L307-L318)).

**Strongest:** the invoice credit-entry sequence and queried reversal; proforma absence; receipt lifecycle identity and relationship checks. ## 4. Prioritized minimal-suite proposal

### P1 — keep the core at three tests; improve its existing observations

1. **Invoice journey:** retain every current semantic step. Add one `QueryInvoicePdf` by known number before reversal; assert returned number and `%PDF-` signature. Upgrade the existing create/XML-query PDF checks to the same signature level. The README explicitly presents independent PDF retrieval as the happy path ([README.md:26,77–86](../../crates/szamlazz-agent/README.md#L26-L86)). Cost: one read, zero extra documents. Do not require byte-identical PDFs or add all-selector live permutations.
2. **Proforma journey:** retain standalone create/delete with both absence checks. This covers deletion, not conversion; it is not redundant with a proforma consumed by an invoice.
3. **Taxpayer smoke:** keep separately selectable so a NAV outage is visible as that dependency's failure. A small additional assertion that the reported stem matches the requested known stem would improve identity checking without pinning mutable company text. Avoid a catalogue of invalid prefixes live; offline path/error cases already cover parser decisions.

The few serious vendor edges already fit this core: half-forint arithmetic accepted and persisted, replacement versus additive credit entries, explicit older fulfillment retained on storno, storno relationship and repeat identity, and actual proforma disappearance. They are worth their small cost even with broad mocks.

### P2 — consolidate the useful optional checks

4. **Populated clearing:** when releasing/using `ClearCreditEntries`, append one clear and read-back after the core's `[200,50]` state, before storno. Check echoed number, full outstanding and empty entries. This retains the strongest clear evidence with no additional invoice/storno pair. Tradeoff: storno would then target an empty-credit invoice, whereas today's journey reverses a credited one. If retaining that path matters, deliberately register and verify one small entry after the successful clear; do not silently claim both paths from the consolidated sequence. Then retire the duplicate populated probe from regular selection; preserve its dated execution note. Keep already-empty clearing as a targeted experiment, rather than an obligatory second invoice.
5. **Receipt acceptance:** select the existing receipt lifecycle as the one extra journey for receipt consumers; its body already asserts enough to justify promotion. Keep it independent because it needs its own prefix. Do not pull MNB or email into its default path. Result: **three invoice-oriented agent scenarios, or four with receipt acceptance**, rather than all ten.

### P3 — retain investigations, drop their routine cost

6. **Appearance mismatches:** keep executable sources/evidence for changes to appearance handling or a specific vendor question. Do not routinely issue two extra originals to reconfirm acceptance of mismatched stornos. Matching paper behavior remains core; the testing guide places matching electronic and EUR chain journeys in the separately reviewed worker live layer ([testing.md:198–216](../testing.md#L198-L216)). That is documented cross-layer allocation, not an independent verification of the worker tests in this review. If agent acceptance must later be fully standalone, choose one representative matching electronic journey instead of promoting both mismatches.
7. **MNB:** run only when automatic foreign-currency receipts are relevant or that behavior changes. Retain the existing test; do not generalize its evidence to invoice conversion or every currency.
8. **Email:** manual capability check with inbox confirmation and the current pacing; report protocol and inbox observations separately. A fixed 16 s delay is not an account-wide rate-limit guarantee. Exclude it from blanket release acceptance and prefer filtered selection over Dagger's all-probes mode.

### Explicitly defer

- No live Cartesian product of kinds, templates, languages, selectors, flags, monetary lexical forms or error codes. No need to manufacture malformed XML, broken HTTP replies or credential failures against the vendor: controlled offline tests are the right regression boundary for the library's handling of those inputs.
- No new general replay/timeout/delayed-write experiment in this small suite. Empty reads and elapsed time cannot prove non-execution; the current helper correctly preserves unresolved sends. Historical external-id uniqueness, duplicate-toggle and fingerprint investigations remain evidence, not assumptions that can be proved by a quick smoke ([behavior.md:66–90](../szamlazz-hu-behaviour.md#L66-L90), [README.md:91–167](../../crates/szamlazz-agent/README.md#L91-L167)).
- Combined `simpleItems`/preview acceptance, corrective lifecycle, zero-total storno, account changes and rendering/template inspection should be issue-driven investigations when those capabilities matter. Existing schema conflicts and synthetic coverage do not establish server acceptance; equally, their existence does not justify adding all of them to rarely run main-use acceptance ([simple_items.rs:20–91](../../crates/szamlazz-agent/tests/simple_items.rs#L20-L91), [fixtures/SOURCES.md:193–226](../../fixtures/SOURCES.md#L193-L226), [behavior.md:194–204](../szamlazz-hu-behaviour.md#L194-L204)).

## Bottom line and limits

The current core is a good fit for rarely run vendor acceptance. Its principal gap is a missing main-use operation, standalone PDF retrieval, not an insufficient count of edge cases. The probe set should remain a menu: retain valuable experiments and their records, consolidate overlapping clearing setup, and select the receipt lifecycle when receipts are part of the release.

All proposed evidence remains account-, setting-, date- and execution-specific. Test-mode acceptance does not establish live-account behavior, NAV reporting, PDF rendering or email contents. Mocks and XSD validation support local correctness; they cannot replace persisted vendor read-back. Conversely, a successful live journey is not exhaustive protocol coverage, proof of concurrency safety, or permission to rerun an uncertain write. This assessment adds no new vendor observation.
