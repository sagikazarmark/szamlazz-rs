# szamlazz-agent — API conformance review

**Revision:** `837dad024300e2a202c2b6351fcba73df82a7744`

**Reviewed:** 2026-09-11

**Baseline:** current docs.szamlazz.hu documentation, inline and downloadable XSDs, official examples; first-party PHP and NAV sources where needed. Recorded live-tested differences are assessed separately.

## Executive conclusion

**The crate implements the documented operation families comprehensively, with one material capability gap and one smaller request-representation exclusion.** No additional confirmed operational/parser defect was established. This is not an unconditional claim of complete API support or live acceptance of every combination.

| Priority | Finding | Effect |
|---|---|---|
| **P2** | Empty credit-entry replacement is blocked | The checked built-in operation cannot submit the documented zero-entry replacement shape. |
| **P3** | Explicit `fizetve=false` is unavailable | False and omission cannot be selected independently; a different server-side paid-state effect is unproven. |

Priorities describe follow-up importance, not observed production incidents. Both are deliberate local restrictions, **not recorded live-tested exceptions**. The first is a capability-completeness issue; the second is a narrower wire-representation issue, with corroborating PHP-wrapper behavior.

Important unresolved questions concern numberless successful credit acknowledgements, conflicting preview/simple-item schema order, and current NAV response forwarding. They are not counted as confirmed defects.

Six subagents independently reviewed separate operation groups against freshly retrieved sources. A seventh adjudicated disputed conclusions. This consolidated report adopts that adjudication: the operation reports' broad “no confirmed defect” summaries must be qualified by the two exclusions above. Detailed reports retain their original findings and evidence for traceability.

## Findings

### F1 — P2: documented empty replacement cannot pass the checked API

**Code:** [`ops/credit_entry.rs:217–223`](../../crates/szamlazz-agent/src/ops/credit_entry.rs#L217), constructor at lines 175–187; [`wire.rs:402–408`](../../crates/szamlazz-agent/src/wire.rs#L402).

The [official credit-entry request definition](https://docs.szamlazz.hu/agent/credit_entry/xml) says:

> If true, former credit entries are retained; otherwise they are replaced.

It permits `kifizetes` with `minOccurs="0" maxOccurs="5"`; the [downloadable XSD](https://www.szamlazz.hu/szamla/docs/xsds/agentkifiz/xmlszamlakifiz.xsd) agrees. There is no documented nonempty-only restriction for replacement.

However, `RegisterCreditEntry::validate` rejects `additive == false && entries.is_empty()` with `EmptyCreditEntryReplace`. Both `to_wire` and the bundled client use this check. Thus callers cannot intentionally replace the existing entries with an empty set through the checked built-in operation. A zero-valued or compensating negative entry is not an equivalent empty set.

**Evidence qualification:** the local refusal is certain; the exact deployed clearing effect has not been live-tested. The behavior notes explicitly leave zero-entry replacement unverified. The crate's README documenting its own restriction does not supply a vendor requirement or a live-test exemption. The unchecked XML writer can emit the shape, but that is not support through the normal checked operation.

**Recommendation:** provide an explicit checked way to request empty replacement, or retain it openly as an unsupported documented capability. An interface can distinguish intentional clearing from accidentally leaving a constructor's collection empty. Confirm the server's exact effect before describing it as an observed clearing operation.

### F2 — P3: explicit false paid flag cannot be represented

**Code:** [`ops/invoice.rs:178–180`](../../crates/szamlazz-agent/src/ops/invoice.rs#L178), writer at [lines 802–804](../../crates/szamlazz-agent/src/ops/invoice.rs#L802).

The [inline invoice request XSD](https://docs.szamlazz.hu/hu/agent/generating_invoice/xml) and [download](https://www.szamlazz.hu/szamla/docs/xsds/agent/xmlszamla.xsd) declare optional boolean `fizetve`, without a schema default/fixed value. The wire can express absence, false and true.

`InvoiceHeader.paid` is a plain bool, and the writer emits the element only when true. No built-in value emits `<fizetve>false</fizetve>`.

**Impact and counter-evidence:** this is a confirmed representation exclusion, not proof of incorrectly paid invoices. Official PHP 2.12.4 uses the same true-only emission. No recorded comparison establishes whether omission and false differ under any payment method or account default.

**Recommendation:** either expose the three states or obtain an authoritative equivalence guarantee. Keep the current limitation distinct from a live-verified equivalence claim. If false can override automatic paid treatment, this becomes a functional compatibility defect.

## Unresolved compatibility questions

### Q1 — Successful credit reply without an echoed invoice number

**Code:** [`ops/credit_entry.rs:250–256`](../../crates/szamlazz-agent/src/ops/credit_entry.rs#L250).

The [response page](https://docs.szamlazz.hu/agent/credit_entry/response) makes the number optional in its schema and says headers “may also arrive.” A synthetic HTTP 200 response with no number header and this valid XML was reproduced as `Missing("szamlaszam")`:

```xml
<xmlszamlavalasz xmlns="http://www.szamlazz.hu/xmlszamlavalasz">
  <sikeres>true</sikeres>
  <kintlevoseg>0</kintlevoseg>
</xmlszamlavalasz>
```

The response XSD covers both success and error; the successful example includes a number, while errors omit it. Consequently schema optionality alone does not settle the success-specific guarantee. Recorded successful credit replies are numbered. This remains a **high-priority contract question**, with potential P2 impact if the numberless form is legitimate.

Ask whether every successful version-2 credit registration echoes a nonblank number in at least one channel. If not, accept success with optional **reported** identity rather than silently treating the requested number as a vendor echo. The present parser returns uncertainty; it does not automatically resend or duplicate entries.

### Q2 — Combined preview and simple-item ordering

**Code:** [`ops/invoice.rs:819–825`](../../crates/szamlazz-agent/src/ops/invoice.rs#L819).

The current [EN](https://docs.szamlazz.hu/agent/generating_invoice/xml) and [HU](https://docs.szamlazz.hu/hu/agent/generating_invoice/xml) inline schemas order `simpleItems` before `elonezetpdf`. The downloadable schema and official PHP 2.12.4 order preview before simple items, matching Rust.

The contradiction is confirmed. Deployed acceptance of the combined request, including its non-issuing preview behavior, is unverified. Reordering solely to satisfy one source would contradict another. Request an authoritative order and align the vendor schemas.

### Q3 — Current taxpayer response contract

The crate supports genuine NAV 2.0 and 3.0 namespace layouts and all examined taxpayer business/address fields. The [Számla Agent examples](https://docs.szamlazz.hu/agent/querying_taxpayer/response) are dated 2020-11-04 and use 2.0, while the delegated NAV specification is 3.0.

Outstanding questions:

- Can `funcCode=OK` legitimately omit `taxpayerValidity`, and what does that mean? The crate requires it on OK, permits absence on ERROR, and never substitutes false.
- Does Számla Agent forward generic NAV failure roots, or always its documented taxpayer response type?
- Which newer optional fields are currently forwarded?

Direct NAV possibilities are not proof of intermediary behavior. Updated complete Számla Agent examples or captures are needed.

“Field coverage” does not mean lossless raw-response retention, full XSD value-space acceptance, or local enforcement of every vendor business rule. In particular:

- The crate selects response version 2 where a choice exists; raw version 1 is not selectable.
- Finite exact Decimal/civil-date policies are narrower than arbitrary XML Schema values. They refuse unrepresentable money rather than silently changing it.
- Unknown tokens and well-formed extensions are handled permissively; the parser is not a full XSD validator.
- Taxpayer exchange/software/notification metadata is omitted from the business projection. Additional PDF headers and numberless-preview metadata have qualified projection limits. No additional operation-specific required mapping was established.
- Prefix eligibility, tax treatment, tender sums, linkage, rendering and account configuration remain largely vendor/caller responsibilities. Not duplicating those validators is distinct from blocking a supported request such as F1.

## Recorded live-tested deviations retained

The [behavior record](../szamlazz-hu-behaviour.md) is explicitly bounded to one TEST account and dated September 3/6/7 observations; historical raw logs are outside the repository. This review accepted the recorded observations within that scope, without claiming to have independently inspected unavailable logs.

| Observation | Treatment |
|---|---|
| Repeat invoice storno echoes existing SS; storno of proforma/delivery note can be a success-shaped no-op | Preserve the distinction between a successful reply and demonstrated reversal. |
| Storno external id attaches to SS; dates/appearance can differ from caller expectations or terse docs | Preserve the observed meaning and guidance to derive original date/appearance. |
| Create issue date can be replaced by today; final invoice does not automatically deduct prepayment | Preserve qualified date documentation and caller-supplied negative prepayment rows. |
| External ids are nonunique and queries select their newest holder | Keep external id as a query handle, not an idempotency key or ownership proof. |
| Proformas can be consumed implicitly; stale links can be silently ignored; paid proformas can be deleted | Preserve explicit linking and caller-owned reconciliation/retention policy. |
| Comma monetary headers, invoice rounding/storage behavior, permissive VAT decimal spelling | Retain demonstrated compatibility; do not extrapolate invoice probes to receipt/currency combinations that were not tested. |

Other justified choices have different evidence: **numbered code 56** has first-party PHP/documentation support rather than a successful live probe; **automatic MNB on receipts** is receipt-specific PHP documentation evidence; the **60-second timeout** is a local policy, not a vendor-mandated constant.

No receipt lifecycle appears in the current live tests. The behavior note also names an older appearance test that has since been split into the lifecycle and separate probes. Test presence is not proof of execution at this revision.

## Recommended next steps

1. Decide how the checked API should expose intentional empty credit-entry replacement; keep the unsupported capability explicit until resolved.
2. Resolve successful credit-response number requirements and combined preview/simple-item ordering with the vendor.
3. Decide whether to expose explicit false `fizetve`, informed by vendor omission/default semantics.
4. Obtain current taxpayer wrapper examples and resolve the remaining source contradictions listed above.
5. When expanding live verification, prioritize receipt lifecycle/call identity, email behavior and foreign-rate handling; existing invoice observations do not establish those behaviors.

**Bottom line:** strong operation and field coverage, one substantive documented capability exclusion, one smaller representation exclusion, and several vendor-contract questions. The evidence supports targeted follow-up rather than wholesale changes to the serializers or parsers.
