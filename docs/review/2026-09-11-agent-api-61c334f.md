## 1. Confirmed implementation finding

### F1 — P3: outbound dates can have invalid XSD 1.0 year spellings

**Location:** [`src/xml.rs:598–607`](../../crates/szamlazz-agent/src/xml.rs#L598), shared by invoice header/ledger dates, storno dates and credit-entry dates.

The writer uses `jiff::civil::Date::to_string()` directly. Jiff permits year zero and negative years:

```text
Date(0, 1, 1)   → 0000-01-01
Date(-1, 1, 1)  → -000001-01-01
```

The vendor request schemas declare these elements as `xs:date`. [XSD 1.0's date grammar](https://www.w3.org/TR/xmlschema-2/#date), through its [dateTime year grammar](https://www.w3.org/TR/xmlschema-2/#dateTime-lexical-representation), prohibits year `0000` and leading zeroes in years longer than four digits. Both examples can pass `to_wire` but fail that lexical contract. The adjudicator independently reproduced this through credit-entry and storno requests.

**Impact:** a year-zero sentinel or nonsensical ancient business date can leave the typed request boundary as nonconforming XML. Ordinary contemporary dates are unaffected. No live vendor rejection or ordinary-invoice failure is claimed.

**Recommendation:** define and validate the outbound year domain consistently across all date-bearing requests, preferably positive years for this business domain. Return a request error instead of silently translating dates. Cover a required date, an optional nested date and a normal leap-day control.

The README's deliberately lenient **response-reader** policy does not justify invalid outbound spellings. Fixing this need not narrow accepted response dates. Receipts have no outbound date field, so they are not an affected writer.

**Evidence:** [invoice report, I-01](2026-09-11-agent-api-61c334f-invoices.md#i-01--p3-shared-date-writer-accepts-jiff-years-which-are-not-valid-xsd-10-dates); [invoice request definition](https://docs.szamlazz.hu/agent/generating_invoice/xml), [storno definition](https://docs.szamlazz.hu/agent/reversing_invoice/xml), [credit-entry definition](https://docs.szamlazz.hu/agent/credit_entry/xml).

## 3. Nonblocking improvements and representation boundaries

### Recovery and identity hardening

- **Unreadable optional PDF can hide readable document data.** Receipt parsing propagates corrupt nonblank base64 at [`receipt.rs:690–701`](../../crates/szamlazz-agent/src/ops/receipt.rs#L690). Ordinary invoice/storno envelopes and XML queries have the same general boundary; numbered code 56 has special salvage behavior. A richer result could preserve usable identity alongside an artifact diagnostic. This is an improvement for malformed replies, not failure on valid encoded PDFs. Current uncertainty must not be interpreted as permission to issue again.
- **Blank document numbers can parse successfully.** XML-query `alap/szamlaszam` and receipt `nyugtaszam` use unvalidated string wrappers. Their XSD string types permit blank values, so a nonblank guarantee would be an additional domain contract. If adopted, enforce it locally on both document parsers while preserving nonblank text; do not import the worker's invoice-number alphabet.

### Feature/projection limitations

- **Gross-first HUF calculation:** documented gross-first B2C amounts are fully expressible with `LineItem::new`; `try_calculated` is net-first. A documented recipe or separately named helper would improve ergonomics. There is no missing wire capability or demonstrated defect in the net-first helper.
- **Taxpayer envelope metadata:** `TaxpayerInfo` exposes the business fields, including detailed addresses, short name, county code, VAT group, incorporation and `infoDate`. It omits NAV header/software metadata and notifications. This is a real projection limitation, not a missing taxpayer business field; it matters if callers need lossless diagnostics.
- **Sparse `OK` taxpayer reply:** validity is required by explicit library policy despite schema optionality. Normal invalid-taxpayer replies contain explicit false. Do not manufacture false from a missing verdict merely to accept a broader schema shape.
- **Version 2, finite Decimal and civil dates:** selecting structured replies, refusing unrepresentable monetary values and using civil-date projections are deliberate supported-domain choices. They do not claim complete XSD value-space coverage. The outbound lexical hole in F1 is distinct from supporting a narrower valid domain.

### Evidence documentation maintenance

The behavior ledger still says clear-all credit entries are not offered ([lines 211–215](../szamlazz-hu-behaviour.md#L211)), although `ClearCreditEntries` now exists. Its statement that zero-entry execution was not established remains valid. The ledger also points to a former `eszamla_semantics` test name. Update those capability/navigation statements without upgrading unexecuted probes to live evidence.

The largest remaining assurance gap is **schema-validation coverage**. Current upstream tests compare examples through a deliberately lossy outline, omit empty containers and trim text. Reviewers compared freshly fetched definitions field by field, but did not execute a complete XSD validator over generated requests. A meaningful follow-up would validate full optional-field matrices against separately identified, unmodified source schemas, explicitly recording expected failures caused by vendor disagreements. A synthesized schema silently merging those sources would not prove vendor acceptance.

Other remaining evidence gaps are combined simplified-preview acceptance; numberless successful credit replies; actual zero-entry clearing; receipt lifecycle/call-ID retention, MNB and resend behavior; current forwarded NAV 3/generic errors; rendered templates and notification delivery. Existing synthetic tests cannot settle those vendor behaviors.

## Recommended next steps

1. Fix the shared outbound date-domain hole and add focused boundary tests.
2. Seek vendor clarification on credit acknowledgement identity and the conflicting schemas, particularly combined preview/simplified items.
3. Add explicitly source-labelled XSD request validation and refresh stale evidence-index prose.
4. Consider structured partial-artifact recovery and nonblank parsed identities as API design improvements.

**Bottom line:** the ordinary documented Agent surface is implemented thoroughly, and the review found no missing in-scope operation or ordinary field-mapping defect. One small outbound lexical defect warrants correction. The remaining work is principally resolving contradictory source contracts and strengthening evidence and recovery behavior.
