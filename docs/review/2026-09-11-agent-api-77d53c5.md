**Reviewed:** 2026-09-11. **Verdict: qualified pass.** All **11 documented Számla Agent operations** are implemented. ## 1. Confirmed findings

### F1 — P3: numbered code-56 documentation overstates the exception

**Location:** [`src/error.rs:369–372`](../../crates/szamlazz-agent/src/error.rs#L369).

The public `outcome_class` documentation says code 56 only surfaces as an error without a document number, and that with a number “the parsers report success.” That is not true across the operation parsers. Credit-entry registration retains code 56 as an API error even with a number; explicit clearing delegates to the same parser. Existing [`tests/response_headers.rs:203–223`](../../crates/szamlazz-agent/tests/response_headers.rs#L203) asserts this, and the adjudicator independently reproduced it at HTTP 200.

The [official PHP response guidance](https://docs.szamlazz.hu/php/valasz-feldolgozas) and its source corroborate **issuance with notification failure**, not success of a credit mutation merely because an invoice number is present.

**Impact:** misleading public guidance when interpreting numbered errors. The operation-specific runtime behavior should remain.

**Recommendation:** scope the documented exception to issuing-response handling; preserve uncertainty for ordinary operation parsers and ambiguous/malformed identity. See [adjudication A-D2](2026-09-11-agent-api-77d53c5-adjudication.md).

### F2 — P3: receipt execution-evidence summary is stale

**Locations:** [`src/error.rs:373–374`](../../crates/szamlazz-agent/src/error.rs#L373), [`src/recovery.md:57–62`](../../crates/szamlazz-agent/src/recovery.md#L57).

The shared documentation still describes receipt/simplified-image additions as unobserved. The September 11 record contains a directly observed **337** prefix refusal, contradicting the blanket absence of observations; it also records a completed-create repeat returning **338** and a subsequent query of the original. The variant documentation already mentions the observed prefix restriction.

**Impact:** incorrect evidence provenance, with no change to wire behavior or classification.

**Recommendation:** identify the newly corroborated codes, date and separate test-account scope. Keep historical documentation provenance and the remaining untested codes distinct. Do not imply that 338 is one of the thirteen later additions or that the new receipt account is the historical invoice account. See [adjudication A-D1](2026-09-11-agent-api-77d53c5-adjudication.md).

### F3 — Low-priority completeness gap: taxpayer diagnostic metadata is unavailable

**Locations:** [`src/ops/taxpayer.rs:184–225`](../../crates/szamlazz-agent/src/ops/taxpayer.rs#L184), recognized paths at 343–397, result conversion at 592–610.

The [official taxpayer success example](https://docs.szamlazz.hu/agent/querying_taxpayer/response) includes response-header correlation/version fields and software metadata. `TaxpayerInfo` exposes neither. Successful result messages are discarded, and NAV informational notifications have no projection either; actual Agent forwarding of the latter remains unverified.

**Impact:** users of the built-in typed request cannot retain those diagnostics through `Client::send`. All inspected taxpayer **business/address fields** are represented, so this is not an incorrect validity or taxpayer-data result.

**Recommendation:** decide explicitly whether to expose optional diagnostic metadata or document the projection boundary on the public result. A custom transport/request can retain raw XML, but that is additional consumer work. See [taxpayer metadata inventory](2026-09-11-agent-api-77d53c5-taxpayer.md) and [adjudication A-C1](2026-09-11-agent-api-77d53c5-adjudication.md).

## 2. Reproduced compatibility questions needing a contract decision

These are concrete implementation/source differences, not dismissed merely because the current Rust types or README describe them. Their occurrence in valid vendor exchanges remains unresolved.

### Q1 — Successful responses without a reported invoice number

The [credit-entry](https://docs.szamlazz.hu/agent/credit_entry/response), [PDF-query](https://docs.szamlazz.hu/agent/querying_pdf/response) and [storno](https://docs.szamlazz.hu/agent/reversing_invoice/response) response schemas make `szamlaszam` optional; accompanying prose says optional elements may be omitted and headers may arrive. The corresponding parsers require a nonblank number from body or header.

Reproduced outcomes:

| Input, HTTP 200 without number headers | Result |
|---|---|
| Credit registration or clearing: `xmlszamlavalasz` containing only `sikeres=true` | `Parse(Missing("szamlaszam"))` |
| PDF query: successful envelope containing a decodable PDF but no number | Same error; usable artifact unavailable through the typed result |
| Storno: bare successful envelope | Same error; reversal identity remains unresolved |

All these are formal schema/parser differences. However, the schemas combine success and failure, and the successful examples are numbered. Neither those examples nor two observed numbered clearing replies prove a universal success-only echo guarantee. Conversely, the published sources do not establish the stricter Rust requirement. **No live-evidence exemption resolves this question.**

**Next step:** ask whether every successful operation guarantees a nonblank invoice number in at least one channel. Credit acknowledgements and fetched PDFs are the strongest candidates for supporting optional reported identity if omission is legitimate. Do not substitute the request's number as a claimed vendor echo, and do not interpret this parse failure as permission to resend a mutation. [Detailed adjudication and sources](2026-09-11-agent-api-77d53c5-adjudication.md#2-numberless-success-formal-incompatibility-established-emission-unresolved).

### Q2 — Customer-account URL header decoding differs from official PHP

**Locations:** [`src/ops/envelope.rs:135–143`](../../crates/szamlazz-agent/src/ops/envelope.rs#L135), [`src/wire.rs:343–350`](../../crates/szamlazz-agent/src/wire.rs#L343).

Official PHP 2.12.4 uses `rawurldecode` for `szlahu_vevoifiokurl`, preserving literal `+`. Rust uses the shared form decoder, which turns `+` into a space. The adjudicator reproduced:

```text
Header: https%3A%2F%2Fexample.test%2Fa+b%3Ftoken%3Dc+d
PHP:    https://example.test/a+b?token=c+d
Rust:   https://example.test/a b?token=c d
```

**Impact if such a header is emitted:** corrupted buyer-facing URL in invoice/storno/credit/clear/PDF header fallback. XML-body URLs are unaffected. Both decoders agree if the vendor always outer-encodes plus as `%2B`.

The decoder disagreement is confirmed; the producer's exact encoding grammar and an affected exchange are not. **Next step:** seek raw-header evidence or an encoding guarantee; consider field-specific percent-only decoding for PHP parity. Do not change invoice-number/error decoding globally. [Detailed evidence](2026-09-11-agent-api-77d53c5-adjudication.md#3-customer-url-header-actual-decoder-disagreement-no-captured-affected-exchange).

### Q3 — Native NAV generic error forwarding

The taxpayer parser supports NAV 2/3 `QueryTaxpayerResponse`, as the [Agent response page](https://docs.szamlazz.hu/agent/querying_taxpayer/response) promises. NAV itself also defines generic error roots, which are not decoded into typed API errors here. NAV's direct contract does not prove Agent forwards those roots.

**Next step:** obtain an Agent-specific capture or vendor confirmation before treating this as a missing error path. [Taxpayer T-S1](2026-09-11-agent-api-77d53c5-taxpayer.md).

Fresh schema checks reproduced the structural conflicts using **unmodified, separately identified schemas**. No synthesized merge was treated as the vendor contract. Exact URLs, hashes, failing inputs and diagnostics appear in the specialist reports.

**Passed:** 430 generated requests across all eleven actions and both credential forms; 860 document/schema checks against 22 source-labelled EN-inline/download schemas: **790 valid, 70 expected source conflicts**. All declared element paths occurred in a fully valid request for each schema. All **seven negative controls** were rejected as intended. These strengthen the source comparison without implying every field combination or business/account rule was exercised.

The public low-level writer is explicitly unchecked. Existing namespace/verdict, body-only error, incomplete-transfer and numbered-56 regression protections also passed.

### Remaining limits

- No new live acceptance, PDF rendering/signature validation, browser runtime or fresh wasm-build result is claimed.
- Exact finite Decimal and civil-date models are narrower than full XSD value spaces; readers are tolerant projections, not complete schema validators or raw archives. No ordinary supported value was demonstrated corrupted.
- Optional improvements include retaining document identity alongside a corrupt optional PDF, nonblank query/receipt identity validation, a gross-first calculation recipe, and direct regression tests for credit/clear numberless success. These are not counted as established valid-exchange defects.
