# Számla Agent — API implementation review

**Date:** 2026-09-11

**Reviewed revision:** `2ba5fb86d9e3365a7c2e9bd99c4fce880fa1ab81`

**Method:** six parallel specialist reviews of current code against freshly fetched official sources, followed by independent adjudication and lead review.

## Executive conclusion

**The crate implements all eleven documented Számla Agent operations and represents all reviewed documented business fields. No missing operation, missing applicable business field, or confirmed failure on an ordinary documented vendor response was established.** The request writers, selectors, response models and open error catalogue have extensive coverage.

**Four findings remain: two P2 implementation corrections and two P3 conformance/documentation corrections.** The most directly actionable is secret disclosure through `Debug` when using the vendor-supported legacy key/key authentication form. The second P2 concerns accepting ambiguous response identity under the numbered-code-56 fallback; its triggering replies are synthetic, not captured vendor behavior.

Numberless successful credit-entry acknowledgement remains the most important unresolved compatibility question. Receipt NAV setup merits a documentation addition. Neither is counted as a confirmed operational defect on the available evidence.

This is the consolidated disposition. It supersedes specialist severity disagreements: the mutation report calls numberless credit success a medium defect, and the receipt report ranks omitted setup guidance P2; adjudication qualifies both below. Earlier September 9/10 reports describe older revisions and must not be used as a current defect list.

### F1 — Agent key leaks through supported legacy authentication

**Code:** [`credentials.rs:88–96`](../../crates/szamlazz-agent/src/credentials.rs#L88), propagation in [`client.rs:149–158`](../../crates/szamlazz-agent/src/client.rs#L149) and [339–345](../../crates/szamlazz-agent/src/client.rs#L339).

The [official authentication page](https://docs.szamlazz.hu/agent/basics/authentication) explicitly allows using the same agent key in `felhasznalo` and `jelszo`. The credential formatter hides only the password:

```rust
format!("{:?}", Credentials::user_password("example-secret", "example-secret"))
// Credentials::UserPassword { username: "example-secret", password: "…" }
```

Formatting the corresponding client or builder also reveals it. Preferred `Credentials::agent_key` is correctly redacted. This is a real secret-bearing use of the username field under the published protocol, not an arbitrary secret placed in an unrelated string.

**Recommendation:** redact both legacy fields in `Debug` and cover the key/key form in a focused regression. Preserve the supported wire authentication form.

[Specialist reproduction](2026-09-11-agent-api-transport.md#t-01--p2-legacy-authentication-aliases-expose-the-agent-key-in-diagnostics) · [Independent verification](2026-09-11-agent-api-adjudication.md#t-01--p2-a-supported-credential-alias-defeats-secret-redaction).

### F2 — Notification-failure leniency also hides invalid identity

**Code:** [`ops/envelope.rs:208–211`](../../crates/szamlazz-agent/src/ops/envelope.rs#L208), identity fallback at [288–318](../../crates/szamlazz-agent/src/ops/envelope.rs#L288).

Under error 56, optional totals/PDF may be unreadable without hiding a valid issued-document number. The code separately checks body identity, but subsequently swallows a failure of that check as though it were optional metadata.

Completed synthetic reply, HTTP 200, with `szlahu_error_code: 56` and `szlahu_szamlaszam: I-4`:

```xml
<xmlszamlavalasz xmlns="http://www.szamlazz.hu/xmlszamlavalasz">
  <sikeres>false</sikeres><hibakod>56</hibakod>
  <szamlaszam>I-2</szamlaszam><szamlaszam>I-3</szamlaszam>
</xmlszamlavalasz>
```

`StornoInvoice::new("I-1").parse(...)` returns `CreatedInvoice` naming **I-4**, with notification failure true. Nested identity and identical duplicates reproduce it too. Body 56 plus just the number header is sufficient. Ordinary success with the same invalid body identity is refused.

The [response schema](https://www.szamlazz.hu/szamla/docs/xsds/agent/xmlszamlavalasz.xsd) declares a singleton scalar number. More importantly, the crate explicitly limits leniency to optional metadata and promises duplicate/scalar-child rejection. Malformed identity is not equivalent to absent identity.

**Recommendation:** preserve the distinction between absent identity and a failed identity check. Continue header fallback for genuine absence and retain a valid unique number despite malformed optional metadata; return uncertainty for malformed/duplicate identity. Add number-header-present negative controls.

**Qualification:** the vendor does not specify conflict precedence for these malformed replies. This proves a local response-integrity boundary failure, not that I-4 was wrong or that a document was duplicated. Numbered-56 behavior itself is supported by first-party PHP 2.12.4; the account probes did not trigger it. A storno wire success remains distinct from a verified reversal.

[Reproduction](2026-09-11-agent-api-transport.md#t-02--p2-numbered-56-metadata-fallback-also-hides-invalid-body-identity) · [Adjudication and controls](2026-09-11-agent-api-adjudication.md#t-02--p2-optional-metadata-recovery-also-swallows-body-identity-failure).

### F3 — Two residual namespace-conformance gaps

**Code:** [`xml.rs:58–68`](../../crates/szamlazz-agent/src/xml.rs#L58), [417–427](../../crates/szamlazz-agent/src/xml.rs#L417).

Adding either `<xmlns:extension/>` or `<?p:target data?>` to an otherwise readable taxpayer reply still succeeds under NAV 2.0 and 3.0. [Namespaces in XML 1.0](https://www.w3.org/TR/2009/REC-xml-names-20091208/) §3 forbids the `xmlns` element prefix; §7 prohibits colons in processing-instruction targets.

**Recommendation:** reject precisely the forbidden element prefix and validate PI targets as NCNames. Preserve legal non-ASCII names and ordinary `xml:*` elements.

The reproduced markup is ignored and changes no taxpayer fact. This is a small shared-parser conformance correction, counted once across all consumers, not a taxpayer-specific extraction vulnerability.

[Reproduction and standards citations](2026-09-11-agent-api-taxpayer.md#tq-01--p3-shared-xml-validation-accepts-namespace-forbidden-markup) · [Adjudication](2026-09-11-agent-api-adjudication.md#tq-01--p3-namespace-invalid-extension-markup-passes-shared-validation).

### F4 — Qualify unsupported protocol guarantees

**Code:** [`error.rs:3–5`](../../crates/szamlazz-agent/src/error.rs#L3), [333–340](../../crates/szamlazz-agent/src/error.rs#L333).

- “Never via HTTP status codes” overgeneralizes the documented in-band domain-error mechanism. The actual client already handles non-2xx conservatively.
- Credential codes occurring “before it looks at the request (its documentation)” is stronger than the [authentication](https://docs.szamlazz.hu/agent/basics/authentication) and [error](https://docs.szamlazz.hu/agent/basics/error-handling) pages establish. Fixing credentials also cannot guarantee that later document validation succeeds.

**Recommendation:** describe the documented error meanings and qualify the integration's interpretation. Keep current uncertainty/recovery rules; no runtime reclassification follows from this documentation finding. The adjacent “endpoint never redirects” comment merits the same provenance cleanup while retaining the no-redirect policy.

[Detailed comparison](2026-09-11-agent-api-transport.md#t-03--p3-qualify-protocol-guarantees-not-established-by-current-sources).

## 2. Compatibility questions and documentation opportunities

### Highest priority: successful credit registration without an echoed number

[`RegisterCreditEntry::parse`](../../crates/szamlazz-agent/src/ops/credit_entry.rs#L250) refuses HTTP 200 with `<sikeres>true</sikeres>` but no number in body or headers. This reproduces for both additive and replacing requests.

The [EN](https://docs.szamlazz.hu/agent/credit_entry/response) and [HU](https://docs.szamlazz.hu/hu/agent/credit_entry/response) schemas make the number optional and their prose says headers may arrive. That establishes a schema-permitted instance the crate cannot represent. However, the schema covers success **and failure**, and every fetched successful example and recorded successful observation is numbered. Neither an always-numbered guarantee nor an operational numberless-success case is established.

**Disposition:** unresolved success-specific contract question, not a confirmed P2 vendor-response failure. The existing [clarification draft](../research/2026-09-10-credit-entry-success-question.md) remains unanswered. If omission is supported, model optional reported identity or distinguish the requested target explicitly; do not invent vendor-reported identity from the request. A parse failure remains uncertain and is not permission to repeat credit entries.

[Specialist mismatch reproduction](2026-09-11-agent-api-mutations.md#finding-m-01--numberless-successful-credit-acknowledgement-becomes-a-parse-failure) · [Why the severity was qualified](2026-09-11-agent-api-adjudication.md#m-01--numberless-successful-credit-acknowledgement-unresolved-compatibility-question).

### Receipt NAV setup: useful onboarding addition

Current [Hungarian vendor guidance](https://tudastar.szamlazz.hu/gyik/nyugtaadat-szolgaltatas-kotelezettseg) describes automatic receipt reporting from September 10, retrospectively for receipts after September 1, conditional on NAV connection and the separate technical-user permission **“Hozzáférés a nyugtaadat-szolgáltatási interfészhez”**. The [connection guide, step 13](https://www.szamlazz.hu/nav-online-szamlazas-regisztracios-segedlet/#lepesek) corroborates the permission; the Agent settings page still has older “nothing to do” wording.

A dated link in receipt guidance would help integrators. This is a **P3 documentation opportunity**: no missing XML flag, false reporting-status claim or actual reporting failure was found. An issued receipt is not a NAV acceptance acknowledgement, and the published response has no such status field.

## 4. Evidence-backed deviations and deliberate boundaries

The [behavior notes](../szamlazz-hu-behaviour.md) describe dated observations on one test account; the original raw logs are outside this repository. They were consulted, not recreated.

Preserve these supported qualifications:

- External ids are nonunique, query their newest holder and attach on actual creation. They are not server idempotency keys.
- Repeating invoice storno can return its existing reversal; storno of a proforma/delivery note can be a success-shaped no-op.
- Storno external id attaches to the new SS, despite ambiguous request prose about referencing the original. Fulfillment-date and appearance observations qualify what the server accepts/defaults.
- Final-invoice lines must deduct prepayment; the server does not net it automatically. A missing explicit proforma reference may be filled by shared order behavior.
- Body-only errors, auxiliary headers, comma-decimal monetary headers, independent invoice-storage rounding and observed arithmetic tolerance remain supported.
- Numbered 56 is **first-party PHP evidence**, not a successful account probe. Receipt-specific automatic MNB omission is likewise documentation-backed rather than newly observed execution.
- Receipt email resend uses a **present empty** `emailKuldes`; absence has different documented meaning. Receipt storno must not inherit invoice replay assumptions.

Finite exact Decimal values, civil-date extraction, widened metadata integers, sparse response content, version-2 built-ins, explicit rounding policy, bounded attachments and refusal of empty replacing credit entries are deliberate library boundaries. No additional required business operation was demonstrated to depend on removing them. Local behavior, vendor documentation and live evidence remain separately identified in the specialist reports.
