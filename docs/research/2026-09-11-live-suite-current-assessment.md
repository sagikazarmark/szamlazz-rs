## 2. Remaining improvements, prioritized for minimal scope

### P1 — align optional-identity assertions with acceptance intent

The live invoice requires `Some(requested_number)` from standalone PDF retrieval and every credit-entry acknowledgement; clearing probes do likewise ([agent:75–103](../../crates/szamlazz-agent/tests/live.rs#L75-L103), [clearing:99–126](../../crates/szamlazz-agent/tests/probes.rs#L99-L126)). **Current deterministic tests intentionally accept successful responses without that number**, preserving balance metadata or PDF bytes without inventing an echo ([numberless responses:18–115](../../crates/szamlazz-agent/tests/numberless_responses.rs#L18-L115)). The clearing execution record explicitly leaves a universal number-echo guarantee unresolved ([record:64–74](2026-09-11-credit-clearing-live.md#L64-L74)).

For main-use acceptance, prefer: **if a number is reported, it must match**; retain strict outstanding/read-back checks for credits and the required artifact/signature for PDF. A missing optional echo can be recorded as vendor drift without claiming the operation failed. Never accept a mismatched echo. If mandatory echoes are deliberately desired as an account-specific drift alarm, label that stricter expectation explicitly rather than treating it as the library contract.

This does not justify relaxing storno evidence: a bare acknowledgement does not identify a reversal. The direct helper's requirement for a numbered reply plus queried storno type/original reference is a separate evidentiary requirement ([helper:162–180,280–307](../../crates/szamlazz-agent/tests/live_support/mod.rs#L162-L307)). A PDF signature alone also cannot prove which invoice is rendered; optional number handling must not be described as stronger artifact identity verification.

### P2 — one worker public-query observation, using an existing invoice

Worker live currently calls `Szamlazz.Agent.check_account`, while document inspection is through the shared **direct agent client**. `get` is already checked, but `Szamlazz.Agent.query` is not exercised against the real vendor ([worker:127–138](../../crates/restate-szamlazz/tests/live.rs#L127-L138), [214–232](../../crates/restate-szamlazz/tests/live.rs#L214-L232)). Its mocked e2e already checks the public projection, so this is a small integration gap, not missing functional coverage ([agent reads:115–139](../../crates/restate-szamlazz/tests/e2e/agent_reads.rs#L115-L139)).

Add **one by-number facade query** before the ordinary original is reversed: assert number, document type, order, test marker, currency/totals and proforma reference against the already fetched document. Cost: one read, no new document. Keep the direct inspection for appearance, which `QueryResponse` does not expose; the facade deliberately omits the seller block too ([contract:117–183](../../crates/restate-szamlazz/src/contract/agent.rs#L117-L183)). Do not expand this into a live selector or facade-handler matrix.

### P2, conditional — correctives are the strongest new business-flow candidate

There is **no corrective live scenario** in either current inventory. Mocked e2e proves correction ID, base reference/flag, issued response and fresh-key discovery, but supplies the vendor responses itself ([corrective e2e:26–125](../../crates/restate-szamlazz/tests/e2e/correct_invoice.rs#L26-L125)). The behavior record establishes one corrective referencing its base; **two distinct correctives under the same order remain unverified there** ([behavior:54–64](../szamlazz-hu-behaviour.md#L54-L64), [141–146](../szamlazz-hu-behaviour.md#L141-L146), [202–204](../szamlazz-hu-behaviour.md#L202-L204)).

If corrections are a main use, add one independently selected worker journey: ordinary base → negative corrective → query persisted type/order/base reference/totals/external-id identity → fresh-key repetition of the same correction ID returns that document. If multiple corrections are a required capability, investigate a second distinct correction ID naming the **original base**, not the first corrective. Establish that behavior before making it recurring acceptance.

Keep this separate from ordinary storno/reissue: corrected bases have historically refused storno with 221. The existing cleanup only reverses ordinary/prepayment/final originals and reports other types unsupported, so it cannot simply clean a new corrective journey ([behavior:108,145–146](../szamlazz-hu-behaviour.md#L108-L146), [cleanup:233–267](../../crates/szamlazz-agent/tests/live_support/mod.rs#L233-L267)). A verified cleanup or intentional retained-document plan is part of designing this scenario. For occasional correction use, start as a targeted investigation rather than automatically expanding core.

### P3 — useful only when the capability warrants it

- **Clearing:** retaining the populated probe is the simplest choice now. If clearing becomes routine acceptance, consolidate it into the core credit-entry sequence to save its extra original/storno pair. But clear → storno would lose today's credited-storno evidence: restore and verify an entry before reversal, or retain the separate probe. Do not consolidate merely to reduce test-function count ([core sequence:85–120](../../crates/szamlazz-agent/tests/live.rs#L85-L120), [clear sequence:87–126](../../crates/szamlazz-agent/tests/probes.rs#L87-L126)).
- **Credit metadata:** amounts/outstanding are covered; persisted date/title and a nonempty description-to-comment round trip are not. If consumers depend on these, attach one distinctive description to an existing entry and compare records by amount rather than return order. This adds no document or read. The wire names differ (`leiras` outbound, `megjegyzes` queried), making this more useful than checking every field ([request fields:21–44](../../crates/szamlazz-agent/src/ops/credit_entry.rs#L21-L44), [queried fields:518–533](../../crates/szamlazz-agent/src/ops/query_xml.rs#L518-L533)); return ordering is historically non-submission order ([behavior:154](../szamlazz-hu-behaviour.md#L154)).
- **Receipt reversal amounts:** optional receipt acceptance already checks original totals/tender sum, but `reverse()` returns a queried reversal whose net/VAT/gross/tenders are not asserted. Comparing its monetary negation with the original would strengthen financial evidence with no extra request. The dated record observed negative reversal totals and tender ([receipt helper:108–140](../../crates/szamlazz-agent/tests/probes/receipts.rs#L108-L140), [record:101–106](2026-09-11-receipts-live.md#L101-L106)). Prefer this over another receipt scenario.

## 6. Current runner setup is appropriate for rare execution

| Layer | Selection and dependencies | Recommended cadence |
|---|---|---|
| Ordinary tests / schemas | Local fixtures, generated XML and HTTP mocks; automatic Dagger checks | Every PR |
| `cargo e2e` | Actual Restate, mocked szamlazz.hu; automatic Dagger check | Every PR |
| `cargo live` | Five core scenarios; actual szamlazz.hu, plus actual Restate for the two worker journeys | Manual acceptance for relevant releases/vendor changes |

Sources: [aliases](../../.cargo/config.toml#L1-L5), [profiles](../../.config/nextest.toml#L5-L43), [automatic Dagger checks](../../.dagger/modules/ci/main.dang#L39-L91), [manual Dagger runner](../../.dagger/modules/ci/main.dang#L135-L166).

**Keep these existing controls:**

- Live/probes are ignored by default, even with credentials present. Aliases explicitly select all features and ignored tests; selecting agent live without transport fails through a sentinel rather than silently running nothing. Missing credentials fail a selected test; missing Restate fails a selected worker journey ([agent live:2–14](../../crates/szamlazz-agent/tests/live.rs#L2-L14), [key helper:38–43](../../crates/szamlazz-agent/tests/live_support/mod.rs#L38-L43), [worker start:31–43](../../crates/restate-szamlazz/tests/live.rs#L31-L43)).
- Both vendor profiles are serial, fail-fast, with zero whole-test retries and successful output retained in JUnit. Their slow timer reports progress without forcing termination of a possibly executing write. Serialization is per runner; concurrent runs against one reused Restate server are not isolated ([profiles:21–43](../../.config/nextest.toml#L21-L43), [server guidance](../testing.md#L59-L65)).
- The worker live harness validates production retry policy configuration, rather than using mock-suite shortened policies ([worker:41–43](../../crates/restate-szamlazz/tests/live.rs#L41-L43)). Zero nextest retries does not mean the worker has no internal durable retries.
- Shared fixtures use UUID order/external ids and log write intent, known numbers and ingress invocation ids. Cleanup reverses known documents in dependency order and deletes remaining proformas; an unresolved write defers mutation cleanup. Successful worker journeys join their local endpoints with `Restate::finish()` ([shared helper:79–138,195–277](../../crates/szamlazz-agent/tests/live_support/mod.rs#L79-L277), [worker call:82–125](../../crates/restate-szamlazz/tests/live.rs#L82-L125), [worker finish:293–297](../../crates/restate-szamlazz/tests/live.rs#L293-L297)).
- Dagger live is manual, injects credentials as a Secret, accepts a nextest filter and requires a fresh run label to invalidate cached execution evidence. The previously recommended filter support **already exists**. Failures expose JUnit and retained server logs through the Dagger trace ([runner:94–112,135–166](../../.dagger/modules/ci/main.dang#L94-L166), [execution freshness](../testing.md#L295-L333)).

Use the intended test account with EUR/e-invoice support and the documented order-number setting. The `test=true` assertion happens after creation, so these runs test the selected account rather than establish the deployed resolver mapping; deployment/rotation seller checks remain separate ([guide:173–177](../testing.md#L173-L177)).

**Cadence:** retain the existing manual policy: run core before a release materially changing transport, XML, arithmetic, conversion or the worker write protocol, and after relevant vendor changes. Documentation-only changes need no new vendor evidence. If no such release has produced evidence for a long time, a quarterly manual drift check is reasonable. Select receipt lifecycle or populated clearing for changes to those capabilities; select appearance/MNB/email only for their specific question. Record the source revision, selection, run label and dated outcome. This is already substantially documented in [testing.md:157–171](../testing.md#L157-L171); no new runner framework or scheduled write job is needed.
